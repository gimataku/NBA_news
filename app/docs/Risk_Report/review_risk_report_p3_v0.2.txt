[YEL-01] バッチをGitHub Actionsのcronに移すと、アプリ側の間隔判定と二重になり
         実質8時間間隔になりうる

  対象箇所: §1-4 再設計案（バッチ層）／ §1-5

  現状の実装（`backend/scheduler.py` L184-187）:

      def check_and_run_batch() -> None:
          last_fetched_at = crud.get_setting("last_fetched_at")
          if last_fetched_at == "" or _elapsed_hours(last_fetched_at) >= BATCH_INTERVAL_HOURS:
              run_batch()

  `BATCH_INTERVAL_HOURS = 4`（`config.py` L16）であり、
  APScheduler は10分ごとに `check_and_run_batch()` をポーリングして
  「前回取得から4時間経過していれば実行する」という**ゲート方式**をとっている。
  10分ポーリング＋4時間ゲートの組み合わせでは、この設計は正しく機能する。

  問題:
    再設計案は**バッチをGitHub Actionsの4時間ごとcronに移す**としている。
    このとき、cron の起動間隔（4時間）とアプリ側のゲート（4時間）が
    **同じ値で二重にかかる**。

    `run_batch()` は先頭で `now_str` を取り、末尾（⑩）で
    `last_fetched_at` に**バッチ開始時刻**を書き込む。
    GitHub Actions のジョブはキュー待ちやランナー起動で
    **数分の遅延が常態的に発生する**（§1-5 リスク3 でも「高負荷時に遅延する」と
    認識されている）。

      cron 00:00 → 実際の開始 00:03 → last_fetched_at = 00:03
      cron 04:00 → 実際の開始 04:01 → 経過 3.97h < 4h → **スキップ**
      cron 08:00 → 実際の開始 08:02 → 経過 7.98h ≥ 4h → 実行

    つまり**1回おきにスキップされ、実効的な取得間隔が8時間になる**。
    しかも `run_batch()` が呼ばれないだけなので**エラーも警告も出ない**。
    GitHub Actions のジョブは「成功」で終わり、記事だけが更新されない。

    同じことが `check_and_run_game_schedule_batch()`（L246-249）にも当てはまる。

    これは §1-5 のリスク表にも挙がっていない。リスク3（cronの遅延）は
    「4時間間隔のため数十分の遅延は許容範囲」としているが、
    **遅延そのものではなく、遅延とゲートの相互作用**が問題である。

  推奨対応:
    ・再設計案では、GitHub Actions から呼ぶエントリポイントを
      **`check_and_run_batch()` ではなく `run_batch()` にする**（ゲートを外す）。
      スケジューリングの責務をcron側に一本化すれば二重判定は消える。
      §1-4 の表の「バッチ」行に、この設計上の前提を1行添える。
    ・ゲートを残す場合は `BATCH_INTERVAL_HOURS` を**cron間隔より短く**する
      （例：3.5時間）か、比較にマージンを設ける。
    ・`/api/fetch`（手動起動）は現状 `run_batch` を直接呼んでおり
      （`routes.py` L104-110）、ゲートを通らない。
      GitHub Actions からの呼び出しもこれに揃えるのが一貫する。
    ・手順3（基本設計）の差分設計（§5 #5）に本論点を含める。

  重要度の根拠:
    実害は「記事の更新頻度が半減し、かつ気付けない」という形で出る。
    要件定義書 §4-1 の指標2（直近N日の取得件数）・指標4（最終取得日時）を
    観測していれば検知できるが、それらの実装は手順7である。
    設計段階で潰しておく方が確実に安い。


[YEL-02] §3-5（401判定）と §3-3（スピンダウンで単純な死活監視が意味を失う）が
         整合していない

  対象箇所: §3-3 ／ §3-5

  §3-3 は再設計案の影響として次を挙げている。

      | Webサービスがスピンダウンする | 「応答がない＝障害」ではなくなる。
                                        **単純な死活監視が意味を失う** |

  一方 §3-5 は認証必須エンドポイントの監視方式として
  **401判定**（認証情報なしでアクセスし401が返れば生存）を採用した。
  判断自体は妥当で、根拠3点も適切である。

  問題:
    401判定は §3-3 が「意味を失う」と述べた**単純な死活監視そのもの**である。
    再設計案（Render無料プラン）を採用すると、次のいずれかになる。

    (1) 監視間隔を空ける場合（例：30分〜1時間ごと）
        15分の無アクセスでスピンダウンしているため、**毎回コールドスタート**に
        なる。§1-2・§1-4-1 が述べる通り復帰に**約1分**かかるため、
        監視ツール側のタイムアウト（一般的な外形監視は30秒前後）に
        引っかかり、**正常なのに障害と判定される**可能性が高い。

    (2) 監視間隔を詰める場合（例：5分ごと）
        スピンダウンしなくなる。UX上は起動待ちが消えて好都合だが、
        **常時起動＝月720時間**を消費する。
        Render 無料枠は **750インスタンス時間/月・ワークスペース単位**であり
        （§1-2 に v0.2 で追記済み）、1サービスで枠の96%を使い切る。
        余裕がほぼなく、無料 Web サービスを他に1つも置けなくなる。
        また「スピンダウンを許容する代わりに無料」という
        §1-4-1 の前提そのものが崩れる。

    §3-5 の「限界」表は
      検知できるもの：サーバープロセスが応答すること／ネットワーク経路
      検知できないもの：DB接続の可否／バッチが動いているか
    としており、**スピンダウンの影響が挙がっていない**。

  推奨対応:
    ・§3-5 の限界表に「**スピンダウン環境では機能しにくい**」を追加し、
      §3-3 との関係を明示する。
    ・監視方式を**現行構成と再設計案とで分けて記述する**。
        現行（Starter・常時起動）：401判定が有効
        再設計案（無料・スピンダウン）：
          401判定は補助。主たる監視対象は「**バッチが4時間ごとに走っているか**」
          （§3-3 が既に指摘している通り）であり、
          これは GitHub Actions のワークフロー実行結果と、
          要件定義書 §4-1 の指標2・4（直近N日の取得件数・最終取得日時）で
          判定できる。**Webサービスの死活は二次的な指標に降格する。**
    ・タイムアウト値を長め（例：90秒以上）に設定できる監視手段を選ぶ、という
      制約条件を §3-2 の比較軸に加える。

  補足:
    本件は「§3-5 の判断が誤っている」という指摘ではない。
    401判定は現行構成では正しく、監視用トークンを増やさない判断も妥当である。
    問題は、**§3-3 で認識した前提の変化が §3-5 に反映されていない**ことにある。
    両節はいずれも v0.2 で書かれた／触れられた箇所であり、
    §3-5 を新設した際に §3-3 との突き合わせが行われなかったものと見られる。

[GRN-01] 移行に要する変更に、Postgresドライバの追加と `DATABASE_URL` の意味変更が
         含まれていない

  §1-4-2 は SQLite依存箇所を4項目で確認し、
  「`create_engine()` 1行のみ（その1行の中で2箇所の変更）」と結論している。
  v0.2 で `connect_args` の除去が補足された点は改善だが、
  移行に必要な変更は他にも2つある。

  (1) **Postgresドライバが `requirements.txt` に存在しない**
      現在の依存は sqlalchemy のみで、`psycopg2-binary` / `psycopg` は入っていない。
      Postgres接続には別途ドライバの追加が必要である。

  (2) **`DATABASE_URL` の意味が変わる**
      `db/models.py` L82-83:
          DB_PATH = os.getenv("DATABASE_URL", "nba_news.db")
          engine  = create_engine(f"sqlite:///{DB_PATH}", ...)
      現在 `DATABASE_URL` は**ファイルパス**として使われており、
      f-string で `sqlite:///` を前置している。
      Postgres では `DATABASE_URL` は**接続URL全体**になるため、
      前置をやめて環境変数をそのまま渡す形に変える必要がある。

      あわせて `render.yaml` の `DATABASE_URL=/data/nba_news.db` も
      接続URLに書き換えることになる。
      Neon の接続文字列は秘匿情報のため `sync: false` 扱いにする必要もある。

  いずれも小さな作業であり「移行コストは低い」という結論は変わらない。
  ただし §1-4-2 は移行判断の中核であり、**変更の全量が見えている方が
  手順6での判断材料として正確**である。

  → §1-4-2 の表に2行追加する。
    「`requirements.txt`：Postgresドライバの追加が必要」
    「`DATABASE_URL` の意味：ファイルパス → 接続URL。`render.yaml` も要変更」


[GRN-02] 再設計案における `/api/fetch`（手動バッチ起動）の扱いが未定義

  §1-4 の表は API 層を「**Render 無料 Web Service（FastAPIのみ・スケジューラなし）**」
  としている。スケジューラを外す方針は明確だが、
  `POST /api/fetch`（`routes.py` L104-110）の扱いが書かれていない。

  同エンドポイントは `BackgroundTasks` で `run_batch` を起動する手動トリガであり、
  スケジューラとは独立して残る。再設計案では次の論点が生じる。

    ・無料インスタンス上で Claude API 呼び出しを含むバッチが走る
      （メモリ・実行時間の制約、処理中のスピンダウン挙動）
    ・GitHub Actions のバッチと**同時に走りうる**
      （`link` に unique 制約があるため重複挿入は防がれるが、
        `save_article` の例外は個別にログされるだけで、
        二重実行そのものは検知されない）
    ・そもそも GitHub Actions 側に手動実行（`workflow_dispatch`）があるなら、
      `/api/fetch` は不要になる可能性がある

  → §1-4 に1行添えるか、§5 の手順3引き継ぎ（#5 差分設計）に
    「`/api/fetch` を残すか、GitHub Actions の `workflow_dispatch` に
    一本化するか」を明記する。


[GRN-03] 60日自動無効化の検知手段が、既存の運用指標と接続されていない

  §1-5 リスク2 は「GitHub Actionsのスケジュールが60日のリポジトリ無活動で
  自動無効化」を**影響度「高」**とし、対処方針を
  「自動無効化の検知手段が必要（監視項目に追加）」としている。
  §3-3 も「GitHub Actions の60日自動無効化を検知する必要がある」と述べている。

  しかし、その検知手段が既に定義済みであることに触れていない。
  要件定義書 §4-1 の運用指標には
    指標2「直近N日の取得件数」
    指標4「最終取得日時（`last_fetched_at`）」
  があり、**バッチが止まればこの2つが動かなくなる**ため、
  自動無効化はこれらで検知できる。

  影響度「高」のリスクに対して「検知手段が必要」で止まっているより、
  「**既存の運用指標2・4で検知できる。閾値（例：最終取得から12時間以上）は
  改修要件5bで定義する**」まで書ける方が、リスクの残存度が下がる。

  → §1-5 リスク2 の対処方針を上記の形に具体化する。
    あわせて GitHub からの workflow 無効化通知メールも補助手段として挙げられる。


[GRN-04] §1-5 のリスク番号「6b」が変則採番になっている

  v0.2 で追加された「Neonの100 CU-hours/月の超過」が、

  以後リスクを追加するたびに 6c・4b といった枝番が増え、

  同種の問題は本プロジェクトで繰り返し発生している。

  1. §0-1（調査項目の消化状況）の実装精度
     前回レビューの結論部で提案した対応表が、A〜Dごとの表として実装された。

     未消化を隠さず可視化する構えは、要件定義書 §9 の自己チェックと同じ発想である。

  2. 事実誤りの訂正と、訂正の意味づけ
     Cloudflare Workers の却下理由については、誤りを認めた上で
     正しい理由（Python/FastAPI の移植コストが桁違い）に差し替え、
     さらに「調査書は判断の根拠を残す文書である」という位置づけを明記した。
     Neon についても「停止なし」を Supabase との差分に限定し、
     100 CU-hours の上限を §1-5 リスク6b として明示的にリスク化している。
     **訂正が「直した」で終わらず、文書の性格の再確認になっている。**

  3. §1-4-4 の判断プロセス
     非移行の採用にあたり、フェーズ2 7-J-4 の3つの理由を
     「理由／本件への当てはまり」で1件ずつ照合している。
     前例を「同じ結論だから同じ」で流用せず、根拠レベルで確認する手続きになっている。
     さらに「移行スクリプトの作成・検証コストに対して、得られるのは
     最大30日で消えるデータである。割に合わない」という一文で
     判断の要点を圧縮している。

  4. 中止基準との区別を自ら発見し、関連文書に反映した
     「計画的な非移行による0件状態」と「意図しないデータ消失」の区別は、
     指摘（YEL-01）が求めた範囲を超えて、要件定義書 §3-3-2 項目5 への

     §5 #9 に「✅実施済み」と記録されており、依頼と実施が対応している。

  5. §1-4-2 テストDBの相互作用の指摘
     案A（PostgresでCI実行）について「**再設計案でGitHub Actionsを導入するなら
     追加コストは小さい**」という相互作用を見つけている。
     移行を採用する場合、テスト環境の一致という副次的な利益が
     ほぼ無料で得られるという指摘であり、手順6の判断材料としても効く。

  6. §3-5 の限界表
     401判定を採用した上で「検知できるもの／検知できないもの」を

       DB接続・バッチ稼働という2つの限界は正しく捉えられている。）

     検出できなかった項目の振り返り）を、調査書にも適用している。
     文書種別を跨いで運用が統一されつつある。
