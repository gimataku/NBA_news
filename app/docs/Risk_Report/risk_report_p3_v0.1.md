## 1. A. 無料ホスティング環境の調査（要望1）

### 1-1. 前提調査：現行DB規模の推定

**Takumi様の判断（2026-08-24）により、実測ではなく推定値で進める。**

| 項目 | 推定値 | 算出根拠 |
|---|---|---|
| 保持記事数 | **約215件** | 30日保持（`DATA_RETENTION_DAYS=30`）× 週50件（トライアル運用実績） |
| 1記事あたりのサイズ | **約5KB** | `summary_ja` 800〜1200字 × UTF-8日本語3バイト ≒ 3.6KB ＋ タイトル・メタ情報 |
| **articles テーブル** | **約1MB** | 215件 × 5KB |
| game_schedule・その他 | 数百KB | 30日保持・1日十数試合 |
| **DB全体** | **約1〜2MB** | — |

> **推定で足りると判断した理由**: 無料DBの容量枠は Neon 0.5GB・Supabase 500MB であり、**推定値の250〜500倍**の余裕がある。多少の推定誤差では判断が変わらない。実測は「容量が判断を分ける場合」にのみ必要だが、本件は該当しない。
>
> **判断が変わる条件**: 記事数が現在の**250倍以上**（週12,500件）になった場合。現実的でない。

### 1-2. Render 無料プランの制約

| # | 制約 | 本アプリへの影響 |
|---|---|---|
| 1 | **Persistent Disk が利用不可**（有料機能・$0.25/GB月） | **SQLiteの永続化ができない**。再起動のたびにデータ消失 |
| 2 | **15分間の無アクセスでスピンダウン**。再開に約1分 | **APScheduler常駐バッチが停止する**。記事が更新されなくなる |
| 3 | Background Worker は有料 | バッチを別プロセスに逃がせない |
| 4 | Static Site は**無料**（100GB帯域/月・500ビルド分/月） | フロントエンドは現状のまま無料で継続可能 |

> **制約1・2により、現構成（FastAPI＋APScheduler＋SQLite on Persistent Disk）のままの無料化は不可能。**

### 1-3. 代替ホスティングの調査

| 候補 | 2026年8月時点の状況 | 採否 |
|---|---|---|
| **Fly.io** | **2026年に無料枠が廃止**。新規は2VM時間または7日間の試用のみ。Volumeは停止中も課金 | ❌不可 |
| **Vercel Hobby** | 実行10秒タイムアウト。**非商用限定** | ❌不可（Claude API呼び出しが10秒に収まらない） |
| **Cloudflare Workers** | 10万req/日・**CPU 10ms/呼び出し**・Cron Trigger 5本まで（無料） | ❌不可（Claude API応答待ちが10msに収まらない） |
| **GitHub Actions** | Private 2,000分/月・**Public無制限**。Cron最短5分間隔 | ✅**バッチの実行先として有力** |
| **Neon**（Postgres） | 無料枠 0.5GB/プロジェクト・**scale-to-zero（プロジェクト停止なし）** | ✅**DBとして有力** |
| **Supabase**（Postgres） | 無料枠 500MB・**7日間リクエストがないとプロジェクト自動停止** | △（自動停止が運用リスク） |

### 1-4. 再設計案：構成の分離

**発想の転換**：現構成が無料化できない原因は「**1つのWebサービスに常駐バッチとAPIを同居させている**」ことにある。バッチを外に出せば、スピンダウンは許容できる。

| 層 | 現行（$7.25/月） | 再設計案（**$0/月**） |
|---|---|---|
| フロントエンド | Render Static Site（無料） | **同左**（変更なし） |
| **バッチ**（RSS取得・翻訳・スコア取得） | Render Web Service内のAPScheduler | **GitHub Actions**（4時間ごとのcron） |
| **API**（`/api/news` 等） | 同上のFastAPI | **Render 無料 Web Service**（FastAPIのみ・スケジューラなし） |
| **DB** | SQLite on Persistent Disk | **Neon**（Postgres 無料枠） |

#### 1-4-1. スピンダウンが許容できる理由

**バッチをGitHub Actionsに移すと、Webサービスのスピンダウンは「データの鮮度」に影響しなくなる。** 影響するのは初回アクセス時の応答時間（約1分の起動待ち）のみである。

| 観点 | 影響 |
|---|---|
| データ鮮度 | **影響なし**。GitHub ActionsがWebサービスの状態と無関係に4時間ごとに更新する |
| 初回アクセス | **約1分の起動待ち**。個人利用（1日数回のアクセス）では許容範囲だが、UXは明確に劣化する |
| 2回目以降 | 15分以内の再アクセスなら待ちなし |

#### 1-4-2. 移行コストの評価：**SQLite → Postgres は低コスト**

コードを確認した結果、**移行の技術的障壁は小さい**。

| 確認項目 | 結果 |
|---|---|
| `db/crud.py` の生SQL（`execute()`） | **0件**。全てSQLAlchemy ORMで記述されている |
| SQLite依存箇所 | **`db/models.py` L83 の `create_engine()` 1行のみ**（`sqlite:///` → `postgresql://`） |
| `db/migrate_p2.py` の `sqlite3` 直接使用 | 一度限りの移行スクリプトであり**ランタイム対象外** |

> **ORMで統一されていたことが、そのまま移行可能性として効いている。** フェーズ2の基本設計でSQLAlchemyを採用した判断が、想定していなかった形で価値を持った。

#### 1-4-3. JWT認証の維持可否（**移行の絶対的ブロッカー**）

| 確認項目 | 判定 |
|---|---|
| Render 無料 Web Service でFastAPIのJWT認証が動作するか | ✅**動作する**（アプリケーション層の実装であり、プランに依存しない） |
| 環境変数（`SECRET_KEY`・`USERNAME`・`USER_PASSWORD`）の設定 | ✅可能 |
| **結論** | ✅**認証は維持できる。移行のブロッカーには該当しない** |

> 計画書§7は「無料化により認証が維持できない場合、**移行の絶対的ブロッカー**として扱う」と定めていた。本調査により**該当しないことを確認**した。

### 1-5. 再設計案のリスク

| # | リスク | 影響度 | 対処方針 |
|---|---|---|---|
| 1 | **初回アクセス時の約1分の起動待ち** | 中 | UXの明確な劣化。**$7.25/月を払う価値があるかの判断**に直結する。手順6で最終判断 |
| 2 | **GitHub Actionsのスケジュールが60日のリポジトリ無活動で自動無効化** | **高** | 個人開発では60日コミットがない期間が現実的に起こりうる。**自動無効化の検知手段**が必要（監視項目に追加） |
| 3 | GitHub Actionsのcronは高負荷時に遅延する | 低 | 4時間間隔のため数十分の遅延は許容範囲 |
| 4 | Private リポジトリの2,000分/月の上限 | 低 | 推定使用量：6回/日×30日×約3分＝**約540分/月**。上限の27%。ただし記事数増で変動 |
| 5 | シークレットの管理先が分散する（Render環境変数＋GitHub Secrets） | 中 | 設定漏れが「起動するが更新されない」故障になる。セキュリティ先行対応（先-1）と同種のリスク |
| 6 | Neonのscale-to-zeroからの復帰遅延 | 低 | バッチ・API双方で数秒の初回接続遅延。許容範囲 |
| 7 | **移行時のデータ消失** | 中 | 中止基準（要件定義書§3-3-2 項目5）に該当。**ステータスAPI拡張を移行より先に実装**する制約を計画書 手順7 に設定済み |

### 2-2. F-15（関連ニュース）の算出方式

#### 2-2-1. 方式の比較

| 案 | 追加依存 | 追加コスト | 計算量 | 判定 |
|---|---|---|---|---|
| **(a) Levenshtein流用** | **なし**（`python-Levenshtein` は既に `requirements.txt` に存在） | **$0** | 1記事の展開ごとに最大49回の比較 | ✅**採用推奨** |
| (b) TF-IDF | scikit-learn 等（数十MB） | $0 | 同程度 | △（依存が重い） |
| (c) Claude API | なし | **記事数に比例して増加** | — | ❌**不採用** |

#### 2-2-2. 判定基準の適用（計画書§1-1 優先順位）

> 判定は「単体のコスト比較」ではなく「**移行後の無料枠の中で成立するか**」で行う（計画書 手順2-B）。
>
> - **案(a)**：追加コスト$0。無料枠に影響しない → ✅成立
> - **案(c)**：Claude APIの呼び出しが増える。無料化を目指す本フェーズの方針（目的2）と**正面から競合する**。優先順位（安全性＞可観測性＞**コスト**＞**機能**）に従い、機能側を削る → ❌不採用

#### 2-2-3. 案(a)の実装上の見通し

| 項目 | 内容 |
|---|---|
| 流用元 | `processor/dedup.py` の `Levenshtein.ratio()` |
| 既存の使い方 | 重複判定に**閾値0.80**（`DEDUP_THRESHOLD`）を使用 |
| F-15での使い方 | **より低い閾値**（0.30〜0.50程度）で「類似」を判定。閾値は手順3で決定 |
| 比較対象 | `title_original`（英語）または `title_ja`。**手順3で決定**（dedupは英語で比較しコスト削減と整合性を確保している） |
| 計算量 | 表示リスト最大50件 → 1記事あたり最大49回の文字列比較。**リクエスト時算出で成立する** |

> **要件定義書§2-3-3 の関連基準との対応**: 基準2（タイトルの語句一致）に案(a)が対応する。基準1（同一カテゴリ）はallタブでのみ識別力を持ち、基準3（取得時期の近接）は `fetched_at` の差分で計算できる。**3基準の重み付けは手順3で設計する。**

## 3. C. 監視方式の調査（要望5）

### 3-1. Claudeスケジュールタスクからの到達可能性（実証結果）

| 対象 | 結果 |
|---|---|
| フロントエンド（Static Site） | ✅**到達可能**（2026-08-23の実行で200応答を確認） |
| バックエンド `/api/status` | ❌**到達不可**。Claudeサンドボックスのネットワーク制限による**構造的な制約**であり、権限や設定では解消しない |

> **ブラウザからは401（`{"detail":"Not authenticated"}`）が返り、サービス自体は正常稼働していることを確認済み**（2026-08-23）。到達不可はClaude側の制約であってアプリの問題ではない。

### 3-2. 方式の比較

| 方式 | 到達性 | コスト | 備考 |
|---|---|---|---|
| **Claudeスケジュールタスク**（現行） | フロントのみ | 無料 | バックエンドを監視できない。**毎回⚠️が記録されアラート疲れを生む** |
| **Render標準のHealth Check通知** | ✅ | 無料 | **先行対応（先-2）で9月までに暫定導入予定**。ただし無料プランで利用可能かは要確認 |
| **外部監視サービス**（UptimeRobot等） | ✅ | 無料枠あり | 5分間隔・50モニタ程度が一般的。**スピンダウン防止のping**を兼ねられる |
| **GitHub Actionsからの監視** | ✅ | 無料 | 再設計案でバッチをGitHub Actionsに移すなら、**同じワークフロー内で死活確認できる** |

### 3-3. 再設計案との相互作用（**重要**）

> **再設計案を採用する場合、監視の設計が変わる。**
>
> | 論点 | 影響 |
> |---|---|
> | Webサービスがスピンダウンする | 「応答がない＝障害」ではなくなる。**単純な死活監視が意味を失う** |
> | 監視対象が増える | Render Web Service・GitHub Actionsワークフロー・Neon の3系統 |
> | **最も重要な監視対象が変わる** | 「サーバーが生きているか」ではなく「**バッチが4時間ごとに走っているか**」。GitHub Actionsの**60日自動無効化**（§1-5 リスク2）を検知する必要がある |
>
> **よって監視方式（改修要件5b）の確定は、要望1の採否確定後とする。** 計画書が5a（項目）と5bを分割した判断が、ここで効いている。

### 3-4. 暫定措置（先-2）との関係

先行対応（先-2）でRender標準のHealth Check通知を9月までに有効化する予定だが、**再設計案を採用する場合は方式ごと見直す**ことになる。計画書 手順2-C の注記「**先行対応で暫定導入済み。本項目ではこれを含めて比較し、継続／置換を判断する**」の通り、暫定措置が本設計を拘束しないようにする。

## 4. D. セキュリティの調査（要望6）

### 4-1. YEL-02（レートリミット欠如）の再評価

**評価軸を「技術的な脆弱性」から「法的前提を崩すリスク」に変更して再評価する。**

| 観点 | 評価 |
|---|---|
| 技術的な観点 | 個人利用アプリであり、攻撃者にとっての価値は低い。単体では優先度は高くない |
| **法的な観点** | 本アプリの公開は**著作権法第30条（私的使用のための複製）**の範囲に依拠している。**JWT認証はその範囲を担保する唯一の手段**である |
| **認証が破られた場合** | 「限られた範囲での利用」という前提が崩れ、**著作権法上の私的利用の範囲を逸脱する**。これは技術的な問題ではなく**法的な問題**である |
| **判定** | 🔴 **対応必須**。要件定義書 F-17 の優先度「高」は妥当 |

> **要件定義書§3-3-1 項目2（認証迂回）は中止基準である。** 認証が破られれば合否・撤退の両方に同時に該当する（§3-3-1-1 の注記）。**予防措置としてのレートリミットは、中止基準に触れる確率を下げる投資**にあたる。

#### 4-1-1. 実装方式の見通し

| 方式 | 備考 |
|---|---|
| アプリケーション層でのレートリミット | `slowapi` 等のライブラリ。**依存が1つ増える**。無料プランでも動作する |
| リバースプロキシ層 | Renderの無料プランでは設定不可 |
| **推奨** | アプリケーション層。**再設計案を採用しても方式は変わらない** |

> 具体的な閾値（例：5回/分・失敗5回で15分ロック）は**手順3で設計する**。

### 4-2. 無料環境移行時のセキュリティ水準

| # | 観点 | 評価 |
|---|---|---|
| 1 | JWT認証の維持 | ✅維持できる（§1-4-3） |
| 2 | HTTPS | ✅Render無料プランでもSSLは提供される |
| 3 | **シークレットの管理先が分散** | ⚠️ Render環境変数＋GitHub Secrets＋Neon接続文字列の3箇所。**設定漏れのリスクが増える**（§1-5 リスク5） |
| 4 | **DB接続経路が外部化** | ⚠️ SQLite（ローカルファイル）→ Neon（ネットワーク越し）。**接続文字列の漏洩が新たな攻撃面**になる |
| 5 | GitHub Actionsからのアクセス | ⚠️ バッチがDBに直接書き込む。**GitHub Secretsの管理が重要**になる |
| **総合判定** | | **水準は低下しないが、管理対象が増える**。計画書§2ガイドライン「無料化は安全性を犠牲にしないことを絶対条件とする」には抵触しないが、**運用の複雑さは増す** |

## 6. 本調査で得られた教訓

### 6-1. 「測る手段」の前に「何を測れば判断できるか」を確認する

計画書 手順2-A は「**Persistent Disk の実使用量**」を無料化可否の判断材料と位置づけ、その実測手段の確保を最優先項目とした。しかし実際には、**Render無料プランに Persistent Disk が存在しない**ため、容量は判断材料になり得なかった。

| 段階 | 内容 |
|---|---|
| v0.5レビューYEL-01 | 「実測手段が確保されていない」と指摘 → 手順2-Aに「実測手段の確保」を新設 |
| v0.6レビューGRN-02 | 「案(b)は4項目中1項目しか満たせない」と指摘 → 選定順序を明記 |
| **本調査** | **そもそも測る対象の見立てが違っていた** |

> **教訓**: 「観測できるかを先に検証する」（振り返り3-9）の一段手前に、「**何を知れば判断できるかを先に確認する**」工程が要る。手段の議論は、対象が正しいことを前提にしている。
>
> 本件では**低コストな調査（無料プランの仕様確認）を先に行えば、実測手段の議論そのものが不要だった**。

### 6-2. 過去の設計判断が想定外の形で効くことがある

フェーズ2で SQLAlchemy ORM を採用した判断により、`db/crud.py` に生SQLが1件も存在しない。結果として **SQLite → Postgres の移行が `create_engine()` 1行の変更**で済む見通しとなった。

> 当時この判断は「移行可能性」を目的にしたものではなかったが、**選択肢を狭めない設計**が後のフェーズで価値を持った例として記録する。
