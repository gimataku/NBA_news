[YEL-01] 計画書 手順2-A の調査項目「移行に伴うデータ移行の要否・手順」が未着手

  対象箇所: §1-4-2 ／ §1-5 リスク7 ／ §5

  現状:
    §1-4-2 は「移行コストの評価：**SQLite → Postgres は低コスト**」として
    **コード変更のコスト**を評価している。内容は正確である（実ファイルで検証済み）。

    しかし計画書 手順2-A が挙げている調査項目は
      「**移行に伴うデータ移行の要否・手順**」
    であり、これは**既存の記事データ（約215件）をSQLiteからNeonへ移すかどうか**、
    移すならどう移すかという論点である。本書はこれを扱っていない。

  問題:
    (1) 判断が必要な論点である
        フェーズ2では 7-J-4（DBデータ移行）を**運用判断により見送った**前例がある。
        見送りの理由は「本番が既に自走中であること」「`delete_old_articles()` の
        30日保持ポリシーにより移行データの大半が早期失効すること」だった。
        フェーズ3の移行にも**同じ論法がそのまま当てはまる**（30日で入れ替わる）。
        「移行しない（新規スタート）」が有力だが、その判断が記録されていない。

    (2) 移行しない場合、記事が一時的に消える
        新規スタートを選ぶと、移行直後は記事0件から始まり、
        4時間ごとのバッチで徐々に埋まる。数日間はコンテンツが薄い状態になる。
        これは要件定義書 §3-3-2 項目5（データ消失＝中止基準）と
        **見分けがつかない事象**である。§1-5 リスク7 は「移行時のデータ消失」を
        中止基準該当としているが、**意図的な非移行と障害による消失の区別**が
        書かれていない。

    (3) §5 の引き継ぎにも入っていない
        §5 は8件を挙げているが、データ移行の要否はどこにもない。
        計画書の調査項目が1件消化されないまま手順3へ進むことになる。

  推奨対応:
    ・§1-4 に「1-4-4. データ移行の要否」を新設し、次を判断・記録する。
        - 移行する／しない（フェーズ2 7-J-4 の判断と同じ論法が使えるか）
        - しない場合、移行直後の記事0件状態をどう扱うか
          （移行前にバッチを1回走らせて即座に埋める等）
        - 中止基準（データ消失）との区別を明記する
          「**計画的な非移行による0件状態は中止基準に該当しない**。
            該当するのは移行後に蓄積したデータが意図せず失われた場合」
    ・要件定義書 §3-3-2 項目5 にも同じ区別を反映する

  対象箇所: §1-4 ／ §5 ／ 要件定義書 §3-1 項目6・§3-3-1 項目1

  現状:
    要件定義書の品質基準は、コストについて次のように定めている。
      §3-1 項目6（合否）    月次コストが**試算の150%以内**
      §3-3-1 項目1（中止）  月次コストが**試算の200%**を超えた場合

    ここでいう「試算」はフェーズ2の **$10.65/月**（Render $7.25 ＋ Claude API $3.40）
    である。

  問題:
    本書 §1-4 が示す再設計案は**ホスティング費用を$0**にする。
    その場合、
      ・「試算」の値そのものが変わる（$10.65 は Render 前提の数値）
      ・ホスティングが$0になると、150%・200%という**倍率の基準が
        意味を持たなくなる**（$0 に対する倍率は定義できない）

    要件定義書 §3-3-1-1 は「合否ラインと中止ラインの関係」を表で管理しており、
    コスト行は「150%以内 / 200%超 / 帯域150〜200% / ✅幅あり」となっている。
    無料化を採用すれば**この行が成立しなくなる**。

  推奨対応:
    ・§1-4 に「**再設計案採用時のコスト基準への影響**」を追記する。
        - 新しい試算値：Claude API のみ（月 $1.3〜$1.7 が実績範囲）
        - 合否・中止の基準を金額で置く案（例：合否 $3以内・中止 $7超）と

    ・§5 の引き継ぎに「**要件定義書 §3-1 項目6・§3-3-1 項目1 の再定義**
      （手順6で要望1の採否確定後）」を追加する。
    ・要件定義書側にも §3-3-4「関連文書の修正」の様式で依頼できる。

    フェーズ2振り返り 2-4 は「撤退ラインを数値で先に決めていたため判定が
    主観に依存しなかった」を良かった点として挙げ、要件定義書 §3-3 はそれを
    継承するために新設された。無料化によってその数値が空洞化する可能性は、
    採否判断（手順6）と同時に扱わなければならない。


[YEL-04] §1-3 代替候補の比較表に、事実の誤りと重要な欠落がある

  対象箇所: §1-3

  外部情報を2026年8月時点で確認したところ、3件の問題があった。

  (1) **Cloudflare Workers の却下理由が誤っている**

      本書の記載
        「10万req/日・**CPU 10ms/呼び出し**・Cron Trigger 5本まで（無料）
          → ❌不可（**Claude API応答待ちが10msに収まらない**）」

      Cloudflare Workers の CPU time は**実行時間（wall time）ではなく
      CPU が実際に処理に費やした時間**であり、
      **`fetch()` の応答待ちなどのI/O待機は CPU time に計上されない**。
      5秒の fetch を待っても、その待機中の CPU 消費はゼロである。

      したがって「Claude API応答待ちが10msに収まらない」という理由は成立しない。
      結論（❌不可）自体は妥当な可能性が高いが、
      **正しい理由は別にある**（本アプリは Python/FastAPI であり、
      Workers の実行環境で FastAPI をそのまま動かすのは現実的でない、
      サブリクエスト数の制限、等）。

      **調査書は判断の根拠を残す文書**である。
      理由が誤ったまま候補を消すと、後日「本当に不可だったのか」を
      再検証する際に誤った前提を引き継ぐ。

  (2) **Neon の記述が不正確・不完全**

      本書の記載
        「無料枠 0.5GB/プロジェクト・**scale-to-zero（プロジェクト停止なし）**」

      0.5GB と scale-to-zero は正しい（computes は5分の無活動で
      scale to zero し、無料プランでは無効化できない）。

      しかし無料プランには **100 CU-hours/月のコンピュート上限**があり、
      **使い切ると次の請求期間まで compute が suspend される**。
      「プロジェクト停止なし」と断定するのは正確でない。
      あわせて **5GB/月の公衆ネットワーク転送**の枠も表にない。

      本件の使い方（4時間ごとのバッチ＋1日数回のAPIアクセス）では
      100 CU-hours に収まる見込みが高いが、
      **Supabase の「7日で自動停止」と対比して Neon を選ぶ根拠**として
      「停止なし」を挙げている以上、上限の存在は書くべきである。

  (3) Fly.io の廃止時期が不正確

      本書は「**2026年に**無料枠が廃止」としているが、
      新規ユーザー向けの無料枠（Hobby/Launch/Scale の無料アロウワンス）は
      **2024年に廃止**されている。現在の状態
      （新規は2VM時間または7日間の試用のみ）の記述は正しい。

  推奨対応:
    ・(1) Cloudflare Workers の却下理由を、CPU time の誤解に基づかない
      正しい理由に書き換える。判定を維持する場合も理由の差し替えが必要。
    ・(2) Neon 行に「100 CU-hours/月・超過時は次期間まで compute 停止」
      「転送 5GB/月」を追記し、「プロジェクト停止なし」を
      「**7日無活動での自動停止はない**（Supabase との差分）」に限定する。
      あわせて §1-5 のリスク表に「CU-hours 超過による compute 停止」を
      低〜中の影響度で追加する。
    ・(3) 「2026年に廃止」→「2024年に新規向け無料枠が廃止。2026年8月時点で
      新規は試用のみ」に修正する。
    ・表に**確認日（2026-08-24）**を明記する。無料枠の条件は変動が速く、
      手順6（リスク正式評価）や手順7（実装）の時点で再確認が要る。

  §1-4 の表は「現行（**$7.25/月**）→ 再設計案（**$0/月**）」と対比しており、
  §0 サマリーも「再設計により**$0/月が成立する見込み**」としている。

  $7.25 は Render の固定費であり、フェーズ2の**月次総額は約$8.5〜$9.0**だった
  （Claude API 実績 $1.27〜$1.72 を含む。`document_baseline_p2.md` §2）。
  再設計案でも Claude API のコストは残るため、月次総額は $0 にはならない。

  表の中では「層」ごとの比較であることが読み取れるが、
  §0 サマリーの「$0/月が成立する」だけを見ると総額ゼロと読める。

  → 「**ホスティング費用 $0/月**（Claude API の $1.3〜$1.7/月 は別途残る）」と
    明記する。YEL-03（コスト基準の再定義）とも直結する。


[GRN-02] `create_engine()` の変更は URL スキームだけでは足りない

  §1-4-2 は「`db/models.py` L83 の `create_engine()` 1行のみ
  （`sqlite:///` → `postgresql://`）」としている。

  実際の L83 は
    `create_engine(f"sqlite:///{DB_PATH}", connect_args={"check_same_thread": False})`
  であり、`connect_args={"check_same_thread": False}` は
  **SQLite ドライバ専用の引数**である。Postgres では不要であり、
  そのまま渡すとエラーになる。

  「1行のみ」という結論は変わらないが、
  **その1行の中で URL 以外にも変更が要る**点は書いておく方が正確である。

  → 「`sqlite:///` → `postgresql://` に変更し、あわせて
    `connect_args={"check_same_thread": False}`（SQLite専用）を除去する」
    と補足する。

  なお `db/models.py` L3 は `event` を import しているが、
  ファイル内に `event.listens_for` の使用箇所はない（未使用の import）。
  移行とは無関係だが、`create_engine` 周辺を触る際に整理できる。


[GRN-03] Render Postgres が候補比較に挙がっていない

  §1-3 の候補表は Fly.io・Vercel・Cloudflare・GitHub Actions・Neon・Supabase を
  比較しているが、**Render 自身が提供する Postgres** が入っていない。

  フロントエンドと API を Render に残す構成である以上、
  同一プラットフォーム内で完結する選択肢は自然な比較対象である
  （設定箇所が増えない＝§4-2 で挙げた「シークレットの管理先が分散」という
  懸念を緩和できる）。

  Render の無料 Postgres は**期限付き**（一定期間後に削除される）という
  制約があり、結果として不採用になる可能性が高い。
  だとしても、**検討した上で外した**という記録があると、
  後から「なぜ同一プラットフォームで完結させなかったのか」を再検証できる。

  → §1-3 に Render Postgres の行を追加し、判定と理由を記録する。


[GRN-04] Render 無料 Web Service の 750 インスタンス時間/月に触れていない

  §1-2 は無料プランの制約を4件挙げているが、
  「**750 インスタンス時間/月（ワークスペース単位）**」がない。

  本件の構成では Web サービスがスピンダウンし、
  スピンダウン中は時間を消費しないため実質的な制約にならない見込みだが、
  §1-2 が「無料プランの制約」を列挙する節である以上、
  枠の存在自体は記載しておく方が網羅的である。

  → §1-2 に1行追加し、「本構成ではスピンダウンにより消費が抑えられるため
    実質的な制約にならない」と評価を添える。

■ 評価できる点
================================================================================

  1. §0-1・§6-1 の「前提が誤っていた」という自己申告
     計画書は v0.5レビューYEL-01・v0.6レビューGRN-02 の2版をかけて
     「Persistent Disk の実使用量を測る手段」を整備した。
     本調査はその前提自体が空振りだったことを最初に書き、
     §6-1 で「『観測できるかを先に検証する』の一段手前に、
     『**何を知れば判断できるかを先に確認する**』工程が要る」と教訓化している。

     さらに「**低コストな調査（無料プランの仕様確認）を先に行えば、
     実測手段の議論そのものが不要だった**」という指摘は、
     手順の順序に関する具体的な改善提案になっている。
     調査書がレビューを待たずに自らの前提を疑った点は、
     フェーズ2振り返りが積み上げてきた姿勢の到達点といえる。

  2. §1-4 の原因分析からの再設計
     「無料化できない原因は1つのWebサービスに常駐バッチとAPIを
     同居させていること」という分析から、バッチの外出しという解に至っている。
     制約（スピンダウン）を回避しようとするのではなく、
     **制約が問題にならない構成に変える**という発想の転換であり、
     §1-4-1 で「スピンダウンが許容できる理由」をデータ鮮度・初回アクセス・
     2回目以降に分けて評価している点も丁寧である。

  3. コード調査の正確さ
     §1-4-2 の3項目と §2-2-3 の記述を実ファイルで照合したところ、
     生SQL 0件・`create_engine` の位置・`python-Levenshtein` の既存・
     `DEDUP_THRESHOLD = 0.80` のいずれも正確だった。
     さらに本レビューで追加確認した `upsert_game_schedule` も
     select-then-update 方式で方言依存がなく、スキーマも Text/Integer のみで、
     **「移行コストは低い」という結論は追加の裏付けを得た**。

  4. §6-2 の「過去の設計判断が想定外の形で効く」
     SQLAlchemy ORM の採用が、当時意図していなかった「移行可能性」として
     価値を持ったという記録は、次フェーズの設計判断に効く。
     良かったことを記録する項目は振り返りで漏れやすいが、
     調査の時点で残している。

  5. §3-3 の「再設計案を採用すると監視の設計が変わる」
     「最も重要な監視対象が『サーバーが生きているか』ではなく
     『バッチが4時間ごとに走っているか』に変わる」という指摘は、
     計画書が改修要件5を 5a（項目）と 5b（方式）に分割した判断
     （RED-02対応）の妥当性を実証している。
     分割していなければ、手順1で決めた監視方式が丸ごと無駄になっていた。

  6. §4-1 の法的観点での再評価
     要件定義書 §3-3-1 項目2（認証迂回＝中止基準）と接続し、
     「**予防措置としてのレートリミットは、中止基準に触れる確率を下げる投資**」
     と位置づけている。技術的な優先度づけではなく、
     プロジェクトの前提（著作権法第30条）から導いている点が一貫している。

  7. §1-1 の推定への切替と「判断が変わる条件」の明示
     実測を推定に切り替えた判断について、
     「無料DBの容量枠は推定値の250〜500倍」「判断が変わるのは記事数が
     250倍になった場合」と、**推定で足りる根拠を定量的に示している**。
     フェーズ1レビュー提言10（数値・閾値の根拠）の観点を満たしている。

  8. 参照セクションが版番号なしで書かれている
     「要件定義書（フェーズ3）§8」「プロジェクト計画書（フェーズ3）手順2」
     という書き方は、要件定義書 v0.3 レビューの YEL-02
     （版番号付き相互参照は双方が古くなり続ける）で推奨した形になっている。

■ 結論
================================================================================

  🔴致命 0件。**手順3（基本設計）への着手可**と判定する。
  ただし要望1（無料化）の最終採否は手順6であり、
  その判断材料として🟡5件のうち3件を先に解消することを推奨する。

  推奨処理順:

    1. YEL-03（コスト基準の再定義）
       無料化の採否は品質基準の再定義を伴う。手順6で採否だけを決めて
       基準を放置すると、トライアル運用（手順10）で判定できなくなる。
       採否と基準の再定義はセットで扱う。

    2. YEL-01（データ移行の要否）
       手順3の設計に直結する。フェーズ2 7-J-4 の判断がそのまま使える見込みで、
       判断自体は短時間で済む。「非移行による0件状態」と
       「障害によるデータ消失」の区別は必ず記録すること。

    3. YEL-02（手順2-Cの未消化2件）
       監視方式は 5b として手順2完了後に定義するが、
       「401応答で生存判定する」という方式の目処は本書で立てられる。
       §3-1 に既に材料がある。

    4. YEL-04（候補比較表の是正）・YEL-05（テストDB）
       いずれも記録の精度に関わる。次版でまとめて処理できる。

  ── 総評 ──

  リスク調査書として、**判断に必要な材料が揃っている**。
  「現構成のままでは不可能」という結論で終わらせず、
  再設計案という選択肢を作り出して $0 の見込みまで示した点が本書の価値である。
  同時に、その選択肢が持つ代償（起動待ち1分・監視設計の変更・
  管理対象の増加）も並べて書かれており、手順6での判断に耐える。

  🟡5件のうち3件（YEL-01・YEL-02）は**計画書の調査項目に対する未消化**である。
  計画書 手順2 は A〜D の下に14項目を列挙しており、本書はそのうち11件を
  完了、1件を部分、2件を未着手としている。
  本書の冒頭に「計画書 手順2 調査項目との対応表」を置き、
  各項目の消化状況（✅／△／❌と理由）を示す形にすれば、
  未消化が可視化される。要件定義書 §9 の自己チェックと同じ発想である。

  なお §0-1 が示した「測る対象の見立てが違っていた」という発見は、
  次の振り返りに残すべき最重要の教訓である。
  計画書は「観測できるかを先に検証する」（振り返り3-9）を
  §8項目8・手順2-C に組み込んだが、本書はその**さらに一段手前**を指摘した。
  §6-1 の記述をそのまま `retrospective_p3` へ引き継げる形になっている。
