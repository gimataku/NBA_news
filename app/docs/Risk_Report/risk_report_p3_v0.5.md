## 1. A. 無料ホスティング環境の調査（要望1）

### 1-1. 前提調査：現行DB規模の推定

**Takumi様の判断（2026-08-24）により、実測ではなく推定値で進める。**

| 項目 | 推定値 | 算出根拠 |
|---|---|---|
| 保持記事数 | **約215件** | 30日保持（`DATA_RETENTION_DAYS=30`）× 週50件（トライアル運用実績） |
| 1記事あたりのサイズ | **約5KB** | `summary_ja` 800〜1200字 × UTF-8日本語3バイト ≒ 3.6KB ＋ タイトル・メタ情報 |
| **articles テーブル** | **約1MB** | 215件 × 5KB |
| game_schedule・その他 | 数百KB | 30日保持・1日十数試合 |
| **DB全体** | **約1〜2MB** | — |

> **推定で足りると判断した理由**: 無料DBの容量枠は Neon 0.5GB・Supabase 500MB であり、**推定値の250〜500倍**の余裕がある。多少の推定誤差では判断が変わらない。実測は「容量が判断を分ける場合」にのみ必要だが、本件は該当しない。
>
> **判断が変わる条件**: 記事数が現在の**250倍以上**（週12,500件）になった場合。現実的でない。
>
> **⚠️ 本推定はSQLiteファイルサイズを前提とする（v0.4追加・レビューGRN-03対応）**: Postgresでは①行あたりのヘッダオーバーヘッド、②インデックス（`models.py` で5本定義）の実体、③MVCCによる更新・削除済みタプル（`delete_old_articles()` が毎日走る）、④Neonのストレージは data に加え **history**（時点復元用）を含む、により**実サイズが数倍になりうる**。それでも 0.5GB に対しては**なお2桁の余裕がある**ため、§1-1の結論（推定で足りる）は変わらない。

### 1-2. Render 無料プランの制約

| # | 制約 | 本アプリへの影響 |
|---|---|---|
| 1 | **Persistent Disk が利用不可**（有料機能・$0.25/GB月） | **SQLiteの永続化ができない**。再起動のたびにデータ消失 |
| 2 | **15分間の無アクセスでスピンダウン**。再開に約1分 | **APScheduler常駐バッチが停止する**。記事が更新されなくなる |
| 3 | Background Worker は有料 | バッチを別プロセスに逃がせない |
| 4 | Static Site は**無料**（100GB帯域/月・500ビルド分/月） | フロントエンドは現状のまま無料で継続可能 |
| 5 | **750 インスタンス時間/月**（ワークスペース単位） 🆕 | **本構成では実質的な制約にならない**。スピンダウン中は時間を消費しないため、1日数回のアクセスなら月数時間程度に収まる |

> **制約1・2により、現構成（FastAPI＋APScheduler＋SQLite on Persistent Disk）のままの無料化は不可能。**

### 1-3. 代替ホスティングの調査

**確認日：2026-08-24**（無料枠の条件は変動が速いため、手順6・手順7の時点で**再確認が必要**）

| 候補 | 2026年8月時点の状況 | 採否・理由 |
|---|---|---|
| **Fly.io** | **2024年に新規向け無料枠（Hobby/Launch/Scale）が廃止**。2026年8月時点で新規は2VM時間または7日間の試用のみ。Volumeは停止中も課金 | ❌**不可**（無料枠が存在しない） |
| **Vercel Hobby** | 実行10秒タイムアウト。**非商用限定** | ❌**不可**（Claude API呼び出しを含むバッチが10秒に収まらない） |
| **Cloudflare Workers** | 10万req/日・CPU time 10ms/呼び出し・Cron Trigger 5本まで（無料） | ❌**不可**（理由は下記注記） |
| **GitHub Actions** | Private 2,000分/月・**Public無制限**。Cron最短5分間隔 | ✅**バッチの実行先として有力** |
| **Neon**（Postgres） | 無料枠 **0.5GB/プロジェクト**・**100 CU-hours/月**（超過時は次の請求期間まで compute 停止）・**転送 5GB/月**・computeは5分の無活動でscale-to-zero（無料プランでは無効化不可）。**7日無活動での自動停止はない** | ✅**DBとして有力** |

| **Render Postgres** 🆕 | 無料インスタンスは**期限付き**（一定期間後に削除される） | ❌**不可**（永続運用に使えない）。ただし**同一プラットフォームで完結する利点**があったため検討対象とした |

> **⚠️ Cloudflare Workers の却下理由の訂正（v0.2・レビューYEL-04対応）**
>
> v0.1は「Claude API応答待ちが10msに収まらない」を理由としていたが、**これは誤りである**。Cloudflare Workers の CPU time は**実行時間（wall time）ではなくCPUが実際に処理に費やした時間**であり、**`fetch()` の応答待ちなどのI/O待機は計上されない**。5秒のfetchを待っても待機中のCPU消費はゼロである。
>
> **正しい却下理由**: 本アプリは Python/FastAPI で構築されており、**Workers の実行環境でFastAPIをそのまま動かすのは現実的でない**。移植するには全面的な書き換えが必要で、移行コストが再設計案（`create_engine()` 1行）と比べて桁違いに大きい。
>
> **なぜ理由の訂正が重要か**: 調査書は**判断の根拠を残す文書**である。誤った理由のまま候補を消すと、後日「本当に不可だったのか」を再検証する際に誤った前提を引き継ぐ。

> **Neon の記述の訂正（v0.2・レビューYEL-04対応）**: v0.1は「scale-to-zero（**プロジェクト停止なし**）」と断定したが、**100 CU-hours/月の上限があり、超過すると次の請求期間まで compute が suspend される**。「停止なし」は**Supabaseの7日自動停止との差分**を指すものに限定する。本件の使い方（4時間ごとのバッチ＋1日数回のAPIアクセス）では100 CU-hoursに収まる見込みだが、上限の存在は§1-5のリスク8に追加した。

### 1-4. 再設計案：構成の分離

**発想の転換**：現構成が無料化できない原因は「**1つのWebサービスに常駐バッチとAPIを同居させている**」ことにある。バッチを外に出せば、スピンダウンは許容できる。

> **⚠️ 「$0/月」の範囲（v0.2で明示・レビューGRN-01対応）**: 本節の $0 は**ホスティング費用のみ**を指す。**Claude API のコストは残る**（フェーズ2実績 $1.27〜$1.72/月）。フェーズ2の月次総額は約$8.5〜$9.0 であり、再設計後の総額は**約$1.3〜$1.7/月**になる見込みである。

| 層 | 現行（ホスティング $7.25/月） | 再設計案（**ホスティング $0/月**） |
|---|---|---|
| フロントエンド | Render Static Site（無料） | **同左**（変更なし） |
| **バッチ**（RSS取得・翻訳・スコア取得） | Render Web Service内のAPScheduler | **GitHub Actions**（4時間ごとのcron）。**⚠️ エントリポイントは `run_batch()`（ゲートを外す）**。理由は§1-4-6 |
| **API**（`/api/news` 等） | 同上のFastAPI | **Render 無料 Web Service**（FastAPIのみ・スケジューラなし） |
| **DB** | SQLite on Persistent Disk | **Neon**（Postgres 無料枠） |

#### 1-4-1. スピンダウンが許容できる理由

**バッチをGitHub Actionsに移すと、Webサービスのスピンダウンは「データの鮮度」に影響しなくなる。** 影響するのは初回アクセス時の応答時間（約1分の起動待ち）のみである。

| 観点 | 影響 |
|---|---|
| データ鮮度 | **影響なし**。GitHub ActionsがWebサービスの状態と無関係に4時間ごとに更新する |
| 初回アクセス | **約1分の起動待ち**。個人利用（1日数回のアクセス）では許容範囲だが、UXは明確に劣化する |
| 2回目以降 | 15分以内の再アクセスなら待ちなし |

#### 1-4-2. 移行コスト(1)：**SQLite → Postgres の置き換えは低コスト**

コードを確認した結果、**移行の技術的障壁は小さい**。

| 確認項目 | 結果 |
|---|---|
| `db/crud.py` の生SQL（`execute()`） | **0件**。全てSQLAlchemy ORMで記述されている |
| SQLite依存箇所 | **`db/models.py` L83 の `create_engine()` 1行のみ**。ただし**その1行の中で2箇所の変更が要る**：①URLスキーム `sqlite:///` → `postgresql://`、②**`connect_args={"check_same_thread": False}` の除去**（SQLiteドライバ専用の引数であり、Postgresに渡すとエラーになる） 🔧（v0.2で補足・レビューGRN-02対応） |
| `db/migrate_p2.py` の `sqlite3` 直接使用 | 一度限りの移行スクリプトであり**ランタイム対象外** |
| **`requirements.txt`** 🆕 | **Postgresドライバが存在しない**（現在は `sqlalchemy` のみ）。`psycopg2-binary` 等の追加が必要 |
| **`DATABASE_URL` の意味** 🆕 | 現在は**ファイルパス**として使われ、`models.py` L83 が f-string で `sqlite:///` を前置している。Postgresでは**接続URL全体**になるため前置をやめる。**`render.yaml` の `DATABASE_URL` も接続URLに書き換え**、Neonの接続文字列は秘匿情報のため **`sync: false` 扱い**とする |
| **`backend/tests/conftest.py`** 🆕 | **L31-33 で SQLite を直接指定**（`sqlite:///{TEST_DB_PATH}` ＋ `connect_args`）。移行後は**本番Postgres・テストSQLite**という状態になる |

##### テストDBの扱い（v0.2追加・レビューYEL-05対応）

**問題**: 移行後、フェーズ2で積み上げた90件のテスト（カバレッジ94%）が**本番環境を代表しなくなる**。SQLiteとPostgresは型の厳密さ・文字列比較の照合順序・`LIKE`の大小文字の扱い・暗黙変換・トランザクション分離が異なる。

**リスクの程度**: 本アプリのスキーマは **Text / Integer のみで方言依存が少なく**、`crud.py` もORMで統一されているため**相対的に低い**。ただし要件定義書§3-1 項目7は「改修部分のカバレッジ80%以上」を合否判定項目としており、**カバレッジの数値は維持できてもそれが担保する内容が変わる**。

| 案 | 内容 | 評価 |
|---|---|---|
| **案A** | テストもPostgresで実行する（**GitHub Actions を使うなら `services: postgres` で完結する**） | 本番との一致度が最も高い。再設計案でGitHub Actionsを導入するなら**追加コストは小さい** |
| 案B | SQLiteのまま維持し、差異が出やすい箇所のみ結合テストでPostgresを使う | 中間案 |
| 案C | SQLiteのまま維持しリスクを受容する | 現状のスキーマなら現実的な選択肢 |

> **手順5（テスト設計）に引き継ぐ。** 再設計案を採用する場合、GitHub Actionsが前提になるため**案Aの追加コストが小さくなる**という相互作用がある。

> **ORMで統一されていたことが、そのまま移行可能性として効いている。** フェーズ2の基本設計でSQLAlchemyを採用した判断が、想定していなかった形で価値を持った。

#### 1-4-3. JWT認証の維持可否（**移行の絶対的ブロッカー**）

| 確認項目 | 判定 |
|---|---|
| Render 無料 Web Service でFastAPIのJWT認証が動作するか | ✅**動作する**（アプリケーション層の実装であり、プランに依存しない） |
| 環境変数（`SECRET_KEY`・`USERNAME`・`USER_PASSWORD`）の設定 | ✅可能 |
| **結論** | ✅**認証は維持できる。移行のブロッカーには該当しない** |

#### 1-4-4. データ移行の要否 🆕（v0.2新設・レビューYEL-01対応）

|---|---|---|
| **非移行（新規スタート）** | Neon上に空のDBを作り、バッチで新規に蓄積する | ✅**採用** |

**採用根拠（フェーズ2 7-J-4 の判断と同じ論法）**

フェーズ2では 7-J-4（DBデータ移行）を運用判断により**見送った**前例がある。その理由は本件にもそのまま当てはまる。

| # | 理由 | 本件への当てはまり |
|---|---|---|
| 1 | 本番が既に自走しており新規記事を自動蓄積する | ✅当てはまる（移行後もバッチが4時間ごとに動く） |

#### 1-4-6. ⚠️ バッチ間隔判定の二重化（**設計上の必須事項**） 🆕（v0.3新設・レビューYEL-01対応）

**GitHub Actionsから呼ぶエントリポイントを `check_and_run_batch()` にすると、実効的な取得間隔が8時間になる。**

**現状の実装**（`backend/scheduler.py` L184-187）

```python
def check_and_run_batch() -> None:
    last_fetched_at = crud.get_setting("last_fetched_at")
    if last_fetched_at == "" or _elapsed_hours(last_fetched_at) >= BATCH_INTERVAL_HOURS:
        run_batch()
```

`BATCH_INTERVAL_HOURS = 4`（`config.py` L16）。APSchedulerが**10分ごとにポーリング**し、「前回取得から4時間経過していれば実行する」という**ゲート方式**をとっている。10分ポーリング＋4時間ゲートの組み合わせでは正しく機能する。

**再設計案で起こること**

cronの起動間隔（4時間）とアプリ側のゲート（4時間）が**同じ値で二重にかかる**。`run_batch()` は末尾（⑩・L180）で `last_fetched_at` に**バッチ開始時刻**を書き込む。GitHub Actionsはキュー待ちやランナー起動で**数分の遅延が常態的に発生する**。

| cron予定 | 実際の開始 | 経過時間 | 結果 |
|---|---|---|---|
| 00:00 | 00:03 | — | 実行。`last_fetched_at = 00:03` |
| 04:00 | 04:01 | 3.97h < 4h | ❌**スキップ** |
| 08:00 | 08:02 | 7.98h ≥ 4h | 実行 |

> **1回おきにスキップされ、実効的な取得間隔が8時間になる。** しかも `run_batch()` が呼ばれないだけなので**エラーも警告も出ない**。GitHub Actionsのジョブは「成功」で終わり、記事だけが更新されない。**同じことが `check_and_run_game_schedule_batch()`（L246-249）にも当てはまる。**

**対処方針：エントリポイントを `run_batch()` にする（ゲートを外す）** ✅

| 案 | 内容 | 採否 |
|---|---|---|
| **ゲートを外す** | GitHub Actionsから `run_batch()` を直接呼ぶ。**スケジューリングの責務をcron側に一本化する** | ✅**採用** |
| ゲートを残す | `BATCH_INTERVAL_HOURS` をcron間隔より短くする（例：3.5時間）か、比較にマージンを設ける | ❌不採用（二重管理が残る） |

**採用根拠**: 責務の所在を1箇所にする方が単純である。加えて **`/api/fetch`（手動起動）は既に `run_batch` を直接呼んでおり**（`routes.py` L104-110）、ゲートを通らない。GitHub Actionsからの呼び出しもこれに揃えるのが一貫する。

> **実害の性質**: 「記事の更新頻度が半減し、かつ気付けない」という形で出る。要件定義書§4-1の指標2（直近N日の取得件数）・指標4（最終取得日時）を観測していれば検知できるが、**それらの実装は手順7**である。**設計段階で潰しておく方が確実に安い。**
>
> **手順3への引き継ぎ**: 差分設計（**§5-1 #1**）に本論点を含める。

### 3-5. 認証必須エンドポイントの監視方式 🆕（v0.2新設・レビューYEL-02対応）

**前提**: `/api/status` は `Depends(get_current_user)` によりJWT必須である（`api/routes.py` L93-94）。監視主体がどうやって認証を通すかを決める必要がある。

**採用方針：401応答をもって「生存」と判定する** ✅

| 案 | 内容 | 採否 |
|---|---|---|
| **401判定** | 認証情報を持たずにアクセスし、**401が返れば「サーバーは生きている」**と判定する | ✅**採用** |
| 監視用トークン | 監視専用の認証情報を発行して200応答を確認する | ❌不採用 |

**採用根拠**

| # | 理由 |
|---|---|
| 1 | **新たなシークレットを増やさない**。§4-2は「シークレットの管理先が分散」を⚠️として挙げており、監視用トークンはこれをさらに悪化させる |
| 2 | **既に実証済み**。2026-08-23にブラウザから `{"detail":"Not authenticated"}`（401）が返ることを確認しており、この判定方式が機能することは確かめられている（§3-1） |
| 3 | 監視用トークンは**認証面を1つ増やす**。認証は著作権法第30条の公開範囲を担保する唯一の手段（§4-1）であり、面を増やすのは方針と整合しない |

**401判定の限界**

| 検知できるもの | 検知できないもの |
|---|---|
| サーバープロセスが応答すること | **DB接続の可否**（401はDBに触れずに返る） |
| ネットワーク経路が生きていること | **バッチが動いているか** |
| — | **⚠️ スピンダウン環境では機能しにくい** 🆕（下記） |

##### ⚠️ 構成による有効性の違い（v0.3追加・レビューYEL-02対応）

**§3-3は「Webサービスがスピンダウンすると、応答がない＝障害ではなくなり、単純な死活監視が意味を失う」と述べている。401判定はまさにその単純な死活監視にあたる。** 前提の変化を§3-5に反映する。

| 構成 | 401判定の位置づけ |
|---|---|
| **現行（Starterプラン・常時起動）** | ✅**有効**。401が返らなければ障害と判定できる |
| **再設計案（無料プラン・スピンダウン）** | ⚠️**補助的な指標に降格**。主たる監視対象は「**バッチが4時間ごとに走っているか**」 |

**再設計案で401判定が機能しにくい理由**

| 監視間隔 | 起こること |
|---|---|
| **空ける**（30分〜1時間） | 15分の無アクセスでスピンダウンしているため**毎回コールドスタート**になる。復帰に**約1分**かかり、外形監視の一般的なタイムアウト（30秒前後）に引っかかって**正常なのに障害と判定される** |
| **詰める**（5分ごと） | スピンダウンしなくなるが**常時起動＝月720時間**を消費する。無料枠は**750インスタンス時間/月・ワークスペース単位**（§1-2 制約5）であり**枠の96%を1サービスで使い切る**。「スピンダウンを許容する代わりに無料」という§1-4-1の前提そのものが崩れる |

**再設計案での監視方針**

| 優先度 | 監視対象 | 判定手段 |
|---|---|---|
| **主** | **バッチが4時間ごとに走っているか** | GitHub Actionsのワークフロー実行結果＋要件定義書§4-1の**指標2（直近N日の取得件数）・指標4（最終取得日時）** |
| 従 | Webサービスの死活 | 401判定（**タイムアウト値を90秒以上に設定できる監視手段を選ぶ**） |

> **§3-2の比較軸への追加**: 再設計案を採用する場合、監視手段の選定基準に「**タイムアウト値を長め（90秒以上）に設定できること**」を加える。
>
> **本節の位置づけ**: 401判定の採否そのものは変わらない（現行構成では正しく、監視用トークンを増やさない判断も妥当）。**§3-3で認識した前提の変化が§3-5に反映されていなかった**ため、構成別に整理した。

#### 4-2-1. シークレットの配置表 🆕（v0.4新設・レビューYEL-01対応）

**⚠️ バッチ実行環境にも JWT署名鍵（`SECRET_KEY`）の配布が必要になる。**

**原因**：`backend/config.py` L59-64 の必須チェックは**モジュールのロード時**に評価される。`scheduler.py` は先頭で `from config import ...` を行うため、**バッチを動かすだけでも `config.py` 全体が読み込まれ、`SECRET_KEY` のチェックが発火する**。同様に `USERNAME` / `USER_PASSWORD`（L69-73）も必須である。

```python
# backend/config.py L59-64
SECRET_KEY = os.getenv("SECRET_KEY", "")
if not SECRET_KEY:
    raise RuntimeError("SECRET_KEY が未設定です。...")
```

**配置表**

| シークレット | Render環境変数（API層） | GitHub Secrets（バッチ層） | バッチ層で**本来必要か** |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | ✅必要 | ✅必要 | ✅**必要**（翻訳） |
| `BALLDONTLIE_API_KEY` | ✅必要 | ✅必要 | ✅**必要**（スコア取得） |
| `DATABASE_URL`（Neon接続文字列） | ✅必要 | ✅必要 | ✅**必要**（DB書き込み） |
| **`SECRET_KEY`** | ✅必要 | ⚠️**現状の実装では必要** | ❌**不要**（バッチはJWTの発行も検証もしない） |
| **`USERNAME`** | ✅必要 | ⚠️**現状の実装では必要** | ❌**不要** |
| **`USER_PASSWORD`** | ✅必要 | ⚠️**現状の実装では必要** | ❌**不要** |

**⚠️ バッチ層に置く値は「本物」である必要がない** 🆕（v0.5追加・レビューYEL-02対応）

import連鎖を実際に確認した結果、**バッチ実行時にこれら3つの値は一度も参照されない**。

| 確認項目 | 結果 |
|---|---|
| `scheduler.py` の import | `config` / `db.crud` / `fetcher.*` / `processor.*` のみ。**`auth` を含まない**（`db/__init__.py` は空） |
| `SECRET_KEY` の使用箇所 | **`auth/jwt.py` L5・L13・L19 のみ** |
| `INIT_USERNAME` / `INIT_USER_PASSWORD` の使用箇所 | **`auth/users.py` L3・L12・L13 のみ** |
| `auth` を import しているモジュール | `api/routes.py` と `main.py` のみ |

つまりこれらは **`config.py` の必須チェックを通過するためだけに存在し、バッチでは参照されない**。GitHub Secrets に置くのは**任意の非空文字列で足りる**。

> **本プロジェクトには既に前例がある**: `backend/tests/conftest.py` L18-22 は、まさにこの方式（チェックを通すためのダミー値）を採用しており、フェーズ2から運用されている。
>
> ```python
> os.environ.setdefault("SECRET_KEY", "test-secret-key-for-testing-purposes-only-32chars")
> os.environ.setdefault("USERNAME", "testuser")
> os.environ.setdefault("USER_PASSWORD", "testpass123")
> ```

**問題の質（v0.5で訂正）**

v0.4は「この鍵を**2箇所に保管する**ことを要求し、**漏洩面がその分増える**」と断定していたが、**これは過大な評価だった**。正確には次の通り。

> **現状の実装のままでは、バッチ層にも「何らかの値」の設定を要求する。本物を置く必要はないが、`config.py` が用途を区別しないため、その判断は運用者に委ねられる。**

**§4-1が述べる通り JWT認証は著作権法第30条の公開範囲を担保する唯一の手段**であり、`SECRET_KEY` はその根拠となる鍵である。したがって**本物を2箇所に置かない選択肢があることは、評価を大きく変える**。

> **先行対応（先-1）との相互作用**: 先-1で `ANTHROPIC_API_KEY` / `BALLDONTLIE_API_KEY` にも同じ `RuntimeError` を追加する予定であり、`config.py` は**すべての必須シークレットが揃わないと import できないモジュール**になる。**バッチ層とAPI層で必要なシークレットが異なるにもかかわらず、両者が同じ全量を要求される構造**になる。

**対処の方向（手順3で決定）**

| 案 | 内容 | 評価 |
|---|---|---|
| **案A** | `config.py` の必須チェックを**用途別に分ける**（認証系は `auth/` 側でロード時に検証する等） | **構造的には正しい**。バッチ環境に `SECRET_KEY` を置かなくて済む |
| 案B | バッチ用に別のエントリポイントを設け、`config` のうち必要な定数のみを読む構成にする | 中間案 |
| 案C | GitHub Secrets にも**本物の** `SECRET_KEY` を置くことを受容し、**ローテーション手順を定める** | ❌**不採用**（漏洩面が増える。案Dで回避できる） |
| **案D** 🆕 | **バッチ層にはダミー値を設定する**（`conftest.py` L18-22 と同じ方式） | ✅**最小コストで漏洩面を回避できる**。ただしダミーと本物の識別が困難 |

**案Dのリスクと歯止め**

| リスク | 歯止め |
|---|---|
| GitHub Secrets 上で本物とダミーが**見分けられない** | 値を **`DUMMY-NOT-USED-BY-BATCH` のようにダミーであることが値自体から分かる形**にする |
| バッチが将来JWTを扱うようになった場合、**静かに壊れる** | 案Aを採れば構造的に防げる。案Dを採る場合は上記の値の命名で気付けるようにする |
| シークレット管理画面に意味のない項目が並ぶ | 受容する |

## 7. 本調査で得られた教訓

### 7-1. 「測る手段」の前に「何を測れば判断できるか」を確認する

計画書 手順2-A は「**Persistent Disk の実使用量**」を無料化可否の判断材料と位置づけ、その実測手段の確保を最優先項目とした。しかし実際には、**Render無料プランに Persistent Disk が存在しない**ため、容量は判断材料になり得なかった。

| 段階 | 内容 |
|---|---|
| v0.5レビューYEL-01 | 「実測手段が確保されていない」と指摘 → 手順2-Aに「実測手段の確保」を新設 |
| v0.6レビューGRN-02 | 「案(b)は4項目中1項目しか満たせない」と指摘 → 選定順序を明記 |
| **本調査** | **そもそも測る対象の見立てが違っていた** |

> **教訓**: 「観測できるかを先に検証する」（振り返り3-9）の一段手前に、「**何を知れば判断できるかを先に確認する**」工程が要る。手段の議論は、対象が正しいことを前提にしている。
>
> 本件では**低コストな調査（無料プランの仕様確認）を先に行えば、実測手段の議論そのものが不要だった**。

### 7-2. 過去の設計判断が想定外の形で効くことがある

フェーズ2で SQLAlchemy ORM を採用した判断により、`db/crud.py` に生SQLが1件も存在しない。結果として **SQLite → Postgres の移行が `create_engine()` 1行の変更**で済む見通しとなった。
