[YEL-01] バッチ実行環境（GitHub Actions）にも JWT署名鍵（SECRET_KEY）の配布が必要になる

  対象箇所: §1-4（再設計案）／ §4-2 観点3・5

  現状の実装（`backend/config.py` L59-64）:

      # JWT設定
      SECRET_KEY = os.getenv("SECRET_KEY", "")
      if not SECRET_KEY:
          raise RuntimeError(
              "SECRET_KEY が未設定です。openssl rand -hex 32 で生成し環境変数に設定してください。"
          )

  この必須チェックは **モジュールのロード時**に評価される。
  `scheduler.py` は先頭で `from config import BATCH_INTERVAL_HOURS, ...` を行うため、
  **バッチを動かすだけでも `config.py` 全体が読み込まれ、SECRET_KEY の
  チェックが発火する**。

  問題:
    再設計案では GitHub Actions のランナー上で `backend/` のバッチを実行する。
    バッチは RSS取得・翻訳・スコア取得・DB書き込みを行うだけで、
    **JWTの発行も検証も一切行わない**。それにもかかわらず、
    `SECRET_KEY` を GitHub Secrets に登録しないと起動しない。

    これは単なる「シークレットが1つ増える」以上の意味を持つ。
    §4-1 が述べる通り、**JWT認証は著作権法第30条の公開範囲を担保する唯一の手段**
    であり、`SECRET_KEY` はその根拠となる鍵である。
    再設計案は、この鍵を **Render 環境変数と GitHub Secrets の2箇所**に
    置くことを要求する。鍵の保管場所が増えれば、漏洩面もその分増える。

    §4-2 は観点3で「シークレットの管理先が分散（Render環境変数＋GitHub Secrets＋
    Neon接続文字列の3箇所）」を⚠️としているが、
    **そこに含まれるのがどのシークレットか**は書かれていない。
    バッチに本来不要な認証鍵まで配ることになる点は、
    「設定漏れのリスクが増える」（§1-5 リスク5）とは質の違う論点である。

    なお先行対応（先-1）で `ANTHROPIC_API_KEY` / `BALLDONTLIE_API_KEY` にも
    同じ RuntimeError を追加する予定であり、`config.py` は
    **すべての必須シークレットが揃わないと import できないモジュール**になる。
    バッチ環境と API 環境で必要なシークレットが異なるにもかかわらず、
    両者が同じ全量を要求される構造になる。

  推奨対応:
    ・§4-2 の観点3を具体化し、**どのシークレットがどこに置かれるか**の
      対応表を作る。
        Render 環境変数：SECRET_KEY・USERNAME・USER_PASSWORD・
                         ANTHROPIC_API_KEY・BALLDONTLIE_API_KEY・DATABASE_URL
        GitHub Secrets ：ANTHROPIC_API_KEY・BALLDONTLIE_API_KEY・DATABASE_URL
                         ＋（現状の実装では）**SECRET_KEY**
      重複と、本来不要なものが見える形にする。
    ・対処の方向を手順3へ引き継ぐ。候補：
        案A：`config.py` の必須チェックを**用途別に分ける**
             （認証系は `auth/` 側でロード時に検証する等）。
             バッチ環境に SECRET_KEY を置かなくて済む
        案B：バッチ用に別のエントリポイントを設け、
             `config` のうち必要な定数のみを読む構成にする
        案C：GitHub Secrets にも SECRET_KEY を置くことを受容し、
             ローテーション手順を定める
      案Aが構造的には正しいが、先行対応（先-1）で `config.py` の
      必須チェックを触るため、**先-1 の実装方針と併せて検討する**のが効率的である。
    ・§1-5 のリスク表に「認証鍵の保管場所が2箇所になる」を追加する。

  重要度の根拠:
    セキュリティ水準の評価（§4-2）は「**水準は低下しないが、管理対象が増える**」
    という総合判定を出しており、無料化が計画書§2ガイドライン
    「安全性を犠牲にしないことを絶対条件とする」に抵触しないという結論を支えている。
    その判定の根拠となる「何が増えるのか」の内訳に、
    認証鍵の複製が含まれていない。手順6の判断材料として精度が足りない。


[YEL-02] 再設計案の実装コストが「DB移行分」しか評価されていない

  対象箇所: §1-4-2（表題：移行コストの評価：SQLite → Postgres は低コスト）／ §1-4

  現状:
    §1-4-2 は移行コストを評価する唯一の節であり、
    **SQLite → Postgres の置き換え**に限定されている（表題の通り）。
    6項目の確認は正確で、v0.3 で `requirements.txt` と `DATABASE_URL` が
    追加され網羅性も上がった。

  問題:
    再設計案は「DBを差し替える」だけの変更ではなく、
    **1つのWebサービスを3つの実行環境に分割する**構成変更である。
    そのために新規に必要となる成果物・変更が、どこにも整理されていない。

    実装を確認したところ、少なくとも次の3点が発生する。

    (1) `main.py` のスケジューラ起動を条件分岐する必要がある
        `main.py` は L12 で `from scheduler import check_and_run_batch, scheduler`、
        L56 で `scheduler.start()`、L63 で `scheduler.shutdown()` を実行している。
        §1-4 の表は API 層を「**FastAPIのみ・スケジューラなし**」としているが、
        現状のコードは起動時に必ず APScheduler を立ち上げる。
        環境変数による切り替えなど、`main.py` の変更が要る。

    (2) GitHub Actions 用のバッチエントリポイントが必要
        §1-4-6 は「`run_batch()` を直接呼ぶ」と決めたが、
        それを呼び出すスクリプト（例：`backend/run_batch_once.py`）は存在しない。
        `run_batch()` と `run_game_schedule_batch()` の2つを
        どう呼ぶか（1ジョブか2ジョブか）も未定である。

    (3) GitHub Actions のワークフロー定義（`.github/workflows/*.yml`）が必要
        cron設定・Python環境構築・依存インストール・シークレット注入・
        失敗時の通知を含む新規ファイルである。

    これらは個別には小さいが、**「$0/月」の対価として支払う実装量**にあたる。
    §5 #1 は手順6で「UX劣化（起動待ち1分）とホスティング$7.25/月を天秤にかける」
    としているが、天秤の片側には**実装コストも乗る**。
    現状の記述では「移行コストは低い（DBは1行）」という印象が先に立ち、
    構成分離そのものの作業量が見えない。

  推奨対応:
    ・§1-4-2 の表題を「**移行コストの評価**」に一般化し、
      「(1) DB移行のコスト」と「(2) 構成分離のコスト」に分ける。
      あるいは §1-4-8 として「構成分離に必要な新規成果物」を新設する。
    ・新規に必要な成果物を一覧化する。
        `main.py` の変更（スケジューラ起動の条件分岐）
        バッチ用エントリポイント（新規スクリプト）
        `.github/workflows/*.yml`（新規）
        `requirements.txt` へのPostgresドライバ追加（既出）
        `render.yaml` の変更（既出）
      それぞれの規模感（小・中）を添えると手順6で使える。
    ・これらは §5 #5（手順3の差分設計）の対象でもあるため、
      引き継ぎ内容に「新規成果物の洗い出しを含む」と明記する。

  補足:
    実装コストの総量は依然として小さい見込みである（いずれも新規ファイル1〜2本と
    既存2ファイルの小変更）。本指摘は「コストが高い」というものではなく、
    **判断材料として全量が見えていない**という点にある。
    §1-4-2 が「1行のみ」という強い表現を含むため、
    読み手が構成分離の作業を過小評価しやすい。

  一方 §1-4-6 では対処方針が**確定**している

    判断のノイズになる。


[GRN-03] DB規模の推定が SQLite 前提であり、Postgres では大きくなる旨の注記がない

  §1-1 は保持記事数 約215件・1記事あたり約5KB・**DB全体 約1〜2MB** と推定している。
  推定の根拠（30日保持 × 週50件、`summary_ja` 800〜1200字 × UTF-8 3バイト）は
  明示されており、フェーズ1レビュー提言10の観点を満たしている。

  ただしこの見積は**現行の SQLite ファイルサイズ**を想定したものである。
  Postgres では次の要因で実サイズが大きくなる。
    行あたりのヘッダオーバーヘッド（SQLiteより大きい）
    インデックス（`models.py` で5本定義されている）の実体
    MVCC による更新・削除済みタプル（`delete_old_articles()` が毎日走る）
    Neon のストレージは data に加え **history**（時点復元用）を含む

  実測すれば数倍になる可能性があるが、それでも Neon 無料枠 0.5GB に対しては
  桁違いの余裕があり、**§1-1 の結論（推定で足りる）は変わらない**。

  → §1-1 に1行添える。
    「本推定は SQLite ファイルサイズを前提とする。Postgres ではインデックス・
      MVCC・Neonのhistoryにより数倍になりうるが、0.5GB に対しては
      なお2桁の余裕がある」
    §1-1 は「判断が変わる条件：記事数が250倍」と明示しているため、
    倍率の余裕を示す形で整合が取れる。


[GRN-04] cron の実行時刻（UTC基準）の設計が未検討

  再設計案はバッチを GitHub Actions の cron に移す。
  GitHub Actions の cron は **UTC 基準**であり、実行時刻が固定される。

  現行の APScheduler は `interval`（10分ポーリング＋4時間ゲート）であり、
  **起動時刻に依存しない**。サービス再起動のたびに位相がずれるが、
  「前回から4時間」は保たれる。

  cron に移すと、例えば `0 */4 * * *` なら UTC 0/4/8/12/16/20時
  ＝ **JST 9/13/17/21/1/5時** に固定される。
  NBA の試合は日本時間の午前中に終わるため、
  **朝の更新が JST 9時になるか、それより前になるか**で
  「朝起きて見たときに前夜の記事が入っているか」が変わる。

  実用上の差は小さく、手順3で決めれば足りる論点だが、

■ 結論
================================================================================

  🔴致命 0件。**手順3（基本設計）への着手可**と判定する。

  🟡2件の推奨処理順:

    1. YEL-01（SECRET_KEY の配布）
       先行対応（先-1）は `config.py` の必須チェックを触る作業であり、
       2026年9月までに実施される。**先-1 の実装方針と併せて検討する**と
       手戻りがない。シークレットの配置表（どれをどこに置くか）を
       §4-2 に作るだけでも、手順6の判断材料としての精度が上がる。

    2. YEL-02（構成分離の実装コスト）
       手順6で「$0/月」と「UX劣化＋実装コスト」を天秤にかける際に要る。
       新規成果物は3点（`main.py` 変更・バッチエントリポイント・
       ワークフロー定義）と少ないため、洗い出し自体は短時間で済む。

  🟢4件はいずれも記述の追加・並べ替えで解消できる。
  GRN-01（引き継ぎ表の採番）は、v0.3 で新設した自己チェック第13項を
  §5 にも適用すれば検出できる。

  ── 総評 ──

  v0.1 → v0.2 → v0.3 の3版を通じて、指摘の解消率は100%を維持している。
  本書の特徴は、指摘への対応が**個別の修正で終わらず、
  検出条件（自己チェック項目）と記録（§6-2）に変換されている**ことである。
  v0.3 で新設された第11〜13項は、いずれも v0.2 の指摘から導かれている。

  今回の🟡2件は、その第11項「提案した構成を『実際に動かすとどうなるか』まで
  検討したか」の適用範囲に関わる。v0.3 はこの項目を新設し、
  §1-4-6（バッチのエントリポイント）と §1-4-7（`/api/fetch`）で実際に適用した。
  ただし適用先が**バッチの呼び出し方**に集中しており、
    ・モジュールロード時に何が要求されるか（SECRET_KEY）
    ・API 側が何を止めなければならないか（`main.py` のスケジューラ）
    ・新規に何を作らなければならないか（ワークフロー・エントリポイント）
  という**構成分離そのものが要求する変更**には及んでいない。

  第11項を次に適用するとすれば、
  「**新構成で動かすために、既存コードのどこに手を入れる必要があるか**」を
  一覧化する形になる。それが YEL-02 の推奨対応にあたる。

  リスク調査書としては、手順6で要望1の採否を判断するための材料が
  ほぼ揃っている。残るのは実装コストの全量（YEL-02）と、
  セキュリティ上の代償の内訳（YEL-01）である。
