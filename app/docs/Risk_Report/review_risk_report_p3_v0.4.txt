[YEL-01] `render.yaml` の実在が未確認で、Render側の構成変更が未整理

  対象箇所: §1-4-2 #5 ／ §1-4-8 #5 ／ §6-1 第7項

  (1) **`render.yaml` が連携フォルダ内に存在しない**

      プロジェクトルートを確認したところ、実体は以下のみである。
        `.claude` `.env.example` `.ipynb_checkpoints`
        `CLAUDE.md` `README.md` `backend` `docs` `frontend` `setup.md`

      **`render.yaml` は存在しない。**
      （なお `.github/` も存在せず、これは §1-4-8 #3 が
        ワークフロー定義を「新規」と判定した前提と一致している。）

      本書は §1-4-2 #5 と §1-4-8 #5 で `render.yaml` を
      「変更が必要なファイル」として2箇所に挙げている。
      実体の所在が確認されていない状態で変更対象に数えている。

      フェーズ2のセキュリティレビュー時には `render.yaml` が
      共有されているため、**Gitリポジトリには存在するが連携フォルダに
      含まれていない**か、**Renderダッシュボードでの設定に切り替えており
      ファイルは使っていない**かのいずれかと考えられる。
      どちらであるかで §1-4-8 #5 の作業内容が変わる。

      **本件は本書自身の仕組みで検出できたはずである。**
      §6-2 の v0.2 GRN-01 の対策欄には
        「第7項の対象に **`requirements.txt`・`render.yaml`** を含める（運用）」
      と記録されている。しかし §6-1 第7項の実施内容は
        「v0.3で `scheduler.py`／`routes.py`／`requirements.txt`／`models.py` を確認」
      のままで、**`render.yaml` が入っていない**。
      運用として決めたことが、次の版で実行されなかった形である。

  (2) **変更内容が `DATABASE_URL` のみで、プランとディスクに触れていない**

      §1-4-2 #5 / §1-4-8 #5 が挙げる `render.yaml` の変更は
      「`DATABASE_URL` を接続URLに・`sync: false`」だけである。

      本セッション前半で共有された `render.yaml` の内容によれば、
      同ファイルには少なくとも次が含まれていた。
        `plan: starter`
        `disk:`（マウントパス `/data`・1GB）
        `healthCheckPath: /healthz`
        `HOST=0.0.0.0`
        シークレット5件（すべて `sync: false`）

      再設計案（Render無料プランへの移行）では、
        ・`plan: starter` → 無料プランへの変更
        ・**`disk:` セクションの削除**（§1-2 の通り無料プランは Persistent Disk 非対応）
      が必須である。いずれも記載がない。

  (3) **作業順序の制約がある**

      Persistent Disk がアタッチされたサービスは、そのままでは
      Disk 非対応のプランへ変更できない。したがって
        ディスクのデタッチ（＝現行データの破棄）→ プラン変更 → 環境変数の差し替え
      という順序になる。

      §1-4-4 が「非移行（新規スタート）」を採用しているため
      データ破棄は方針と整合するが、**順序そのものは記録されていない**。
      §1-4-8 は「何を変えるか」の一覧であり「どの順で行うか」がない。
      §1-4-6 でバッチのエントリポイント、§1-4-7 で `/api/fetch` と
      「動かすとどうなるか」を詰めてきた流れからすると、
      移行手順そのものも同じ水準で見ておく価値がある。

  推奨対応:
    ・`render.yaml` の所在を確認し、結果を §1-4-8 #5 に記録する。
      存在しない（ダッシュボード設定に移行済み）場合は、
      作業内容を「Renderダッシュボードでの再設定」に書き換える。
    ・変更内容に `plan` の変更と `disk:` セクションの削除を追加する。
    ・§1-4-8 の後に「移行の作業順序」を数行で示す。
      （ディスクのデタッチ → プラン変更 → 環境変数の差し替え →
        GitHub Actions の有効化 → 初回バッチ実行 → 切り替え）
      §1-4-4 の「移行前にバッチを1回走らせる」という対処も
      この順序の中に位置づけられる。
    ・§6-1 第7項の実施対象に `render.yaml` を実際に含める
      （§6-2 で決めた運用を実行する）。


[YEL-02] §4-2-1 の対処案に「バッチ層にはダミー値を置く」が欠けており、
         問題の評価が過大になっている可能性がある

  対象箇所: §4-2-1「対処の方向」／「問題の質」／ §1-5 リスク10

  §4-2-1 は問題の質を次のように評価している。

      「§4-1が述べる通り **JWT認証は著作権法第30条の公開範囲を担保する
        唯一の手段**であり、`SECRET_KEY` はその根拠となる鍵である。
        再設計案はこの鍵を**2箇所に保管する**ことを要求し、
        **漏洩面がその分増える**。」

  対処として案A（用途別分離）・案B（別エントリポイント）・
  案C（受容＋ローテーション）の3案が示されている。

  問題:
    **バッチ層に置く値は、本物である必要がない。**
    import 連鎖を実際に確認した結果は次の通りである。

      `scheduler.py` の import：
        config / db.crud / fetcher.rss / fetcher.score /
        processor.claude_client / processor.dedup / processor.filter
        → **`auth` は含まれない**（`db/__init__.py` は空）

      `SECRET_KEY` の使用箇所：`auth/jwt.py` L5・L13・L19 のみ
      `INIT_USERNAME` / `INIT_USER_PASSWORD` の使用箇所：
        `auth/users.py` L3・L12・L13 のみ
      `auth` を import しているのは `api/routes.py` と `main.py` のみ

    つまりバッチ実行時、これら3つの値は **`config.py` の必須チェックを
    通過するためだけに存在し、一度も参照されない**。
    GitHub Secrets に置くのは任意の非空文字列で足りる。

    **本プロジェクトには既に前例がある。**
    `backend/tests/conftest.py` L21：

        os.environ.setdefault("SECRET_KEY", "test-secret-key-for-testing-purposes-only-32chars")

    テスト環境ではまさにこの方式（チェックを通すためのダミー値）が
    採用されており、フェーズ2から運用されている。

    この選択肢を加えると、§4-2-1 の評価は変わる。
      ・「認証鍵を2箇所に保管する」必要はない
      ・「漏洩面がその分増える」は**回避できる**
      ・§1-5 リスク10 の残存度は「中（案Aを採れば低）」から
        「**低（ダミー値で回避可能）**」に下がる

  ただしダミー値には固有のリスクがある:
    ・GitHub Secrets 上で本物とダミーが**見分けられない**。
      将来「SECRET_KEY が設定されている」ことを根拠に
      誤った前提を置く可能性がある
    ・バッチが将来 JWT を扱うようになった場合、静かに壊れる
    ・シークレット管理画面に意味のない項目が並ぶ

  推奨対応:
    ・対処案に**案D「バッチ層にはダミー値を設定する」**を追加し、
      評価（最小コストで漏洩面を回避できる／ダミーと本物の識別が困難）を記す。
      `conftest.py` L21 の前例も根拠として挙げられる。
    ・ダミーを採る場合の運用上の歯止めを1行添える。
      例：「GitHub Secrets の値を `DUMMY-NOT-USED-BY-BATCH` のように
      **ダミーであることが値自体から分かる形**にする」
    ・§4-2-1 の「問題の質」を書き換える。
      現状の記述は「鍵を2箇所に保管することを要求する」と断定しているが、
      正確には「**現状の実装のままでは、バッチ層にも何らかの値の設定を要求する**。
      本物を置く必要はないが、`config.py` が用途を区別しないため
      その判断は運用者に委ねられる」となる。
    ・§1-5 リスク10 の残存度を見直す。

  重要度の根拠:
    §4-2 の総合判定「水準は低下しないが、管理対象が増える」は、
    無料化が計画書§2ガイドライン「安全性を犠牲にしない」に
    抵触しないという結論を支えている。
    §4-2-1 は v0.4 でその内訳として追加された節であり、
    **内訳の評価が実態より重い**と、手順6の判断が過度に保守的になる。


[YEL-03] 先-1（2026年9月まで）と手順3の前後関係が未整理で、記述が両立していない

  対象箇所: §4-2-1 末尾 ／ §5-1 #4 ／ §1-5 リスク10

  §4-2-1 は末尾で次のように述べている。

        先-1は2026年9月までに `config.py` の必須チェックを触る作業であり、
        **同じファイルを2度触ることを避けられる**。」

  一方 §5-1 #4 は同じ論点を **手順3（基本設計）** への引き継ぎとしている。
  §1-5 リスク10 の対処方針も「先行対応（先-1）の実装方針と併せて
  **手順3で決定する**」となっている。

  問題:
    計画書のマイルストーンでは、先-1 の期限は **2026年9月まで**である。
    手順3（基本設計）の時期は未定だが、手順1の着手が 2026-08-23、
    手順2が実施中（2026-08-25）であることから、
    **手順3が9月中に完了する保証はない**。
    フェーズ2の実績（手順1〜11で約11週間）を当てはめれば、
    手順3〜4に入るのは9月中〜下旬になる。

    先-1 が手順3より先に実施される場合、
    **案A〜C（あるいは案D）を決めないまま `config.py` を触る**ことになり、
    §4-2-1 が避けようとした「同じファイルを2度触る」が起きる。
    「併せて検討するのが効率的」と「手順3で決定する」は、
    先-1 が先に来る前提では両立しない。

  推奨対応:
    次のいずれかを選び、記録する。

      案1：**先-1 の実施前に方針だけ決める**
           config.py の必須チェックの扱い（用途別分離するか／
           ダミー値運用にするか）を、手順3を待たずに決定する。
           判断材料は §4-2-1 に揃っており、決定自体は短時間で済む。
           先-1 の実施時に一緒に反映できる。

      案2：**先-1 では触らないと決める**
           先-1 の対象を「ANTHROPIC_API_KEY / BALLDONTLIE_API_KEY の
           必須チェック追加」に限定し、用途別分離は手順3以降とする。
           その場合 `config.py` を2度触ることになるが、
           先-1 の変更は3行であり手戻りは小さい。

      案3：**要望1の採否が確定するまで判断を保留する**
           そもそも要望1が不採用なら、バッチ層は存在せず本論点は消える。
           採否は手順6であり、先-1 より後になる。

    案1を推奨する。§4-2-1 が「2度触ることを避けられる」という
    効率性を根拠に挙げている以上、その効率を得るには
    **先-1 より前に決める**必要がある。

  補足:
    同種の前後関係は §5-4 #11（Health Check通知の無料プランでの可否確認）にも
    ある。先-2 も2026年9月までの作業であり、
    可否が未確認のまま実施時期を迎える。

  1. §6-1 第14項——チェック項目の適用漏れを検出する項目
     v0.3 GRN-01 は「第13項を新設した同じ版で、別の表に適用していなかった」

     これはチェック項目を1つ増やしているが、

     項目数を線形に増やすのではなく、項目の運用そのものを監視する層を
     1つ置いた形であり、計画書 §8-0-1 が掲げた
     「ルールを増やすのではなく古くなる書き方を排除する」と
     同じ方向の判断にあたる。

  本書の特徴は、指摘への対応が**個別の修正 → 検出条件の追加 →
