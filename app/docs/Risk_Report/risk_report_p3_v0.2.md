## 1. A. 無料ホスティング環境の調査（要望1）

### 1-1. 前提調査：現行DB規模の推定

**Takumi様の判断（2026-08-24）により、実測ではなく推定値で進める。**

| 項目 | 推定値 | 算出根拠 |
|---|---|---|
| 保持記事数 | **約215件** | 30日保持（`DATA_RETENTION_DAYS=30`）× 週50件（トライアル運用実績） |
| 1記事あたりのサイズ | **約5KB** | `summary_ja` 800〜1200字 × UTF-8日本語3バイト ≒ 3.6KB ＋ タイトル・メタ情報 |
| **articles テーブル** | **約1MB** | 215件 × 5KB |
| game_schedule・その他 | 数百KB | 30日保持・1日十数試合 |
| **DB全体** | **約1〜2MB** | — |

> **推定で足りると判断した理由**: 無料DBの容量枠は Neon 0.5GB・Supabase 500MB であり、**推定値の250〜500倍**の余裕がある。多少の推定誤差では判断が変わらない。実測は「容量が判断を分ける場合」にのみ必要だが、本件は該当しない。
>
> **判断が変わる条件**: 記事数が現在の**250倍以上**（週12,500件）になった場合。現実的でない。

### 1-2. Render 無料プランの制約

| # | 制約 | 本アプリへの影響 |
|---|---|---|
| 1 | **Persistent Disk が利用不可**（有料機能・$0.25/GB月） | **SQLiteの永続化ができない**。再起動のたびにデータ消失 |
| 2 | **15分間の無アクセスでスピンダウン**。再開に約1分 | **APScheduler常駐バッチが停止する**。記事が更新されなくなる |
| 3 | Background Worker は有料 | バッチを別プロセスに逃がせない |
| 4 | Static Site は**無料**（100GB帯域/月・500ビルド分/月） | フロントエンドは現状のまま無料で継続可能 |
| 5 | **750 インスタンス時間/月**（ワークスペース単位） 🆕 | **本構成では実質的な制約にならない**。スピンダウン中は時間を消費しないため、1日数回のアクセスなら月数時間程度に収まる |

> **制約1・2により、現構成（FastAPI＋APScheduler＋SQLite on Persistent Disk）のままの無料化は不可能。**

### 1-3. 代替ホスティングの調査

**確認日：2026-08-24**（無料枠の条件は変動が速いため、手順6・手順7の時点で**再確認が必要**）

| 候補 | 2026年8月時点の状況 | 採否・理由 |
|---|---|---|
| **Fly.io** | **2024年に新規向け無料枠（Hobby/Launch/Scale）が廃止**。2026年8月時点で新規は2VM時間または7日間の試用のみ。Volumeは停止中も課金 | ❌**不可**（無料枠が存在しない） |
| **Vercel Hobby** | 実行10秒タイムアウト。**非商用限定** | ❌**不可**（Claude API呼び出しを含むバッチが10秒に収まらない） |
| **Cloudflare Workers** | 10万req/日・CPU time 10ms/呼び出し・Cron Trigger 5本まで（無料） | ❌**不可**（理由は下記注記） |
| **GitHub Actions** | Private 2,000分/月・**Public無制限**。Cron最短5分間隔 | ✅**バッチの実行先として有力** |
| **Neon**（Postgres） | 無料枠 **0.5GB/プロジェクト**・**100 CU-hours/月**（超過時は次の請求期間まで compute 停止）・**転送 5GB/月**・computeは5分の無活動でscale-to-zero（無料プランでは無効化不可）。**7日無活動での自動停止はない** | ✅**DBとして有力** |
| **Supabase**（Postgres） | 無料枠 500MB・**7日間リクエストがないとプロジェクト自動停止** | △（自動停止が運用リスク） |
| **Render Postgres** 🆕 | 無料インスタンスは**期限付き**（一定期間後に削除される） | ❌**不可**（永続運用に使えない）。ただし**同一プラットフォームで完結する利点**があったため検討対象とした |

> **⚠️ Cloudflare Workers の却下理由の訂正（v0.2・レビューYEL-04対応）**
>
> v0.1は「Claude API応答待ちが10msに収まらない」を理由としていたが、**これは誤りである**。Cloudflare Workers の CPU time は**実行時間（wall time）ではなくCPUが実際に処理に費やした時間**であり、**`fetch()` の応答待ちなどのI/O待機は計上されない**。5秒のfetchを待っても待機中のCPU消費はゼロである。
>
> **正しい却下理由**: 本アプリは Python/FastAPI で構築されており、**Workers の実行環境でFastAPIをそのまま動かすのは現実的でない**。移植するには全面的な書き換えが必要で、移行コストが再設計案（`create_engine()` 1行）と比べて桁違いに大きい。
>
> **なぜ理由の訂正が重要か**: 調査書は**判断の根拠を残す文書**である。誤った理由のまま候補を消すと、後日「本当に不可だったのか」を再検証する際に誤った前提を引き継ぐ。

> **Neon の記述の訂正（v0.2・レビューYEL-04対応）**: v0.1は「scale-to-zero（**プロジェクト停止なし**）」と断定したが、**100 CU-hours/月の上限があり、超過すると次の請求期間まで compute が suspend される**。「停止なし」は**Supabaseの7日自動停止との差分**を指すものに限定する。本件の使い方（4時間ごとのバッチ＋1日数回のAPIアクセス）では100 CU-hoursに収まる見込みだが、上限の存在は§1-5のリスク表に追加した。

### 1-4. 再設計案：構成の分離

**発想の転換**：現構成が無料化できない原因は「**1つのWebサービスに常駐バッチとAPIを同居させている**」ことにある。バッチを外に出せば、スピンダウンは許容できる。

> **⚠️ 「$0/月」の範囲（v0.2で明示・レビューGRN-01対応）**: 本節の $0 は**ホスティング費用のみ**を指す。**Claude API のコストは残る**（フェーズ2実績 $1.27〜$1.72/月）。フェーズ2の月次総額は約$8.5〜$9.0 であり、再設計後の総額は**約$1.3〜$1.7/月**になる見込みである。

| 層 | 現行（ホスティング $7.25/月） | 再設計案（**ホスティング $0/月**） |
|---|---|---|
| フロントエンド | Render Static Site（無料） | **同左**（変更なし） |
| **バッチ**（RSS取得・翻訳・スコア取得） | Render Web Service内のAPScheduler | **GitHub Actions**（4時間ごとのcron） |
| **API**（`/api/news` 等） | 同上のFastAPI | **Render 無料 Web Service**（FastAPIのみ・スケジューラなし） |
| **DB** | SQLite on Persistent Disk | **Neon**（Postgres 無料枠） |

#### 1-4-1. スピンダウンが許容できる理由

**バッチをGitHub Actionsに移すと、Webサービスのスピンダウンは「データの鮮度」に影響しなくなる。** 影響するのは初回アクセス時の応答時間（約1分の起動待ち）のみである。

| 観点 | 影響 |
|---|---|
| データ鮮度 | **影響なし**。GitHub ActionsがWebサービスの状態と無関係に4時間ごとに更新する |
| 初回アクセス | **約1分の起動待ち**。個人利用（1日数回のアクセス）では許容範囲だが、UXは明確に劣化する |
| 2回目以降 | 15分以内の再アクセスなら待ちなし |

#### 1-4-2. 移行コストの評価：**SQLite → Postgres は低コスト**

コードを確認した結果、**移行の技術的障壁は小さい**。

| 確認項目 | 結果 |
|---|---|
| `db/crud.py` の生SQL（`execute()`） | **0件**。全てSQLAlchemy ORMで記述されている |
| SQLite依存箇所 | **`db/models.py` L83 の `create_engine()` 1行のみ**。ただし**その1行の中で2箇所の変更が要る**：①URLスキーム `sqlite:///` → `postgresql://`、②**`connect_args={"check_same_thread": False}` の除去**（SQLiteドライバ専用の引数であり、Postgresに渡すとエラーになる） 🔧（v0.2で補足・レビューGRN-02対応） |
| `db/migrate_p2.py` の `sqlite3` 直接使用 | 一度限りの移行スクリプトであり**ランタイム対象外** |
| **`backend/tests/conftest.py`** 🆕 | **L31-33 で SQLite を直接指定**（`sqlite:///{TEST_DB_PATH}` ＋ `connect_args`）。移行後は**本番Postgres・テストSQLite**という状態になる |

##### テストDBの扱い（v0.2追加・レビューYEL-05対応）

**問題**: 移行後、フェーズ2で積み上げた90件のテスト（カバレッジ94%）が**本番環境を代表しなくなる**。SQLiteとPostgresは型の厳密さ・文字列比較の照合順序・`LIKE`の大小文字の扱い・暗黙変換・トランザクション分離が異なる。

**リスクの程度**: 本アプリのスキーマは **Text / Integer のみで方言依存が少なく**、`crud.py` もORMで統一されているため**相対的に低い**。ただし要件定義書§3-1 項目7は「改修部分のカバレッジ80%以上」を合否判定項目としており、**カバレッジの数値は維持できてもそれが担保する内容が変わる**。

| 案 | 内容 | 評価 |
|---|---|---|
| **案A** | テストもPostgresで実行する（**GitHub Actions を使うなら `services: postgres` で完結する**） | 本番との一致度が最も高い。再設計案でGitHub Actionsを導入するなら**追加コストは小さい** |
| 案B | SQLiteのまま維持し、差異が出やすい箇所のみ結合テストでPostgresを使う | 中間案 |
| 案C | SQLiteのまま維持しリスクを受容する | 現状のスキーマなら現実的な選択肢 |

> **手順5（テスト設計）に引き継ぐ。** 再設計案を採用する場合、GitHub Actionsが前提になるため**案Aの追加コストが小さくなる**という相互作用がある。

> **ORMで統一されていたことが、そのまま移行可能性として効いている。** フェーズ2の基本設計でSQLAlchemyを採用した判断が、想定していなかった形で価値を持った。

#### 1-4-3. JWT認証の維持可否（**移行の絶対的ブロッカー**）

| 確認項目 | 判定 |
|---|---|
| Render 無料 Web Service でFastAPIのJWT認証が動作するか | ✅**動作する**（アプリケーション層の実装であり、プランに依存しない） |
| 環境変数（`SECRET_KEY`・`USERNAME`・`USER_PASSWORD`）の設定 | ✅可能 |
| **結論** | ✅**認証は維持できる。移行のブロッカーには該当しない** |

> 計画書§7は「無料化により認証が維持できない場合、**移行の絶対的ブロッカー**として扱う」と定めていた。本調査により**該当しないことを確認**した。

#### 1-4-4. データ移行の要否 🆕（v0.2新設・レビューYEL-01対応）

**判断：既存データは移行しない（新規スタート）** ✅

| 案 | 内容 | 採否 |
|---|---|---|
| **非移行（新規スタート）** | Neon上に空のDBを作り、バッチで新規に蓄積する | ✅**採用** |
| 移行 | 既存の約215件をSQLiteからNeonへ移す | ❌不採用 |

**採用根拠（フェーズ2 7-J-4 の判断と同じ論法）**

フェーズ2では 7-J-4（DBデータ移行）を運用判断により**見送った**前例がある。その理由は本件にもそのまま当てはまる。

| # | 理由 | 本件への当てはまり |
|---|---|---|
| 1 | 本番が既に自走しており新規記事を自動蓄積する | ✅当てはまる（移行後もバッチが4時間ごとに動く） |
| 2 | `delete_old_articles()` の**30日保持ポリシーにより移行データの大半が早期失効する** | ✅当てはまる（**移行しても30日で全て入れ替わる**） |
| 3 | 直近データは同じRSSソースから再取得できる | ✅当てはまる |

> 移行スクリプトの作成・検証コストに対して、得られるのは**最大30日で消えるデータ**である。割に合わない。

**移行直後の記事0件状態への対処**

| # | 対処 | 内容 |
|---|---|---|
| 1 | **移行前にバッチを1回走らせる** | 切り替え直後から記事が表示される状態にする |
| 2 | 数日間はコンテンツが薄い | 30日分が揃うまで徐々に増える。個人利用のため許容 |

**⚠️ 中止基準（データ消失）との区別**

要件定義書§3-3-2 項目5は「意図しないデータ消失」を中止基準としている。**計画的な非移行による0件状態は、これと見分けがつきにくい事象**であるため、区別を明記する。

| 事象 | 中止基準への該当 |
|---|---|
| **計画的な非移行による移行直後の0件状態** | ❌**該当しない**（意図した状態） |
| 移行後に蓄積したデータが意図せず失われた場合 | ✅**該当する** |

> **要件定義書への反映が必要**（§5 引き継ぎ #9）。§3-3-2 項目5 に本区別を追記する。

### 3-5. 認証必須エンドポイントの監視方式 🆕（v0.2新設・レビューYEL-02対応）

**前提**: `/api/status` は `Depends(get_current_user)` によりJWT必須である（`api/routes.py` L93-94）。監視主体がどうやって認証を通すかを決める必要がある。

**採用方針：401応答をもって「生存」と判定する** ✅

| 案 | 内容 | 採否 |
|---|---|---|
| **401判定** | 認証情報を持たずにアクセスし、**401が返れば「サーバーは生きている」**と判定する | ✅**採用** |
| 監視用トークン | 監視専用の認証情報を発行して200応答を確認する | ❌不採用 |

**採用根拠**

| # | 理由 |
|---|---|
| 1 | **新たなシークレットを増やさない**。§4-2は「シークレットの管理先が分散」を⚠️として挙げており、監視用トークンはこれをさらに悪化させる |

**401判定の限界**

| 検知できるもの | 検知できないもの |
|---|---|
| サーバープロセスが応答すること | **DB接続の可否**（401はDBに触れずに返る） |
| ネットワーク経路が生きていること | **バッチが動いているか** |

> **限界への対処**: 再設計案では**最も重要な監視対象は「バッチが4時間ごとに走っているか」**である（§3-3）。401判定は補助的な位置づけとし、バッチの監視は別途 改修要件5b で定義する。

## 7. 本調査で得られた教訓

### 7-1. 「測る手段」の前に「何を測れば判断できるか」を確認する

計画書 手順2-A は「**Persistent Disk の実使用量**」を無料化可否の判断材料と位置づけ、その実測手段の確保を最優先項目とした。しかし実際には、**Render無料プランに Persistent Disk が存在しない**ため、容量は判断材料になり得なかった。

| 段階 | 内容 |
|---|---|
| v0.5レビューYEL-01 | 「実測手段が確保されていない」と指摘 → 手順2-Aに「実測手段の確保」を新設 |
| v0.6レビューGRN-02 | 「案(b)は4項目中1項目しか満たせない」と指摘 → 選定順序を明記 |
| **本調査** | **そもそも測る対象の見立てが違っていた** |

> **教訓**: 「観測できるかを先に検証する」（振り返り3-9）の一段手前に、「**何を知れば判断できるかを先に確認する**」工程が要る。手段の議論は、対象が正しいことを前提にしている。
>
> 本件では**低コストな調査（無料プランの仕様確認）を先に行えば、実測手段の議論そのものが不要だった**。

### 7-2. 過去の設計判断が想定外の形で効くことがある

フェーズ2で SQLAlchemy ORM を採用した判断により、`db/crud.py` に生SQLが1件も存在しない。結果として **SQLite → Postgres の移行が `create_engine()` 1行の変更**で済む見通しとなった。

> 当時この判断は「移行可能性」を目的にしたものではなかったが、**選択肢を狭めない設計**が後のフェーズで価値を持った例として記録する。
