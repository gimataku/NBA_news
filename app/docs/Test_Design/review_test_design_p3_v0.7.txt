  ■ 何が誤りだったか

    検証できないものは **1つではなく2つに分かれる**。

      | 対象 | 自動化 | 根拠 |
      |------|-------|------|
      | **Render が実際にどのヘッダを付けるか**（追記か上書きか） | ❌不可 | 外部システムの挙動。実機でしか分からない |
      | **どのヘッダのどの位置を信頼するか**（キーの決め方） | ✅**可能** | 自前のロジック。`TestClient` の `headers=` で与えられる |

    本書 v0.6 までは両者を「実環境依存」として一括し、
    **当方はその一括を「正しい」と書いた**。
    後者を自動化していれば——つまり
    「`X-Forwarded-For: spoof, 実IP, プロキシ` を与えたとき、
    キーは `実IP` になるか」を1本書いていれば——
    **設計段階で `get_remote_address`（先頭を採る）が不適切だと分かった**。

    結果として F8（偽装でレート制限をバイパスできる状態）は
    **本番に入り、2026-10-15 の実測まで検出されなかった**。
    製造検証ログの教訓も同じ点を指している。

      「設計書の確認対象（実装を読む）では見えず、**本番での偽装試験でのみ
        検出できた**（テスト設計書は「手順9の実機確認」に委ねていたが、
        **確認内容が「別回線の影響の有無」だけで、偽装は含まれていなかった**）」

  ■ 当方の観点表の欠落

    観点表§3（深度確認）は「『Xが必要になる』」「『この構成で動く／動かない』」
    「『候補を却下する』」など、**文書が主張していることを一段深く問う**項目を
    並べている。しかし

      **「『自動化できない／検証できない』と書かれている」**

    という形の主張を問う項目が無かった。
    当方はこれを**むしろ評価すべき姿勢**として扱っており、
    疑う対象に入れていなかった。
    「自動化できないものを自動化しない」は正しい規律だが、
    **その判定自体が検証を要する主張である**。

  ■ 観点表への反映

    docs/review_checklist.md §3 に以下を追加した。

      §3-7（新設）「**『自動化できない／検証できない』と書かれている**」
        出す前に確認すること:
        **何が検証できないのかを分解する。**
        ①**外部システムの挙動**（API の応答・プロキシが付けるヘッダ・
          サービスの通知）は実機でしか分からない → 手動確認で正しい
        ②**自前のロジック**（受け取った値をどう解釈するか・どの値を信頼するか）
          は**必ず自動化できる**。入力はテスト側から与えられる
        両者が混ざった主張を「正しい」と是認してはならない。
        とくに**セキュリティに関わる判定ロジック**（信頼の境界）は②に属する。
        （見落とし例：`forwarded_allow_ips`／`X-Forwarded-For` の扱いを
          「`TestClient` では検証できない」として手動確認へ回す判断を
          **2報告書・3箇所で是認**した。実際には
          「Render が何を付けるか」は①だが「どの位置を信頼するか」は②であり、
          後者を自動化していれば設計段階で F8 を検出できた）

            （`spoof{i}, 203.0.113.50, 198.51.100.1`）誤った認証情報で6回」

            **2番目の要素**＝`203.0.113.50` ✅

    【検証】実物の `get_client_ip` を読んだ。

        parts = [p.strip() for p in xff.split(",") if p.strip()]
        if len(parts) >= 2:
            return parts[-2]

      `spoof1, 203.0.113.50, 198.51.100.1` → parts[-2] = `203.0.113.50` ✅
      偽装値を変えても `parts[-2]` は不変 → **同じバケット** ✅

    【結論】**期待値は実装と整合する。指摘なし。**
            K-4（`xff` が1要素のとき `request.client.host` へフォールバック）も
            `len(parts) >= 2` の条件と整合する ✅
