  ■ 観点の欠落

    観点表1-4は「コード引用の行番号と内容を `sed -n 'Np'` で照合」と
    定めている。当方はこれを**引用された行が正しいか**の確認としてのみ
    運用しており、**引用された行が意図どおり効いているか**——
    直前・直後の行によって無効化されていないか——を見ていなかった。

    `os.environ.setdefault` は「まだ設定されていなければ設定する」関数であり、
    **その効果は直前の状態に依存する**。この種の
    「前後関係で意味が変わる行」を引用するときは、
    行だけでなく**その行が実行される時点の状態**を確認しなければならない。

  ■ 観点表への反映

    docs/review_checklist.md に以下を追加した。

      §1-4 の対象拡張 🔧
        コード引用の照合は**行の一致だけで終わらせない**。
        引用された行が **条件つき・冪等・既定値依存**（`setdefault`・
        `os.getenv(k, default)`・`if not X:` 等）である場合は、
        **その行が実行される時点で条件が成立しているか**を、
        同一ファイルの先行行まで読んで確認する。
        （見落とし例：`conftest.py` L19-23 の `setdefault` を4回引用しながら、
          L8-11 の `load_dotenv(override=True)` により無効化されている
          ことに気付かなかった）

  🟡 TD-R-01：T-P3-05（F-21 の回帰テスト）が `main.py` の実設定を読まない。
              DD-01 と同じ型の乖離を検出できない
  ────────────────────────────────────────────────────────────────────────────

  【該当】§2-0 #2／T-P3-05 の「前提」欄／§1-2-2

  【事実】

    T-P3-05 の前提欄:
      「**新設フィクスチャ `cors_client`**（§2-0 #2）。
        **`main.py` と同じミドルウェア設定を持つアプリを組む**」

    §1-2-2 の `main.py` の扱い:
      「**CORS設定（L33-39）は `TestClient` で検証できる**ため
        対象に含める（T-P3-05）」

    実物（`backend/main.py` L33-39）:
      L33  app.add_middleware(
      L34      CORSMiddleware,
      L35      allow_origins=_origins,
      L36      allow_credentials=True,
      L37      allow_methods=["*"],
      L38      allow_headers=["*"],
      L39  )

  【問題1：回帰テストが守りたいものを守らない】

    `cors_client` は「`main.py` と**同じ設定を持つ**アプリを組む」ものであり、
    **`main.py` そのものではない**。したがって

      ・`main.py` の `allow_methods` が `["GET", "POST"]` のまま
      ・フィクスチャの `allow_methods` が `["GET", "POST", "PUT"]`

    という状態でも、**TC-05-3 は通る**。

    これは DD-01 が起きたときの構図そのものである。DD-01 は
    「**設計書に書かれた値と、実際に使われるメソッドが食い違っていた**」
    という欠陥だった。その回帰テストが
    「**テスト側に書いた値と、テスト側に書いた値を比べる**」形になっていると、
    同じ欠陥が再発しても検出できない。

    テスト設計書自身が TC-05-3 を
    「基本設計書 v0.6 の欠陥に対する回帰テストである」と位置づけ、
    「自動テストで固定する価値が高い」と書いている。
    **その価値が、フィクスチャの作り方によって失われる。**

  【問題2：§1-2-2 の根拠が成立しない】

    §1-2-2 は「`main.py` の除外を見直す」判断の根拠として
    「CORS設定（L33-39）は `TestClient` で検証できる」を挙げている。
    しかし `cors_client` が `main.py` を import しないなら、
    **`main.py` L33-39 は1行も実行されない**。
    カバレッジ計測上、`main.py` を対象に含めても
    **CORS の行は 0% のまま**である。

    つまり「F-21 が1行もテストされない状態を回避する」という
    §1-1／§1-2-2 の目的（v0.1 変更履歴②）が達成されない。

  【重要度が🟡である理由】

    テストは書かれるし通る。CORS の**振る舞い**（プリフライトの応答形式・
    `allow_credentials` との組み合わせ）は正しく検証される。
    失われるのは「**本番の設定値と一致しているか**」だけである。
    ただしそれこそが DD-01 の再発防止の要点であり、
    IT-P3-05 も同じ限界を持つ（結合テストも実アプリを使わないなら同じ）。

  【対処案】

    案A（推奨・小）: **CORS の設定値を `config.py` の定数に切り出す**。

        # config.py
        CORS_ALLOW_METHODS = ["GET", "POST", "PUT"]
        CORS_ALLOW_HEADERS = ["Authorization", "Content-Type"]

        # main.py
        allow_methods=CORS_ALLOW_METHODS,
        allow_headers=CORS_ALLOW_HEADERS,

        # conftest.py（cors_client）
        allow_methods=CORS_ALLOW_METHODS,   ← 同じ定数を読む

      → **フィクスチャと本番が同じ値を読む**ため、乖離が原理的に起きない。
        `config.py` はカバレッジ除外のままでよい（定数定義のため）。
        詳細設計書§2-6 は既に `LOGIN_RATE_LIMIT`・`METRICS_WINDOW_DAYS` を
        `config.py` に置いており、**方針が一貫する**。

    案B（中）: `cors_client` を **`main.py` の `app` を import して作る**。

        from main import app
        with TestClient(app) as client: ...

      → 実物を検証できる。ただし
        ・`main.py` の import で `os.makedirs("logs")` が走る
        ・`TestClient` の context 進入で `startup_event()` が走り、
          **`scheduler.start()` と `check_and_run_batch()` が実行される**
        という副作用がある。
        後者は **`ENABLE_SCHEDULER=false` を設定すれば止まる**
        （詳細設計書§2-4-3）。つまり案Bは
        **T-P3-16（`ENABLE_SCHEDULER` の分岐）と同じ仕掛けを使う**。
        ただし §2-4-3 の実装は要望1採用時に適用される扱い（§6）であり、
        **採否が決まるまで案Bは使えない**。

    案C: 案Aと案Bの併用。定数化で乖離を防ぎつつ、
         要望1採用後に案Bへ移行する。

    → **案Aを推奨する**。要望1の採否に依存せず、追加コストが小さく、
      詳細設計書§2-6 の既存方針と一貫する。
      なお案Aを採る場合、**詳細設計書§2-4-1／§2-6 の改訂**が必要になる
      （テスト設計側の都合で本番コードの構造を決めることになるため、
      §9 の引き継ぎに「詳細設計書へ差し戻し」として明記すること）。

  🟢 TD-R-05：外部パッケージの版番号に確認日がなく、既に版が変わっている
  ────────────────────────────────────────────────────────────────────────────

  【該当】§1-3 のテスト基盤の表／§8-1 の「外部パッケージの互換性」

  【事実】本書は次を**コマンドで確認した事実**として記載している。

    「$ npm view vitest version peerDependencies
        version = '4.1.11'
        peerDependencies.vite = '^6.0.0 || ^7.0.0 || ^8.0.0'」

    当方が **2026-09-06 に再実行**した結果:

      $ npm view vitest version
        **5.0.0**
      $ npm view vitest peerDependencies
        vite: '^6.4.0 || ^7.0.0 || ^8.0.0'
        '@types/node': '^22.0.0 || >=24.0.0'

      $ npm view @testing-library/react version peerDependencies
        version = '16.3.3'
        react: '^18.0.0 || ^19.0.0'      ← **変化なし**

    本プロジェクト（`frontend/package.json`）:
      vite `^8.0.12` / react `^19.2.6` / engines.node `>=22.0.0`

  【判定】

    ・**互換性の結論は変わらない**。vitest 5.0.0 の peer は
      `vite ^6.4.0 || ^7.0.0 || ^8.0.0` であり、vite ^8.0.12 は対応内。
      `@types/node` の要求（`^22 || >=24`）も engines と整合する。
      → **案Bの採用判断は覆らない。**

    ・ただし本書は **`4.1.11` という具体的な版を本文に固定**している。
      §1-3 は「`@vitest/coverage-v8` は `vitest` と**同一バージョンに揃える**
      （peer が `4.1.11` 固定）」と書いており、
      手順7で `npm install -D vitest` を実行すると **5.x が入る**。
      「4.1.11 に揃える」と読むと**意図せず旧版を固定する**ことになり、
      「最新に揃える」と読むと**本文と食い違う**。

    ・観点表4-2（確認日の明記）・4-3（変動可能性の判定）に照らすと、
      **確認日のない版番号は、書いた瞬間から古くなる**。
      計画書§8-0-1「古くなる書き方の排除」が扱っている類型である。

  【対処案】

    案A（推奨）: 版番号に**確認日を添え**、運用は版非依存の書き方にする。

      | テストランナー | `vitest`（**2026-09-01時点 4.1.11 / 2026-09-06時点 5.0.0**） |
      | カバレッジ | `@vitest/coverage-v8`。**`vitest` と同一のメジャー・マイナーに揃える** |
      |            | （`npm i -D vitest @vitest/coverage-v8` を**同時に実行する**）|

      → 「同一バージョンに揃える」という**運用**が本質であり、
        その時点の版が何であるかは本質ではない。

    案B        : 導入時に版を固定し、`package.json` に書いた値を正とする。
                 本書からは版番号を落とす。

  ■ 3-1. §2-0 #3 の `limiter.reset()` は実在するか

    【疑義】`slowapi` は `requirements.txt` に未導入である。
            `Limiter.reset()` が存在しなければ、

    【検証】サンドボックスに `slowapi` を導入して確認した（2026-09-06）。

        >>> hasattr(Limiter, 'reset')
        True
        >>> inspect.getsource(Limiter.reset)
        def reset(self) -> None:
            """resets the storage if it supports being reset"""
            try:
                self._storage.reset()
                self.logger.info("Storage has been reset and all limits cleared")
            except NotImplementedError:

    【結論】**実在する。既定のインメモリストレージは `reset()` に対応する。
            §2-0 #3 の設計は成立する。指摘なし。**

            **`reset()` が黙って何もしない可能性がある**。

            当面は問題ない。

  ■ 3-2. §6-4「テストDBは SQLite 維持」の受け入れリスク③

    【該当】「③**`connect_args` の可否**」を「移行時に1回だけ現れる差異」と
            している。

            **無条件に削除**しつつ、既定値を `sqlite:///nba_news.db` に
            している。これがローカル実行を壊すなら、
            「移行時に1回だけ」では済まない。

            SQLAlchemy 2.0.52 で確認した。

              >>> e.dialect.create_connect_args(e.url)
              (['/tmp/t2.db'], {'check_same_thread': False})   ← 自動付与

            → **SQLAlchemy 2.0 は file-based SQLite に対し
              `check_same_thread=False` を自動的に付ける**。
              削除しても挙動は変わらない。

            （`connect_args={"check_same_thread": False}` を明示）、
            `models.SessionLocal` を差し替えているため、
            そもそも `models.py` の変更の影響を受けない。

            `conftest.py` がテスト用エンジンを自前で持つ構造のおかげで、
            要望1採用時も**テスト側は無改修で済む**。
            §6-4 が「SQLite 維持」を採用した根拠として、
            この点を1行足すとより強くなる（任意）。
