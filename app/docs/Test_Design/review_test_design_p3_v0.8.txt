2. 本版の指摘
--------------------------------------------------------------------------------

  ────────────────────────────────────────────────────────────────────────────
  🟡 TD8-01：本番の設定（`render.yaml` のキー名）を検証する手段が無い。
             SEC-1 の発見事項③はテストでは検出できなかった
  ────────────────────────────────────────────────────────────────────────────

  【該当】T-P3-16（`ENABLE_SCHEDULER` の分岐）／§1-2-1（改修部分の定義）／
          §8-2（B：判断）

  【事実】

    製造検証ログ 2026-10-29 の発見事項③：

      「③`render.yaml` のキー名が **`ENABALE_SCHEDULER`（誤字）**だった
        → `ENABLE_SCHEDULER` に修正」

    T-P3-16 の6ケースを確認した。

      | TC-16-1 | 未設定 | 既定 true・`scheduler.start()` と `check_and_run_batch()` が呼ばれる |
      | TC-16-2 | `"false"` | どちらも呼ばれない |
      | TC-16-3 | `"False"` / `"FALSE"` | 同上（`.lower()` が効いている） |
      | TC-16-4 | `"true"` / `"1"` / 空文字 | true 扱い（`!= "false"` の判定） |
      | TC-16-5 | `"false"` で起動 → シャットダウン | `SchedulerNotRunningError` が出ない |
      | TC-16-6 | `"false"` で起動 | `init_db()` と `init_user()` は呼ばれる |

    **6ケースすべてが `ENABLE_SCHEDULER` という正しいキー名を前提に
    値を変えている。** キー名そのものは検証対象になっていない。

  【問題：この設定は「誤記が有効側に倒れる」】

    実装は

      `os.getenv("ENABLE_SCHEDULER", "true").lower() != "false"`

    であり、**未設定なら `true`**（詳細設計書§2-4-3・基本設計書§5-3）。
    したがって

      ・キー名が正しい ＋ 値が `false` → 止まる（設計どおり）
      ・**キー名が誤っている** → 未設定扱い → **`true` → 動く**

    つまり**誤記は「安全側」ではなく「有効側」に倒れる**。
    しかも**動いても例外は出ず、ログにも何も残らない**
    （`logger.info("Scheduler started")` が出るだけで、
    それは正常時の出力と区別できない）。

    **TC-16-1 が「未設定なら true」を正常系として固定している**ため、
    テストは「未設定＝正しい挙動」と保証しており、
    **キー名の誤記で未設定になった状態も「正しい」と判定してしまう。**

  【なぜ 🟡 か】

    本書の既存記述に誤りはない。T-P3-16 はアプリのロジックを
    正しく検証しており、6ケースの設計も妥当である。
    欠けているのは**設定の検証**という守備範囲である。

    一方で実害は出ている（約1か月、本番で意図しない状態が継続）。
    そして **当方が v0.3 で立てた観点（本番の値を読む）の横展開漏れ**でもある。

  【対処案】

    案A（推奨）: **T-P3-16 に TC-16-7 を追加する**——`render.yaml` を読み、
                 **キー名と値を検証する**。

      ```python
      def test_tc_p3_16_7_render_yaml_disables_scheduler():
          """本番（render.yaml）で ENABLE_SCHEDULER=false が設定されていること。
          キー名の誤記は os.getenv の既定 "true" に倒れ、スケジューラが
          動いてしまう（SEC-1 発見事項③）。ロジックのテストでは検出できない。
          """
          import yaml, pathlib
          p = pathlib.Path(__file__).resolve().parents[3] / "render.yaml"
          spec = yaml.safe_load(p.read_text(encoding="utf-8"))
          envs = {e["key"]: e.get("value")
                  for s in spec["services"] for e in s.get("envVars", [])}
          assert "ENABLE_SCHEDULER" in envs, \
              "render.yaml に ENABLE_SCHEDULER が無い（誤記の可能性）"
          assert str(envs["ENABLE_SCHEDULER"]).lower() == "false"
      ```

      **注意点**

      | # | 内容 |
      |---|------|
      | 1 | `render.yaml` は**リポジトリルート**にあり、`app/backend/tests/` から見て `parents[3]`。**パスの段数を実測で確認する**（`parents[2]` だと `app/` に着く） |
      | 2 | `pyyaml` が `requirements.txt` に無い。**`apscheduler` が依存として持っている可能性があるが、暗黙依存に頼らない**。追加するなら §2-7 に明記する。または**正規表現で `ENABLE_SCHEDULER` の行を探す**だけでも誤記は検出できる（YAML パースを避けられる） |
      | 3 | **値の検証より名前の存在検証が本質**である。誤記は「名前が無い」として現れる |
      | 4 | 同じ形で **`PYTHON_VERSION: 3.11.18`**（SEC-1）も検証できる。`HOST`・`ALLOWED_ORIGINS` も対象になりうる |
      | 5 | **シークレット6件は `sync: false` で値を持たない。値をアサートしてはならない**（キーの存在と `sync: false` のみ） |

    案B        : テストではなく**週次チェックリスト**で目視する。
                 → 7-B の改訂（基本設計書§8 #7）に1項目足すだけで済む。
                   ただし **目視は忘れる**。フェーズ2振り返り3-9 が
                   「機能していない監視を惰性で継続した」ことを問題視した
                   のと同じ構図になりうる

    案C        : `main.py` 側で**起動時に警告を出す**——`ENABLE_SCHEDULER` が
                 未設定のとき `logger.warning("ENABLE_SCHEDULER unset; "
                 "scheduler ENABLED (local default)")` を出す。
                 → 誤記が**ログで見える**ようになる。本番では未設定が
                   異常なのだから、警告として正しい。
                   **案Aと併用すると強い**（テストで防ぎ、ログで気付く）

    → **案A＋案C を推奨する。** 案Aだけでは `render.yaml` を直接編集した
      場合（Blueprint の性質上ありうる）に push 前のテストを通らずに
      本番へ入る経路が残る。案Cはその最後の砦になる。

      なお **案Aは詳細設計書§3-6 の新設（DD6-02 の対処）を前提にする**。
      設計書に「`render.yaml` の設定表」が無いと、テストが何を正として
      検証するのかが決まらない。**DD6-02 → TD8-01 の順で処理する。**

  【あわせて：§1-2-1 の「改修部分」について】

    §1-2-1 は Python／JavaScript の改修ファイルを列挙する。
    `render.yaml`・`batch.yml` は**カバレッジの対象ではない**ため
    ここに載せる必要はない。ただし

      「**カバレッジでは測れないが、変更が本番の挙動を決めるファイル**」

    という区分が本書に無い。`render.yaml`・`batch.yml`・

    （TC-16-7／`Show versions`／手動確認）を1行ずつ書くと、
    守備範囲の空白が見えるようになる（任意）。
