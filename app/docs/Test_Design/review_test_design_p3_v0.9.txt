  ────────────────────────────────────────────────────────────────────────────
  🟢 TD9-01：TC-16-7b・7c の判定条件が、注意点#2（`re` で読む）と
             両立しないか、厳密には成り立たない
  ────────────────────────────────────────────────────────────────────────────

  【該当】§6-2 の TC-16-7b・TC-16-7c

  ■ (1) TC-16-7b：「`3.11.18` **以上**」が `re` では素直に書けない

    【記述】

      | 🆕 TC-16-7b | 同上 | **`PYTHON_VERSION` が存在し、
        値が `3.11.18` 以上**（SEC-1。詳細設計書§3-6） |

    【問題】注意点#2 は「**`pyyaml` を使わない**…`re` で読む
            （YAML パース不要・**新しい依存なし**）」と定めている。
            `re` で取り出せるのは**文字列**である。

            版の大小比較を文字列でやると**辞書順**になる。

              `"3.11.9" > "3.11.18"` → **True**（`9` > `1`）

            つまり **3.11.9 が「3.11.18 以上」と判定される**。
            正しく比較するには

              ・`packaging.version.Version`（**`requirements.txt` に無い**。
                pip の依存として入るが、注意点#2 が禁じた「暗黙依存」である）
              ・または `tuple(int(x) for x in v.split("."))` による自前比較

            が要る。後者なら依存は増えないが、
            **注意点に書かれていないため実装者が迷う**。

    【さらに：そもそも「以上」が必要か】

      詳細設計書§3-6 は `PYTHON_VERSION` を **`3.11.18`（固定値）**と
      定めている。CLAUDE.md も「`render.yaml` の `PYTHON_VERSION: 3.11.18`」と
      固定値である。**設計が固定値なら、テストは完全一致で足りる。**

      「以上」にすると、**設計が `3.11.18` のままで値だけ上げても
      テストが通る**——つまり**設計と設定の乖離を許す**ことになり、
      TC-16-7 の目的（設計どおりに設定されているかを見る）と逆を向く。

    【対処案】

      案A（推奨）: **`3.11.18` と完全一致**にする。
                   版を上げるときは**設計書§3-6 とテストを同時に直す**
                   （＝設計と設定が常に一致する）。
                   注意点に「**固定値なので完全一致で見る。
                   版を上げるときは §3-6 と本ケースを同時に更新する**」を
                   1行添える。

      案B        : 「以上」を残すなら、注意点に
                   **`tuple(int(x) for x in v.split("."))` で比較する**と
                   明記する（`packaging` を増やさない）。
                   ただし上記の「乖離を許す」問題は残る。

      → **案Aを推奨する。** 詳細設計書レビュー§6 で指摘した
        「**固定した版をいつ見直すか**」の論点とも整合する——
        完全一致にしておけば、**版を上げる作業が必ず設計書に触る**。

  ■ (2) TC-16-7c：「値が無いこと＝`sync: false` の行があること」が
       厳密には成り立たない

    【記述】

      注意点#4：「シークレットの値をアサートしない（TC-16-7c は
        `sync: false` とキーの存在のみ）。**ファイルに値が書かれていた
        場合は失敗させる（値が無いこと＝`sync: false` の行があること）**」

    【問題】**`sync: false` があることと、`value:` が無いことは別**である。

      ```yaml
        - key: SECRET_KEY
          sync: false
          value: "..."        # ← これがあっても sync: false は存在する
      ```

      上の形を**このテストは検出できない**（`sync: false` の行はある）。
      Render の Blueprint 仕様で併記が許されるかは当方では確認できないが、
      **テストの目的は「値が書かれていないこと」の保証**であり、
      `sync: false` の存在はその**必要条件にすぎない**。

      しかもこれは**最も事故ってはいけない項目**である——
      シークレットの値が `render.yaml` に書かれれば、
      **Git に入り、コミット履歴に残る**。

    【対処】判定を2条件にする。

      各シークレットのブロックについて
        ① `sync: false` の行が**ある**
        ② `value:` の行が**無い**

      を**両方**確認する。注意点#4 を次に差し替える。

        「シークレットの値をアサートしない。**①`sync: false` がある
          かつ ②`value:` が無い**の2条件を見る（`sync: false` の存在だけでは
          『値が書かれていない』の証明にならない）。
          **万一 `value:` が見つかっても、その値をエラーメッセージに
          出力しない**（キー名だけを出す）」

      最後の1文は当方からの追加である。**テストが落ちたときに
      値が CI のログへ出る**のでは本末転倒になる。

  【重要度が🟢である理由】

    TC-16-7 は**未実装**（§0-4 が ⬜・手順8）であり、
    **実装前に直せば実害はない**。(1) は実装者が気付く可能性が高く、
    (2) は気付かないまま通る可能性があるが、
    **現状 `render.yaml` に値は書かれていない**（詳細設計書§3-6 で確認）ため
    いま壊れているわけではない。

  ────────────────────────────────────────────────────────────────────────────
  🟢 TD9-02：`autoDeploy` も「未指定が安全側でない」が、
             TC-16-7 の対象に入っていない
  ────────────────────────────────────────────────────────────────────────────

  【該当】§6-2 の TC-16-7・7b・7c の対象範囲

  【事実】

    TC-16-7 系が見るのは3つである。

      | TC-16-7  | `ENABLE_SCHEDULER` | 未設定＝有効側に倒れる |
      | TC-16-7b | `PYTHON_VERSION` | SEC-1 の基準 |
      | TC-16-7c | シークレット6件 | `sync: false` |

    一方、詳細設計書§3-6 は「その他の固定値」として
    `buildCommand`／`startCommand`／`healthCheckPath`／`plan` と並べ、
    **`autoDeploy` は指定していない（既定の On）**と記している。

    CLAUDE.md は `autoDeploy` について 🔴 で警告している。

      「🔴 **Blueprint sync はダッシュボードの値を `render.yaml` の内容で
        上書きする**（プレースホルダが残ると正しい値が壊れる／
        **`autoDeploy` 未指定は既定の On に戻りうる**）」

    **これは `ENABLE_SCHEDULER` と同じ型である**——未指定が「On」に倒れ、
    しかも**無言で**そうなる。

  【なぜ問題になりうるか】

    現状 Auto-Deploy は On でよい（CLAUDE.md が「On（On Commit）」と明記）。
    したがって**いま実害は無い**。

    ただし **Off にする運用が設計に存在する**。
    リスク調査書§1-4-9 の移行手順は「**案B：Auto-Deploy 一時停止**」を
    採っており、基本設計書§5-6 がそれを参照している。
    つまり

      ・移行や緊急対応で Auto-Deploy を Off にする
      ・その後 `render.yaml` を編集して Blueprint sync が走る
      ・**未指定なので On に戻る**
      ・**気付かないまま push がデプロイを起こす**

    という経路がある。SEC-1 では実際に `render.yaml` を編集しており、
    同種の作業は今後も起こる。

    なお `buildCommand`・`startCommand`・`healthCheckPath` は性質が違う——
    **壊れればデプロイが失敗する**ので無言では進まない。
    検証対象に加える価値は `autoDeploy` ほど高くない。

  【対処案】

    案A（推奨）: **TC-16-7d を追加**し、`autoDeploy` の**現在の方針が
                 ファイルに書かれていること**を確認する。
                 いま On でよいなら、**`autoDeploy: true` を明示的に
                 書いたうえで**テストで固定する（未指定のままにしない）。
                 → 「未指定＝既定に倒れる」項目を**1つ減らす**。
                   詳細設計書§3-6 への追記（`autoDeploy` を
                   「その他の固定値」から設定表へ移す）が前提。

    案B        : テストは足さず、**週次チェックリスト**（§9-1 #23）の
                 ダッシュボード確認に `autoDeploy` を加える。
                 → 目視に頼る。#23 は既にダッシュボード項目を持つので
                   追加コストは小さい。

    案C        : 何もしない（現状 On が正しく、変える予定もない）。
                 → **移行手順が Off を使う**以上、いつか踏む。

    → **案A か案B。** 当方は**案B（週次チェックリストに加える）で足りる**と
      考える。理由は、`autoDeploy` を Off にするのは**人が意図して行う
      一時的な操作**であり、そのとき人は Render のダッシュボードを見ている。
      `ENABLE_SCHEDULER`（設定して以後ずっと放置される）とは
      **忘却の起きやすさが違う**。
      ただし**どちらにするかを決めて記録する**ことは必要である。
