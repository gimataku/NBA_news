## 1. プロジェクト概要

### 1-1. フェーズ3の目的

フェーズ2で本運用に移行したNBAニュース翻訳アプリに対し、以下を実施する。

1. **運用基盤の整備**：フェーズ2の振り返りで判明した運用面の穴（可観測性・監視・セキュリティ指摘の未対応）を塞ぐ
2. **コスト最適化**：Render有料プラン（$7.25/月）から無料環境への移行可否をリスク評価の上で判断する
3. **機能改修**：ユーザー要望（要望整理.txt）に基づくUI・機能改善
4. **プロセス改善**：フェーズ2振り返りの改善策をプロセスに組み込む

> **テーマ設定の根拠（振り返り§4-3より）**: フェーズ2で機能面は要件を満たし切った（トレーサビリティ全項目✅）一方、運用面には複数の穴が残っている。**機能を足す前に、いま動いているものを確実に見られる状態にする**方が投資効率が高い。よってフェーズ3は運用基盤を最優先とし、機能改修はその後に着手する。

#### 目的間の優先順位 🆕（YEL-04対応）

目的が競合した場合、以下の順位で判断する。

```
安全性（法的前提の担保） ＞ 運用可観測性 ＞ コスト ＞ 機能
```

| 順位 | 判断軸 | 具体的な意味 |
|---|---|---|
| 1 | **安全性** | JWT認証の維持は絶対条件。無料化・機能追加のいずれもこれを犠牲にしてはならない |
| 2 | **運用可観測性** | 「動いているものが見える状態」を機能追加より優先する（本フェーズのテーマ） |
| 3 | **コスト** | 無料化は望ましいが、上位2つと両立しない場合は現行プランを維持する |
| 4 | **機能** | 上位3つを満たした残りのリソースで実施する |

> **本順位が必要な理由**: 目的2（無料化）と要望4（関連ニュース表示・Claude API利用の可能性）は**正面から競合する**。無料枠に収める制約下で新規API呼び出しを増やす構図であり、両立しない場合は上表に従い機能側を削る。手順2-Bのコスト試算は「**移行後の無料枠の中で成立するか**」という観点で行うこと。

#### 継続事項#1の詳細：ネタバレ判定UIの検証と要望2の衝突 🆕（RED-01対応）

**問題の構造**

実装を確認したところ、`SpoilerOverlay` は `has_score=true` のとき `summary_ja` 全体をぼかしプレースホルダに置換する方式で、`NewsCard.jsx` の**summary表示領域そのもの**に描画されている（`NewsCard.jsx` L56・L67・L76・L81-86）。

一方、改修要件2（ニュースをタイトルのみ表示し、クリックで本文展開）は**同一の領域を改修対象とする**。これにより2つの問題が生じる。

| # | 問題 | 内容 |
|---|---|---|
| 1 | **検証対象が改修で消滅する** | フェーズ3の手順10は製造（手順7）の後。「フェーズ2のネタバレUIを開幕後に確認する」という承認条件（Takumi様2026-06-28承認）が、**改修後のUIでしか実施できなくなる**。フェーズ2の受け入れ条件が本人の再承認なくフェーズ3の条件にすり替わる |
| 2 | **隠蔽機構の二重化** | 「デフォルト非表示（タイトルのみ）」と「ネタバレ防止のぼかし」が重なる。ユーザーはクリック展開 → さらに「スコアを表示」を押す**二段操作**になるか、あるいはネタバレ防止機能が要望2に吸収されて役割を失う。**F-05／F-05bの存続可否**という要件レベルの論点 |

**対応方針：案Aを採用する**

| 案 | 内容 | 採否 |
|---|---|---|
| **案A** | **要望2の製造着手前に、開幕直後の現行UIでSection Cを2週分実施してフェーズ2を正式クローズする** | ✅**採用** |
| 案B | フェーズ2の承認条件を「改修後UIでの確認」に読み替え、Takumi様の再承認を得る | ❌不採用 |

**案Aを採用する根拠**: 承認条件の事後的な読み替えは、フェーズ2振り返り3-7（レビュー指摘が追跡されず放置される）と同型の劣化を招く。**「検証していないものを、検証しないまま改修する」ことを避ける**方が原則として健全である。加えて、Section Cの実施は開幕直後の2週間で完了し、フェーズ3の手順1〜6（設計工程）と並走できるため、**日程上のコストがほぼ発生しない**。

**制約事項**

- 要望2（および `NewsCard.jsx` のsummary領域に触れる全ての改修）の**製造着手は、フェーズ2 Section C のクローズ後**とする
- 手順7のサブ手順設計時に、この依存関係を実装順序に反映すること
- Section Cが2週分で合格しなかった場合、フェーズ2の残課題対応が要望2に優先する

## 2. ガイドライン

| 区分 | 内容 |
|---|---|
| 法的制約 | スクレイピング禁止。RSSまたは公式APIのみ使用 |
| 著作権・公開範囲制約 | 公開範囲は著作権法第30条の私的利用範囲に収める。JWT認証は**セキュリティ目的ではなく著作権法遵守が主目的**であることを設計判断の前提とする |

| **運用成果物の定義（振り返り§6-1・新規）** | 監視ツール・運用手順書・ステータスAPI・チェックリスト設計を**成果物として§5に登録**し、レビュー・変更追従の対象に含める。要件定義（手順1）の段階で運用時に見たい指標を洗い出す |
| **インフラ変更の断絶（フェーズ2から継承）** | 要望1（無料環境移行）はホスティング基盤を変更する。基本設計では「フェーズ2との差分設計」として独立セクションを設け、**運用手順・監視ツールも差分レビューの対象に含める**（振り返り3-3対応） |
| 可観測性 | 「運用時に見たい指標」を要件定義の段階で定義し、専用エンドポイントとして設計に組み込む。**取得手段（API）と記録欄（チェックリスト）はセットで設計する**（振り返り3-4・3-8対応） |

> **注記（項目5の根拠）：** フェーズ2では項目4を「ルールとして明文化」した後も同種の追従漏れが2件再発した（`retrospective_p2_v1.1.md` R-4・§4-0）。しかも初回のgrep実行で、レビューが検出できていなかった2件目が発見された。**「確認した」ではなく「grepの出力を貼る」ところまでを完了条件とする。**

### 8-1. grep結果の判定基準 🆕

grepのヒットは**すべてが修正対象ではない**。以下の3分類で判定すること。

| 分類 | 内容 | 対応 |
|---|---|---|
| **🔧 追従対象** | 現行の生きているドキュメントが旧バージョンを参照している | **修正する** |
| **📌 実施記録** | 日付付きの実施記録・検証記録（週次チェックリストの各回等）。作成時点で正しかった参照 | **修正しない**。改変は記録の改竄にあたる |
| **📖 履歴的記述** | 変更履歴・注記内の過去バージョン名の記録、grep証跡の引用 | **修正しない** |

> **判定の根拠：** 実施記録は「その時点で何を参照して判断したか」を示す証拠であり、事後に書き換えると監査可能性を失う。一方で生きているドキュメントの参照は常に最新を指すべきである。この区別を明示せずgrepを機械適用すると、記録を壊す方向のミスが起こりうる。
