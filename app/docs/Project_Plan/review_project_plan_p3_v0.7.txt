  対象箇所: §1-2 L186（見出し）／L179・L180・L212・L985・L995・L996・L1008（参照）

  現状:
    §1-2 の継続事項表は #1〜#7 で構成されている。

      #1 ネタバレ判定UIの未検証
      #2 セキュリティ指摘の未対応
      #3 死活監視が機能していない
      **#4 可観測性の不足**（`/api/status` が2項目しか返さない）

      「**#### 継続事項#4：工程外の先行対応（共通ルール）**」
    であり、**表の #4（可観測性の不足）と番号が衝突している**。

  問題:
    (1) 参照が誤った先を指す
        L179「実施ルールは**継続事項#4**を参照」、L212、L985 などが
        「継続事項#4」と書いているが、読み手が §1-2 の表を引くと
        「可観測性の不足」に行き当たる。
        既存の #1〜#3 は「継続事項#Nの詳細」という形で表の行に対応しているため、
        同じ命名規則で #4 と書かれれば表の #4 を指すと解釈されるのが自然である。

    (2) **番号衝突が既に証跡の誤りを生んでいる**
        付録A-7 (c)「§1-2継続事項の対応欄 → 実体」の検証表は次の5行から成る。

          #2 セキュリティ要否判断      ✅（実在）
          #3 死活監視の再設計          ✅（実在）
          **#4 工程外の先行対応**       ← **継続事項表に存在しない行**
          #6 フェールオーバー実績      ✅（実在）
          #7 Disk実使用量              ✅（実在）

        実在する **#4（可観測性の不足 → 改修要件5で拡張）は検証されていない**。
        つまり (c) は、存在しない項目を検証し、存在する項目を飛ばしている。

    (3) (c) の網羅性が §8項目6 の定義を満たしていない
        §8項目6 は「宣言箇所（§1-2・§4・§7）の**各項目**について」突き合わせると
        定めている。(a) は §4管理表の全13項目、(b) は §7の全8行を扱っているのに対し、
        (c) は7行中4行（＋幻の1行）しか扱っていない。
        欠落しているのは #1（ネタバレ判定UI）・#4（可観測性）・#5（選手名表記ゆれ）で、
        いずれも実体は特定できる。

          #1 → §1-2継続事項#1の詳細 ＋ 手順7 L432（例外適用）
          #4 → 手順1 L312「改修要件5a：監視『項目』の定義」
          #5 → 手順1 L316「選手名表記ゆれの対応要否判断」

    ・見出しを番号から外す。本ブロックは継続事項表の1行ではなく、
      #2 と #3 の両方から参照される**共通ルール**である。例：
        「**#### 共通ルール：工程外の先行対応**（継続事項#2・#3から参照）」
      参照側も「§1-2『共通ルール：工程外の先行対応』」と書く。
    ・付録A-7 (c) から「#4 工程外の先行対応」の行を外し、

      (a)(b) は全項目を扱えているため、対象範囲の書き方だけの問題である。

    参照が曖昧になった件）と同じ型である。当時は「番号を振り直す」ことで解消したが、
    今回は逆に「番号を振らない」ことが解になる。
    共通ルールは表の行ではないため、行番号を持たせない方が構造に合う。

[YEL-03] 新設した適用基準を先-1・先-2に当てはめた検証記録がなく、先-2は基準2に抵触する疑いがある

  対象箇所: §1-2「適用基準」L197-207 ／ 対象一覧 L192-195

  現状:
    v0.7 は適用基準を3項目に再定義し、「以下を**すべて**満たすものに限る」と定めた。

      1 変更範囲が局所的で、ロールバックが単一操作で完結する
      2 **フェーズ3の設計判断（手順2〜6の結論）に依存しない**
      3 放置による実害が明確にある

    しかし対象一覧（先-1・先-2）には「由来」「変更の種類」「ベースラインの更新先」の
    3列しかなく、**各対象が3基準を満たすかの判定が記録されていない**。
    基準を新設した版で、その基準を既存2件に適用した形跡がない。

  問題（先-2 と基準2）:
    先-2 は「**Render標準の**Health Check通知を有効化」である。
    一方、改修要件1（無料環境移行）は Render からの移設も選択肢に含み、
    手順2-A の調査項目には「代替候補の調査（Fly.io・Railway・Vercel＋外部DB等）」が
    挙がっている。

    移行先が Render 以外になった場合、**先-2 で入れた設定は移行とともに失われる**。
    つまり先-2 は、手順2〜6の結論（要望1の可否・移行先）に**依存している**。
    基準2「フェーズ3の設計判断に依存しない」を厳密に読めば、
    先-2 は先行対応の対象から外れることになる。

    なお `render.yaml` には既に `healthCheckPath: /healthz` が設定されており、
    Health Check 自体はフェーズ2から有効である。先-2 が追加するのは
    「通知」の設定であり、この点も対象一覧からは読み取れない。

  推奨対応:
    次のいずれかを選び、対象一覧に判定を記録する。

      案A：**基準2に但し書きを添える**
           「ただし、失われた場合の損失が小さく（設定作業のみ・数分で再設定可能）、
             それまでの期間に実害を防ぐ効果があるものは、依存があっても許容する」
           先-2 はこれに該当する。9月〜移行までの期間、
           到達可能な通知を確保する効果は実際に得られる。
           §1-1の優先順位（安全性＞可観測性＞コスト＞機能）とも整合する。

      案B：**先-2 を先行対応から外し、手順2-C の結論を待つ**
           基準を厳密に運用する立場。ただし「毎回⚠️が記録される監視」が
           10月以降まで続くことになり、基準3（放置による実害）と衝突する。

    案Aを推奨する。基準は判断を助けるためのものであり、
    2件目を評価できずに弾いてしまうなら、基準の側を調整する方が実態に合う。
    いずれにせよ**判定を記録に残す**ことが要点である。
    対象一覧に「基準1／2／3」の3列を足し、○と但し書きを書けば足りる。

  補足:
    先-2 の「変更の種類：設定変更のみ」も、
    どのプラットフォームの何の設定かまでは書かれていない。
    移行時に引き継ぎが必要な設定であることを明示しておくと、
    手順2-Aで移行先を比較する際の評価軸（通知機能の有無）にもなる。

[GRN-03] 検証ルールB の「一定期間」が未定義

  検証ルールB（設定変更のみの場合）の第4項:
    「[ ] **意図しない頻度で通知が飛ばないこと**を一定期間観測して確認する」

  「一定期間」が定義されていないため、いつ完了と判定するかが決まらない。
  先-2 の期限は「2026年9月まで」であり、9月中に有効化してから観測する場合、
  観測期間が期限を超える可能性もある。

  これはフェーズ2振り返り3-5（合格条件が「読了に支障がないレベル」という
  定性表現だったため判定が主観に依存した）と同じ型にあたる。

  → 期間を数値で定める（例：「有効化後**7日間**」）。
    あわせて「観測値欄に受信した通知の件数と内訳を記録する」と書けば、
    §4項目5（合否欄＋観測値欄）の方針とも揃う。
    9月中の有効化を前提とするなら、実施時期を「9月上旬」と具体化しておくと
    観測期間が期限内に収まる。


[GRN-04] 🆕 の扱いが §4 と他の表で不統一になった

  GRN-04（v0.6レビュー）への対応として §4 から🆕を全除去し
  「本表では🆕を使わない」と注記した（L555）。判断は妥当である。

  一方、§1-2継続事項表（#6・#7）・§5-2運用成果物表・§7リスク表には
  🆕 が残っている。いずれも「版を重ねると古くなる印」という
  §8-0-1 の排除対象と同じ性質を持つ。

  結果として、文書内で🆕の意味が場所によって異なる状態になっている。
    §4      ：使わない（由来列で判別）
    §1-2/§5-2/§7：残っている（いつ付いたかは変更履歴を追う必要がある）

  → §4 と同じ整理を他表にも広げるか、逆に「🆕は直近1版で追加された行に付し、
    次版で外す」という運用を明文化するかのいずれかに統一する。
    前者を推奨する。§1-2・§5-2・§7 の各行も、対応表と変更履歴から
    追加時期を追えるため、🆕がなくても情報は失われない。
