## 1. プロジェクト概要

### 1-1. フェーズ3の目的

フェーズ2で本運用に移行したNBAニュース翻訳アプリに対し、以下を実施する。

1. **運用基盤の整備**：フェーズ2の振り返りで判明した運用面の穴（可観測性・監視・セキュリティ指摘の未対応）を塞ぐ
2. **コスト最適化**：Render有料プラン（$7.25/月）から無料環境への移行可否をリスク評価の上で判断する
3. **機能改修**：ユーザー要望（要望整理.txt）に基づくUI・機能改善
4. **プロセス改善**：フェーズ2振り返りの改善策をプロセスに組み込む

> **テーマ設定の根拠（振り返り§4-3より）**: フェーズ2で機能面は要件を満たし切った（トレーサビリティ全項目✅）一方、運用面には複数の穴が残っている。**機能を足す前に、いま動いているものを確実に見られる状態にする**方が投資効率が高い。よってフェーズ3は運用基盤を最優先とし、機能改修はその後に着手する。

#### 目的間の優先順位 🆕（YEL-04対応）

目的が競合した場合、以下の順位で判断する。

```
安全性（法的前提の担保） ＞ 運用可観測性 ＞ コスト ＞ 機能
```

| 順位 | 判断軸 | 具体的な意味 |
|---|---|---|
| 1 | **安全性** | JWT認証の維持は絶対条件。無料化・機能追加のいずれもこれを犠牲にしてはならない |
| 2 | **運用可観測性** | 「動いているものが見える状態」を機能追加より優先する（本フェーズのテーマ） |
| 3 | **コスト** | 無料化は望ましいが、上位2つと両立しない場合は現行プランを維持する |
| 4 | **機能** | 上位3つを満たした残りのリソースで実施する |

> **本順位が必要な理由**: 目的2（無料化）と要望4（関連ニュース表示・Claude API利用の可能性）は**正面から競合する**。無料枠に収める制約下で新規API呼び出しを増やす構図であり、両立しない場合は上表に従い機能側を削る。手順2-Bのコスト試算は「**移行後の無料枠の中で成立するか**」という観点で行うこと。

#### 継続事項#1の詳細：ネタバレ判定UIの検証と要望2の衝突 🆕（RED-01対応）

**問題の構造**

実装を確認したところ、`SpoilerOverlay` は `has_score=true` のとき `summary_ja` 全体をぼかしプレースホルダに置換する方式で、`NewsCard.jsx` の**summary表示領域そのもの**に描画されている（`NewsCard.jsx` L56・L67・L76・L81-86）。

一方、改修要件2（ニュースをタイトルのみ表示し、クリックで本文展開）は**同一の領域を改修対象とする**。これにより2つの問題が生じる。

| # | 問題 | 内容 |
|---|---|---|
| 1 | **検証対象が改修で消滅する** | フェーズ3の手順10は製造（手順7）の後。「フェーズ2のネタバレUIを開幕後に確認する」という承認条件（Takumi様2026-06-28承認）が、**改修後のUIでしか実施できなくなる**。フェーズ2の受け入れ条件が本人の再承認なくフェーズ3の条件にすり替わる |
| 2 | **隠蔽機構の二重化** | 「デフォルト非表示（タイトルのみ）」と「ネタバレ防止のぼかし」が重なる。ユーザーはクリック展開 → さらに「スコアを表示」を押す**二段操作**になるか、あるいはネタバレ防止機能が要望2に吸収されて役割を失う。**F-05／F-05bの存続可否**という要件レベルの論点 |

**対応方針：案Aを採用する**

| 案 | 内容 | 採否 |
|---|---|---|
| **案A** | **要望2の製造着手前に、開幕直後の現行UIでSection Cを2週分実施してフェーズ2を正式クローズする** | ✅**採用** |
| 案B | フェーズ2の承認条件を「改修後UIでの確認」に読み替え、Takumi様の再承認を得る | ❌不採用 |

**案Aを採用する根拠**: 承認条件の事後的な読み替えは、フェーズ2振り返り3-7（レビュー指摘が追跡されず放置される）と同型の劣化を招く。**「検証していないものを、検証しないまま改修する」ことを避ける**方が原則として健全である。加えて、Section Cの実施は開幕直後の2週間で完了し、フェーズ3の手順1〜6（設計工程）と並走できるため、**日程上のコストがほぼ発生しない**。

**制約事項**

- 要望2（および `NewsCard.jsx` のsummary領域に触れる全ての改修）の**製造着手は、フェーズ2 Section C のクローズ後**とする
- 手順7のサブ手順設計時に、この依存関係を実装順序に反映すること
- Section Cが2週分で合格しなかった場合、フェーズ2の残課題対応が要望2に優先する

### 8-0-1. 追従漏れを構造的に防ぐ書き方 🆕（v0.5新設・v0.4レビュー傾向分析への対応）

**背景：3版連続で、新設したルールの初回適用がそのルール自身の基準を満たさなかった。**

| 版 | 新設したメタルール | 初回適用の結果 |
|---|---|---|
| v0.2 | §8項目6（宣言↔実体の突き合わせ） | 件数ベースで自己参照を除外できず → **v0.2レビュー**YEL-03で指摘 |
| v0.3 | §8-2（項目6の判定基準） | 自らの除外規則に反する引用が2件 → **v0.3レビュー**YEL-01で指摘 |
| v0.4 | §8項目8・§8-0（波及確認3方向） | ①横方向・②証跡下方向の両方で自己検証を通らず → **v0.4レビュー**YEL-01・YEL-02 |

**原因の分析（v0.4レビューの傾向分析より）**

| # | 原因 | 根拠 |
|---|---|---|
| 1 | **集計を手で書いている** | 件数（ヒットN件・全M項目）は整形の過程でずれる。一方、**引用ベースの項目6証跡は全20行が正確**だった。**引用は正確に書けるが、集計は間違える** |
| 2 | **自己言及の構造** | 証跡ブロック自身が検索対象文字列を含み、注記自身が表を要約する。「書いた瞬間に対象が変わる」ため静的なチェックでは必ずずれる |

**方針：ルールを増やすのではなく、古くならない書き方に変える**

追従確認のルールを足しても、確認する対象が増えるだけで根治しない。**そもそも古くなる書き方を排除する**方が確実である。

| 排除するもの | 代わりの書き方 | 理由 |
|---|---|---|
| **件数**（ヒットN件・全M項目・N件を検証） | 「各項目について」「追従対象として修正した行」 | 版ごとに必ず変動し、過去の証跡と比較できない（§8-2が件数ベースを否定したのと同じ理屈） |
| **範囲指定**（項目N〜M） | **列の値を参照する**（「由来列が『振り返り』のもの」） | 表に行を足すたびに黙って古くなる。v0.4 YEL-01の直接原因 |
| **手による整形・要約** | **コマンド出力をそのまま貼り、各行の右に注記を付ける** | 整形の過程で行番号・件数がずれる。v0.4 YEL-02の直接原因 |
| **本文中の版番号付き相互参照** 🆕 | **節番号のみで参照する**（「要件定義書（フェーズ3）§3-1」）。**版番号を書くのはヘッダの参照欄と§5成果物一覧に限る** | 計画書と要件定義書が互いの版番号を固定して参照すると、**どちらかが版を上げるたびに他方が古くなる**。両書とも同日中に複数版を重ねており、相互の陳腐化が必ず発生する（要件定義書 v0.3レビューYEL-02） |

> **この方針が有効な理由**: 本計画書の**本文の内容そのものには誤りがほとんどない**（指摘の解消率は4版連続100%）。ずれているのは常に「**本文を要約・集計した二次的な記述**」である。二次的な記述を減らせば、追従確認の対象自体が減る。

### 8-0-2. 版を上げる作業の手順 🆕（v1.5新設）

**背景**: 要件定義書ヘッダの他文書参照が**4版連続（v1.2〜v1.5）で追従漏れとして検出されている**。毎版必ず発生し、毎版必ず修正している。

**自動化できない理由**: ヘッダの「参照」欄は§8-1の📌**実施記録**にあたり、「**どの版を見て作業したか**」を示す。機械的に最新版へ書き換えると、実際には旧版を見て作業した場合でも最新版を見たことになり、記録の正確性が失われる。**手動更新である必要がある。**

**対処：検出ではなく手順で防ぐ**

版を上げる作業は**必ず以下の順で行う**。

| # | 作業 |
|---|---|
| 1 | **本文の修正**（レビュー指摘の反映・新規記述） |
| 2 | 自文書のヘッダ（バージョン番号）・§5成果物一覧の更新 |
| 3 | **関連文書のヘッダ参照欄の更新**（本文修正が完了してから） |
| 4 | **証跡の採取**（§8-0「証跡は最終稿確定後に採取する」） |
| 5 | 変更履歴の追記 |

> **手順3を独立させたことが要点**。従来は「本文を直す → 証跡を採る」の間に関連文書のヘッダ更新が入っておらず、証跡採取で初めて気付いていた。**気付くのではなく、手順として通る**形にする。

### 8-0-3. 自己チェックの二分（機械確認／判断） 🆕（v1.7新設・リスク調査書v0.6レビューの知見）

**背景**: リスク調査書の自己チェックは**25項目**に達した。§6-2を見ると、**v0.1〜v0.5の指摘22件に対して項目が19件新設**されている。**指摘1件につき項目1件**という運用であり、版を重ねるほど自己チェックが重くなる。

**3回続けて同じ型の失敗が起きている**

| 版 | 失敗 |
|---|---|
| v0.3 GRN-01 | 第13項（採番）を新設した版で、別の表に適用していなかった |
| v0.5 YEL-04 | §6-2への記録が部分的にとどまった |
| **v0.6 YEL-01** | **第23項（件数で機械確認）を新設した版で、第23項が実行されていない** |

> **「新設した項目を、その版で適用し忘れる」という失敗に対して「適用漏れを検出する項目（第14項）」を足したが、効いていない。項目を足す対処は、少なくともこの型には効かないことが3回で確認できた。**

**方針：チェック項目を「機械確認」と「判断」に二分する**

| 区分 | 内容 | 実行方法 |
|---|---|---|
| **A. 機械確認** | 件数の照合／採番の連続性／行番号の照合／参照先ファイルの実在／旧識別子の残存 | **`grep` / `wc` / `sed` で確定できる。毎回コマンドで実行する** |
| **B. 判断** | 評価が過大でないか／前提変化の波及／実行時系列での追跡／記述の粒度／依存関係の循環 | 読んで判断する。実行者の注意力に依存する |

> **区分Aは「実行すれば必ず検出できる」**。v0.6レビューの🟡3件・🟢2件は**すべて区分Aで検出できた種類**だった。項目として書かれていても実行されなければ意味がなく、**逆に実行しさえすれば漏れない**。
>
> **区分Bは項目を増やしても効果が逓減する**。読み手の注意力という有限の資源を分割するだけになる。

**運用**

1. 版を上げる際、**区分Aは必ずコマンドで実行する**（§8-0-2の手順4「証跡の採取」に統合）
2. **区分Bは項目を増やす前に、既存項目との統合可能性を検討する**（性質が近いものは統合する）
3. 指摘1件につき項目1件を機械的に追加しない

> **本方針の適用範囲**: リスク調査書に限らず、**フェーズ3の全文書の自己チェックに適用する**。

### 8-1. grep結果の判定基準 🆕

grepのヒットは**すべてが修正対象ではない**。以下の分類で判定すること。

| 分類 | 内容 | 対応 |
|---|---|---|
| **🔧 追従対象** | 現行の生きているドキュメントが旧バージョンを参照している | **修正する** |
| **📌 実施記録** | 日付付きの実施記録・検証記録（週次チェックリストの各回等）。作成時点で正しかった参照 | **修正しない**。改変は記録の改竄にあたる |
| **📖 履歴的記述** | 変更履歴・注記内の過去バージョン名の記録、過去版の証跡の引用 | **修正しない** |
| **🔁 証跡ブロック自身のヒット** 🆕 | **現在書いている証跡ブロックが、検索対象の文字列を含むために自らヒットとして現れたもの** | **修正しない。件数の一致も求めない** |

> **判定の根拠：** 実施記録は「その時点で何を参照して判断したか」を示す証拠であり、事後に書き換えると監査可能性を失う。一方で生きているドキュメントの参照は常に最新を指すべきである。この区別を明示せずgrepを機械適用すると、記録を壊す方向のミスが起こりうる。
>
> **🔁 を追加した理由（v0.5・v0.4レビューYEL-02対応）：** 証跡ブロック自身が検索対象の文字列を含むため、**証跡を書いた瞬間に新しいヒットが生まれ、数え直すとまた増える**という自己言及の構造がある。「最終稿確定後に採取する」というルールだけでは一致せず、実行者は手で辻褄を合わせることになり、そこで差異が生まれる（v0.4の項目5-aで実際に発生）。
>
> **したがって総ヒット数は記載しない。** 記載するのは **🔧追従対象として修正した行のみ**とする（§8-0-1の方針）。

### 8-2. 項目6の判定基準 🆕（v0.3追加・YEL-03対応）

項目6の証跡は**件数ではなく「実体行の引用」で残す**。件数ベースの判定には以下の欠陥がある。

| 欠陥 | 内容 |
|---|---|
| **自己参照が混入する** | 管理表の行そのものが必ずヒットする。**極端には実体ゼロでも管理表＋対応表で2件ヒットし「✅実体あり」と誤判定される** |
| **再現性がない** | 検索語を伏せると第三者が同じ結果を得られない |
| **版によって数が変動する** | 記述の追加・削除で件数が変わり、過去の証跡と比較できない |

**証跡の形式**

```
改善N（項目名）
  宣言箇所 : §4 管理表 L{行番号}
  参照先   : 手順X
  実体行   : L{行番号}「実際の作業項目行をそのまま引用」
  判定     : ✅実体あり ／ ❌乖離
```

**カウント除外対象**（自己参照）

- §4管理表の行そのもの
- §7リスク表の行そのもの
- §1-2継続事項表の行そのもの
- レビュー指摘 対応表の行
- 変更履歴・注記内の記述
- **§1-1の優先順位表・マイルストーン表**（宣言側であり手順の実体ではない） 🆕

> **⚠️ 除外規則の適用における注意（v0.4追加・v0.3レビューYEL-01対応）**
>
> v0.3の付録A-3では、上記除外対象に該当する行を**実体として引用してしまった**（§7の宣言を§1-1の注記L48・§1-2継続事項L102で裏付けた）。結論（乖離0件）自体は正しかったが、証跡としては「**宣言箇所を宣言箇所で裏付けた**」形になっており、v0.2の件数ベース証跡が抱えていた自己参照問題と同じ構造だった。
>
> **実体行は必ず §3（開発手順）または §8（ルール本体）の記述であること**を確認する。§1・§4・§7の記述は宣言側であり、原則として実体にはならない。

**実体の定義（v0.6で例外を追加・v0.5レビューYEL-04対応）**

| | 内容 |
|---|---|
| **原則** | 実体は **§3（開発手順）または §8（ルール本体）** の記述とする |
| **例外** | **§3の工程に属さない作業**（工程外の先行対応・前フェーズのクローズ処理等）は、「**§1-2の詳細ブロックに手順が定義されている**」かつ「**§5に成果物として登録されている**」の2条件をもって実体ありとみなす |

> **例外を設けた理由**: 工程外の先行対応（§1-2継続事項#2）もフェーズ2クローズ処理（§1-2継続事項#1）も、**§3に存在しないことが正しい**作業である。前者は定義上フェーズ3の工程外であり、後者はフェーズ2の後始末で手順1〜12のどれにも属さない。したがって§3実体を探しても永久に見つからず、現行ルールのままではこの2行が毎版「規則違反の引用」か「❌乖離」のどちらかになるしかなかった。**ルール側の穴**であり、適用範囲を正しく定義し直す。
>
> なお本件は「ルールを足す」のではなく「**既存ルールの適用範囲を定義し直す**」ものであり、§8-0-1の方針（ルールを増やさない）と矛盾しない。

> **本基準が必要な理由（v0.2レビューYEL-03）：** 項目6はv0.2で新設した目玉のルールであり、その最初の適用結果が「宣言と実体の乖離0件」という**安心を与える結論**を出した。しかし証跡は件数ベースで自己参照を除外しておらず、再現性もなかった。**証跡が弱いまま安心だけが残るのは、ルールがない状態より危うい。** §8-1がgrep（項目5）について解決したのと同じ厳密さを、項目6にも与える。
