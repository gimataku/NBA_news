#### ② 🔴 Health Check Path を設定すると、起動時バッチが原因でデプロイが失敗しうる

**設計書のどの文書もこの点に触れていない。**

```python
# main.py L50-58（現行）
@app.on_event("startup")
def startup_event() -> None:
    init_db()
    init_user(crud)
    scheduler.start()
    check_and_run_batch()      # ← 同期実行
```

| # | 事実 | 根拠 |
|---|---|---|
| 1 | `check_and_run_batch()` は **`last_fetched_at` から4時間経過していれば `run_batch()` を実行する** | `scheduler.py` L184-187 |
| 2 | `run_batch()` は RSS取得に加え、**記事ごとに Claude API を呼ぶ**。呼び出しごとに **`time.sleep(CLAUDE_INTERVAL=1.0)`** が入る | `processor/claude_client.py` L86・`config.py` L17 |
| 3 | **FastAPI の startup イベントは、アプリがリクエストを受け付ける前に完走する**。完了するまで **`/healthz` は応答しない** | ASGI lifespan の仕様 |
| 4 | **Health Check Path 未設定なら、Render はポートバインドで起動を判定する**。設定した瞬間に、**起動時間が判定対象に入る** | Render の挙動（**要確認**） |

> **つまり、Health Check Path の設定は「監視を足す」だけの変更ではない。デプロイの成否判定に起動時間を持ち込む変更である。**
>
> **顕在化する条件**: **前回バッチから4時間以上空いた状態でのデプロイ・再起動**。定常運用では4時間ごとにバッチが走るため大半のデプロイでは起きないが、**朝一番のデプロイ・障害復旧後の再起動・長時間停止後の起動**で起きる。**「たまに落ちる」形で現れるため、原因の切り分けが難しい種類**である。
>
> **⚠️ 失敗が連鎖しうる**: デプロイが失敗して Render が再起動をかけると、**再び startup が走り、再びバッチが走る**。
>
> **いつ解消するか**: **7-A-10（移行）以降は起きない。** 基本設計書§5-3 が **`ENABLE_SCHEDULER=false` の分岐対象に `check_and_run_batch()` を含めている**ため、移行後の Render では起動時バッチ自体が走らない。**露出するのは「9月中の有効化」から「移行完了」までの期間に限られる。**

**対処（実施順）**

| # | 対処 | 内容 |
|---|---|---|
| 1 | **設定前に Render の Health Check のタイムアウト／猶予時間を画面で確認する** | 起動時バッチの所要時間（記事件数 × 約1〜数秒）に対して十分かを見る。**確認結果を下表に記録する** |
| 2 | **設定変更がデプロイを誘発するかを確認する** | Health Check Path の変更だけで再デプロイが走るなら、**その1回目がまさに上記の条件に当たりうる** |
| 3 | **設定の直前に手動でバッチを走らせ、`last_fetched_at` を更新しておく** | 直後のデプロイで `check_and_run_batch()` が**走らない**状態を作る。**現行は `POST /api/fetch` が使える**（7-A-11 で削除予定だが、9月時点では存在する） |
| 4 | **失敗した場合は Health Check Path を空に戻す** | 先-2 は**補助**であり、§6-2-2 の主4つを置き換えない。**デプロイを不安定にしてまで維持する価値はない** |

### 7-A-2 の発見事項

#### F1 ⚠️ 2つの秒数が論理的に両立しない

| 値 | 当初のラベル |
|---|---|
| **2分37秒（157秒）** | Health Check のタイムアウト／猶予時間（確認事項②） |
| **2分48秒（168秒）** | 起動所要時間 (a)→(d)（手順2） |

**ラベルどおりなら 168秒 > 157秒 であり、Health Check はタイムアウトしてデプロイが失敗する。しかしデプロイは成功している。したがって、少なくとも一方のラベルが誤っている。**

| 可能性 | 内容 | もっともらしさ |
|---|---|---|
| **A** | **両方ともデプロイ所要時間**（ビルド＋起動の合計）。別々のデプロイを見たため11秒ずれた | **高い**。`2m 37s`／`2m 48s` は Render がデプロイ一覧に表示する形式そのものであり、**2回の値がこの程度ばらつくのは自然**。またビルド（pip install 等）に2分前後かかるのは妥当 |
| B | 2分37秒がタイムアウトで、2分48秒は (a)→(d) の実測 | **低い**。成立するとデプロイが失敗するはずで、観測と矛盾する |
| C | 2分37秒がタイムアウトで、2分48秒は別の何か | 判断材料なし |

> **可能性Aが正しい場合、論点②の懸念はほぼ解消する。** デプロイ全体が168秒で完了しているなら、**そのうち起動（(a)→(d)）は数秒〜十数秒**であり、Health Check のタイムアウト（Render 既定は十分に長い）に対して余裕がある。
>
> **⚠️ ただし確定していない。** 確定させるには**Deploy Log 内の (a)〜(d) の行の時刻差**を見る必要がある（デプロイ一覧の所要時間表示ではなく、**ログ本文の時刻**）。
>
> **📌 F1 を「解消」とせず「未確定」で残す根拠**: **移行（7-A-10）で `ENABLE_SCHEDULER=false` になれば起動時バッチは走らなくなる**（基本設計書§5-3）。**残り11日で移行する計画である以上、F1 の確定に時間を使う価値は小さい**。ただし**移行が期限内に終わらなかった場合は、開幕後に顕在化しうる懸念として生き残る**ため、**消さずに残す**。

##### ✅ F1 の決着（2026-10-11・3点目の実測により確定）

**7-A-2 終了後のデプロイが 1分37秒（97秒）だった。3つの値が揃い、F1 は論理的に決着する。**

| # | 値 | 当初のラベル | 取得時期 |
|---|---|---|---|
| 1 | **2分37秒（157秒）** | Health Check のタイムアウト／猶予時間 | 着手前確認② |
| 2 | **2分48秒（168秒）** | 起動所要時間 (a)→(d) | 手順2 |

**🔴 設定値は変動しない。3つの値がすべて異なる以上、これらは設定値ではなく測定値である。**

| # | 推論 |
|---|---|
| 1 | **タイムアウトは定数である。** 157／168／97 と3通りの値が出たのだから、**少なくとも2つは測定値**であり、**3つすべてが測定値である可能性が最も高い** |
| 2 | **#2 が「起動所要時間」で #3 が「デプロイ所要時間」だとすると、起動(168秒) > デプロイ全体(97秒) となり成立しない**（同一システムの別デプロイとしては無理がある） |
| 3 | **したがって 157／168／97 はいずれもデプロイ所要時間である。** `2m 37s`／`2m 48s`／`1m 37s` は Render がデプロイ一覧に表示する形式そのものであり、**デプロイごとにこの程度ばらつくのは自然**である |

**結論**

| 項目 | 結論 |
|---|---|
| 「2分37秒」の正体 | ✅**Health Check のタイムアウトではなかった。デプロイ所要時間である**（可能性A が確定） |
| Health Check のタイムアウト値 | ⚠️**依然として不明**（一度も取得できていない） |
| 起動所要時間 (a)→(d) | ⚠️**依然として未実測**（デプロイ全体の所要時間しか見ていない） |
| **論点②（起動時バッチでデプロイが失敗しうる）** | 🟢**観測により実質的に解消。これ以上追求しない** |

> **📌 論点②を🟢に下げる根拠は「確定した」ではなく「観測が揃った」である。**
>
> | # | 観測・仮説 |
> |---|---|
> | 1 | **3回のデプロイがすべて成功している**（97／157／168秒）。**Health Check は3回とも通った** |
> | 2 | **ばらつきの幅は71秒**（97→168）。**この差が起動時バッチの有無で説明できる**——バッチが走ったデプロイが60〜70秒長かった、という読みは自然である。**仮説であり確定ではない** |
> | 3 | 仮説2が正しければ、**起動時バッチが走ったデプロイも成功している**ことになり、**論点②は実測で否定されたことになる** |
>
> **🔴 それでも「解消」と断定しない。** タイムアウト値が不明なため、**余裕がどれだけあるかが分からない**。**開幕（2026-10-20）で記事件数が増えれば起動時バッチは長くなる**。成立しているのは「**現在の記事件数では3回連続で通った**」という事実だけである。

> **📌 本件の教訓**: 🔴**「2分37秒」を受け取った時点で、それが設定値か測定値かを確かめていなかった。** 当方は②を「Health Check のタイムアウト」という**問いの形**で尋ね、返ってきた数値を**その問いの答えとして受け取った**。しかし**設定値には「変動しない」という性質がある**——**2点目が出た時点で矛盾に気付けたが、3点目まで待った**。**数値を受け取るときは、それが定数なのか測定値なのかを、単位や桁ではなく*性質*で確かめる。**

### 🔴 F8：`forwarded_allow_ips="*"` により、`X-Forwarded-For` の偽装でレート制限をバイパスできる（2026-10-15・本番実測）

| 項目 | 内容 |
|---|---|
| 事象 | 偽装なしでは 5回目まで 401・6回目から 429（IP 単位で効いている）。**毎回違う IP を `X-Forwarded-For` に付けると 7回とも 401**＝バケットが偽装値ごとに分かれ、**制限が働かない** |
| 原因（推定） | uvicorn は `forwarded_allow_ips="*"` のとき **`X-Forwarded-For` の先頭**を採る。**Render が受信した値を上書きせず追記する**場合、先頭はクライアントが付けた値になる。詳細設計書§2-4-2 は「Render 以外から直接ポートに到達できない」ことのみを前提とし、**クライアントによる偽装は想定していなかった**（当方の指示文§0・7-A-4 の注意#7 で懸念を挙げ、実測で確認した） |

### ✅ F4 の原因確定（2026-10-12）── `render.yaml` のプレースホルダが Blueprint sync でダッシュボードの実値を上書きした

|---|---|
