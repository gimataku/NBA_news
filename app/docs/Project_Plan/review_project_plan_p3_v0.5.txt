[YEL-01] 手順2-Aの前提調査に、実行手段が確保されていない

  対象箇所: 手順2-A「【前提調査】現行Persistent Diskの実使用量とDB増加率の実測」

  現状:
    手順2-Aは「実使用量が分からなければ代替先の容量が足りるかを判断できない。
    判断材料が欠けた状態で移行先の比較に入ると、選定をやり直すことになる」として、
    本項目を他の調査項目より先に実施すると定めている。判断は正しい。

  問題:
    **その実測をどうやって行うかが、現時点で確立していない。**

    ・振り返り3-4は「総取得記事数を確認しようとした際、Render Web Shell から
      SQLiteに直接クエリを投げる必要があったが、**DBパスの解決に失敗し
      その場では取得できなかった**」と記録している。
    ・その対策として振り返り§4-1 #3「Render Web Shell からのDB接続手順を確立し
      `docs/` に記録する」が短期アクションに挙げられているが、**未実施**である
      （`docs/` に該当する手順書は存在しない）。
    ・代替手段となるステータスAPIの拡張は、手順3・4で設計し手順7で実装するため、
      **手順2の時点では存在しない**。

    つまり手順2-Aの最優先項目が、着手した瞬間に手段の不在で止まる可能性が高い。
    振り返り3-9が「机上で決めた監視方式が実際には到達不能だった」という失敗であり、
    本計画は §8項目8・手順2-C で「観測できるかを先に検証する」を掲げている。
    **その原則が手順2-A自身には適用されていない。**

  推奨対応:
    ・手順2-Aの前提調査の直前に「**実測手段の確保**」を独立項目として置く。
      候補：
        (a) Render Web Shell からのDB接続手順を確立し `docs/` に記録する
            （振り返り§4-1 #3の実施。フェーズ3の運用手順書の第一版にもなる）
        (b) Renderダッシュボードの Disk メトリクスで代替できるか確認する
            （使用量だけならシェル不要で取れる可能性がある）
        (c) 記事件数からの推定に切り替える（`/api/news` の limit 上限100の制約下で
            どこまで正確に出せるかを含めて判断する）
    ・(a) を採る場合、成果物は §5-2「運用手順書」の前倒し作成として登録できる。

  重要度の根拠:
    手順2-Aは無料化可否の判断根拠であり、要望1のスコープアウト判断に直結する。
    ここで止まると手順2全体が滞る。かつ本計画が自ら掲げた
    「観測できるかを先に検証する」原則の適用漏れである。


[YEL-02] 先行対応の検証チェックリストが、追加する動作そのもの（異常系）を見ていない

  対象箇所: §1-2 継続事項#2「*検証*」（L180-187）

  現状の検証項目:
      [ ] ロールバック手段を事前に確認する
      [ ] 変更差分のコードレビューを実施する
      [ ] 環境変数が**正しく設定された状態**で起動確認を行う
            - Render デプロイログに起動成功が出ること
            - `/api/status` が 401 を返すこと
      [ ] 上記の結果を実施記録に含める

  問題:
    YEL-01の修正内容は「`ANTHROPIC_API_KEY`／`BALLDONTLIE_API_KEY` が空なら
    `RuntimeError` を送出する」というものである。すなわち**追加する動作は
    「未設定のときに起動を止める」ことそのもの**である。

    ところが検証項目は「正しく設定された状態で起動すること」しか見ていない。
    これは**修正を入れる前でも通る確認**であり、
    `RuntimeError` が実際に配線されているかは検証されない。
    たとえば条件式を書き間違えて常に False になっていても、この検証は通過する。

    正常系だけを確認して異常系を確認しないのは、
    振り返り3-8（合否だけを残して観測値を残さない）と同じ構造
    ——「確認したことにはなるが、確認したい対象を確認していない」——にあたる。

  推奨対応:
    ・検証項目に異常系を追加する。**本番では行わない**。
        [ ] ローカル環境で `ANTHROPIC_API_KEY` を空にして起動し、
            `RuntimeError` が送出され起動が停止することを確認する
        [ ] 同様に `BALLDONTLIE_API_KEY` についても確認する
    ・可能なら単体テストを1件追加する（`backend/tests/` に
      「必須環境変数が空なら起動時に例外」を確認するテスト）。
      既存の `SECRET_KEY` 側に同種のテストがあれば、それを踏襲すればよい。
      テストがあれば、フェーズ3の手順8で自動的に回帰確認される。
    ・本番での確認は「正しく設定された状態で起動すること」に留める
      （異常系を本番で試すとサービスが落ちるため）。

  補足:
    この指摘は「3行だから安全ではない」という v0.5 の注記（L189）と同じ方向だが、
    そこで想定されているリスクは「設定不備で起動しなくなる」という**副作用**である。
    本指摘はそれとは別で、「**意図した動作が入っているかを誰も見ていない**」という点にある。

[YEL-04] 「実体は§3または§8に限る」ルールが、工程外作業に対して構造的に成立しない

      | 工程外対応の検証必須化 | **§1-2継続事項#2**「*検証*」チェックリスト |

                                     **§1-1**マイルストーン＋**§1-2**継続事項#1 |

    §8-2の「カウント除外対象」は §1-2継続事項表・§1-1の表を明示的に挙げているため、
    **自ら定めた除外規則に反する引用**になっている。

    その方針からすると、本件は「ルールを足す」のではなく
    「**既存ルールの適用範囲を正しく定義し直す**」ものであり、方針と矛盾しない。

[GRN-04] クローズ判定基準「C-1〜C-5の全項目がOK」のうちC-5は2週で満たせない可能性がある

  §1-2継続事項#1のクローズ判定は「C-1〜C-5の全項目がOKであること」を求めている。
  テンプレートのC-5は
    「試合日程タブの Scheduled/**In Progress**/Final で has_score が
      正しく反映されているか」
  であり、**In Progress の確認は試合開催中にアクセスする必要がある**
  （NBAの試合時間は日本時間の午前中に集中する）。

  開幕直後の2週間で Scheduled と Final は確実に観測できるが、
  In Progress を捕まえられるかは実施タイミング次第である。

  → 判定基準に「**C-5のIn Progress確認が実施タイミングの都合で
    観測できなかった場合の扱い**」を定めておく。
    v0.5は既に「C-5のみNGの場合は要望2の製造をブロックしないが
    フェーズ2のクローズは保留する」と場合分けしているため、
    「NG」と「観測機会なし」を区別する一行を足せば足りる。
    フェーズ2はまさに「観測機会がないものを未確認のまま残した」ことが
    本件の発端であり、同じ状態を再び作らないための線引きが要る。

  ── 版を重ねることについて ──

  v0.1からv0.5まで、指摘の解消率は5版連続100%である。
  本版で初めてメタルール層に新規指摘が出ず、🟡4件のうち3件が
  計画の内容そのもの（実行手段・検証設計・関連文書の整合）に関するものになった。
  文書統治の整備は一区切りついたと判断してよい。

  §8（バージョン管理ルール）関連が約230行、付録の証跡が約300行を占める。
  対して手順3・4・6・8.5・12は依然として1〜2行のスタブである。
  これは工程の詳細を後段の成果物（基本設計書・テスト設計書）に委ねる設計であり
  それ自体は妥当だが、**計画書の重心が実行計画から文書統治へ寄っている**ことは
  認識しておく価値がある。

  フェーズ2振り返り§6-3は「改善策の実効性は、その抽象度に反比例する」と結論した。
  §8のルール群は既に十分に具体的で実効性が確認できている。
  ここからの投資は、ルールの精緻化よりも手順1（要件定義）の実作業に向ける方が
  費用対効果が高い。本レビューの🟡3件が実行可能性の指摘に寄ったのは、
  計画書側にもう大きな穴が残っていないことの反映でもある。
