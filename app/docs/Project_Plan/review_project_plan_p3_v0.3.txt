[YEL-01] 付録A-3の証跡が最終稿に対して再現せず、§8-2の除外規則にも反している

  対象箇所: 付録A-3「項目5-a」「項目6 (b)」

  §8-2は「証跡は件数ではなく実体行の引用で残す」「自己参照を除外する」
  「検索語を伏せない」と定めた。方針は正しいが、**その最初の適用結果が
  基準を満たしていない**。

  (1) 項目5-a の行番号が最終稿と一致しない

      付録A-3は次のように記録している。
        ./Project_Plan/project_plan_p3_v0.3.md:428  → 🔧 追従対象 ★検出
        ./Project_Plan/project_plan_p3_v0.3.md:609  → 📖 履歴的記述（付録A-2の引用）

      実際に v0.3 に対して同じgrepを実行すると、ヒットは L621・L622・L700 の3件で
      あり、L428・L609 はヒットしない。
        ・L428 は修正後にファイル名が v0.3 に変わったため当然ヒットしない
          （★検出→修正済みの記録としては妥当だが、修正前の行番号である旨の
            但し書きがない）
        ・L609 は現行では対応表の「（結論）」行であり、当該ファイル名を含まない。
          編集途中で採取した行番号がそのまま残っている

      §8-2が掲げた「再現性がない（第三者が同じ結果を得られない）」という
      欠陥に、証跡自身が該当している。

  (2) 項目6 (b) が、§8-2の「カウント除外対象」に挙げた宣言箇所を実体として引用している

      §8-2は除外対象として「§1-2継続事項表の行そのもの」「変更履歴・注記内の記述」
      を明記している。ところが (b) の5行中2行がこれに抵触する。

        宣言「手順2-Bの判定基準」
          引用: L48「移行後の無料枠の中で成立するか」
          → L48 は §1-1 の注記であり、手順ではない。
             真の実体行は L227（手順2-B）
               「判定基準: 単体のコスト比較ではなく『要望1で移行した後の
                 無料枠の中で成立するか』で評価する」

        宣言「案A・手順7実装順序」
          引用: L102「製造着手は、フェーズ2 Section C のクローズ後」
          → L102 は §1-2継続事項#1の制約事項であり、§8-2が明示的に
             除外対象とした箇所。真の実体行は L288（手順7）
               「要望2（および NewsCard.jsx のsummary領域に触れる全ての改修）は、
                 フェーズ2 Section C のクローズ後に着手する」

      いずれも実体は別の行に確かに存在するため**結論（乖離0件）は正しい**が、
      証跡としては「宣言箇所を宣言箇所で裏付けた」形になっている。
      これは v0.2 の件数ベース証跡が抱えていた自己参照問題と同じ構造である。

  推奨対応:
    ・付録A-3を最終稿に対して再実行し、行番号を採り直す。
      修正によって消えたヒット（L428）は「修正前 L428 → 修正後は該当なし」と
      前後を併記する。
    ・(b) の2行の実体行を L227・L288 に差し替える。
    ・§8-2に「**証跡は最終稿確定後に採取する**」という手順上の注意を追記する。
      編集途中の行番号を貼ると必ずずれる。

  重要度の根拠:
    §8-2はv0.3の目玉であり、「証跡が弱いまま安心だけが残るのは、ルールがない
    状態より危うい」という前回レビューの指摘に応えて新設されたルールである。
    その初回適用が基準未達では、ルールの実効性が最初から損なわれる。

[YEL-04] セキュリティ指摘の対応時期が、ベースラインと本計画で食い違っている

  対象箇所: §1-2継続事項#2 ／ §1-3改修要件6 ／ 手順1

  現状:
    `document_baseline_p2.md` §3 残課題3（L96）は次のように定めている。
      「セキュリティレビュー指摘の対応要否判断（🟡YEL-01〜04・🟢GRN-01〜04）
        → **短期（2026年9月まで）**。**YEL-01は`config.py`3行追加で完結・即応推奨**」

    一方 本計画は、改修要件6として手順1で要否判断 → 手順3以降で設計 → 手順7で製造
    という通常の工程に載せている。マイルストーンからすると製造は10月中旬以降であり、
    **「9月まで」には収まらない**。

  問題:
    クローズ済みフェーズのベースラインが定めた期限と、次フェーズ計画の工程が
    整合していない。どちらが有効かが不定のまま両方が生きている状態である。

    実務上とくに問題になるのはYEL-01（APIキー未設定でも起動する）で、
    ベースラインが「3行追加で完結・即応推奨」と評価している軽微な修正を、
    要件定義〜設計〜製造の全工程に乗せると2か月近く待つことになる。
    この間、環境変数の設定漏れは「起動はするが翻訳されない」という
    気付きにくい故障として顕在化しうる。

  推奨対応:
    次のいずれかを明示的に選択し、計画書とベースラインの双方に記録する。
      案A：セキュリティ指摘のうち**低リスク・低コストのもの（YEL-01等）を
           フェーズ3工程外の先行対応**とし、手順1では残りの要否判断のみを行う。
           先行対応分は手順7.5の指摘対応表に「対応済み」として引き継ぐ
      案B：ベースライン§3残課題3の期限を「フェーズ3手順7で対応」に改め、
           「9月まで」の記述を取り下げる

    案Aを推奨する。§1-1の優先順位は「安全性」を最上位に置いており、
    3行で解消できる安全性の欠落を工程都合で2か月保留するのは、
    その優先順位と整合しない。

    その場で自己検算できる形が望ましい。

  総評として、v0.1 → v0.2 → v0.3 の3版を通じて指摘の解消率は100%を維持しており、
  対応表・証跡・ベースライン更新まで含めた追跡体制は、フェーズ2の同時期と比べて
  明確に高い水準にある。

  一方で3版連続して「本文は直したが周辺（注記・証跡・関連文書）が追従しない」型の
  指摘が出続けている点は、傾向として認識しておく価値がある。

  今回のYEL-01（証跡 ↔ 最終稿）・YEL-02（表 ↔ 注記）・YEL-04（計画 ↔ ベースライン）は
  いずれもその射程の外にある。

  次に何かルールを足すとすれば、チェックの種類を増やすより
  「**修正を入れたら、その修正が引用・要約・参照されている箇所を洗う**」という
  一段抽象的な確認を §8 に置く方が、費用対効果が高いと考える。
