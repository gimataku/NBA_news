1. 自己検出漏れの記録（観点表§5-2・必須）
--------------------------------------------------------------------------------

  【本版の最大の問題は、当方が書いた指示文の誤りである】

  製造検証ログ 2026-10-29 の発見事項②は、原因を明記している。

    「②`Show versions` を `pip install -r` の前に置いたため certifi 未導入で
      失敗（**指示文の順序誤り**）→ 後ろへ移動」

  ■ 当方が書いたもの（`instruction_SEC-1.md` §4）

    ```yaml
      - name: Upgrade pip
        run: python -m pip install --upgrade "pip>=26.2.2"
      - name: Show versions
        run: |
          python -VV
          python -m pip --version
          python -c "import certifi; print('certifi', certifi.__version__)"   ← ここ
      - run: pip install -r app/backend/requirements.txt
    ```

    **`certifi` は `requirements.txt` 経由でしか入らない。**
    その `pip install -r` より前に `import certifi` を実行させた。
    **必ず `ModuleNotFoundError` でジョブが落ちる。**

  ■ さらに悪いことに、確認の仕組みごと壊していた

    当方は §4 の注意点 #4 でこう書いた。

      「`python-version: '3.11'` は runner のツールキャッシュにある最新の
        3.11.x に解決される。**`Show versions` の `python -VV` で
        3.11.18 以降であることを確認する**。満たない場合は `'3.11.18'` に
        固定して報告する」

    つまり **①の検出を②のステップに委ねていた**。
    その②が落ちるのだから、**①は永久に検出されない設計**だった。
    実測では `'3.11'` は **3.11.17** に解決されており、**基準未満**だった。

    実装側が「落ちた → 順序がおかしい → 直す → ついでに版を実測して固定」と
    自力で辿ったため両方とも解消したが、**指示どおりに進めていれば
    Python が基準未満のまま運用に入っていた**。

  ■ 観点の欠落

    当方は文書のコードブロックに対して **2-9（例示コードと注記の整合）**と
    **3-2（実行時の到達性）**を当てている。
    しかし**自分が指示文に書いたコードブロックには当てていなかった。**

    レビュー対象の文書は疑うが、**自分の書いたものは疑わない**——
    これは §5-3 で繰り返し記録してきた型（「そのままでよい」と述べた箇所の
    検証が甘い／新設した規則を自分に当てきれない）の、もう一段ひどい版である。

  ■ 観点表への反映

    docs/review_checklist.md §5-3 に以下を追加した。

      5-3-6 **自分が書いたコードブロック・コマンドは、実行順に1行ずつ辿る。**
            指示文・対処案に載せるコード断片は、**レビュー対象の文書と
            同じ基準**（2-9・3-2）で検証する。とくに
            ①**依存の導入前に import しているもの**
            ②**前段の出力・副作用に依存するもの**
            ③**環境に無いコマンド・ファイルを前提にしているもの**
            は順序と前提を確認する。
            （失敗例：SEC-1 §4 で `Show versions`（`import certifi`）を
              `pip install -r` の**前**に置いた。certifi は
              `requirements.txt` 経由でしか入らないため必ず落ちる）

      5-3-7 **「Xを確認して、足りなければYする」と書くときは、
            Xが動くことを先に確かめる。**
            確認ステップが壊れていれば、Yは永久に起きない。
            条件分岐の根拠を別のステップに委ねる書き方は、
            **そのステップの健全性まで込みで1つの指示**である。
            （失敗例：`python-version: '3.11'` の妥当性判定を
              `Show versions` の出力に委ねたが、その `Show versions` が
              落ちる書き方だった。実測は 3.11.17 ＝基準未満）

  ■ 効いた指示も記録する

    §5-1 で「**`render.yaml` の現在の内容を全文読み、そのまま報告する。
    Takumi様が確認し、指示を受けてから編集する**」とした点は機能した。
    その過程で **`ENABALE_SCHEDULER`（誤字）** が発見されている（発見事項③）。
    **編集前に全文を読ませる**指示が、1か月生きていた本番の不整合を
    掘り当てた。

    「python 3.11.18 以降／pip 26.2.2 以降／certifi 2026.10.19 以降であること」
    と**基準は正しく書いている**。しかし**設定値がその基準を満たさない**。
    コメントと値が食い違っている（観点表2-9）。

  【問題3：本書の位置づけに反する】

    §0 の位置づけ（v0.5）は
    「v0.4 までは『実装前の設計』だった。7-A の製造で**設計…**」

      2026-10-29        製造検証ログに発見事項①〜④を記録
      →                 **本書への差し戻しが行われていない**

    B区分（設計書）を A区分（実装）より**先に**終わらせたため、
    実装で判明した訂正を受け取る機会が無かった。

  【対処】§3-3 のコードブロックを実装に合わせる。

          - uses: actions/setup-python@v5

          - run: pip install -r app/backend/requirements.txt

  【問題：誤字を発見する手段が設計側に無かった】

    製造検証ログ 2026-10-29 の発見事項③：

      「③`render.yaml` のキー名が **`ENABALE_SCHEDULER`（誤字）**だった
        → `ENABLE_SCHEDULER` に修正」

    本書§2-4-3 の実装は

      `os.getenv("ENABLE_SCHEDULER", "true").lower() != "false"`

    であり、**未設定なら `true`** である（§2-6 の注記・基本設計書§5-3 の
    「既定値 true」）。したがってキー名が `ENABALE_SCHEDULER` であった間、
    本番 Render Web Service では

      ・`_scheduler_enabled()` が **True** を返す
      ・**APScheduler が起動**（`scheduler.start()`）
      ・**起動時バッチが実行**（`check_and_run_batch()`）

    していたことになる。基本設計書§5-3 は「本番（要望1採用時）＝ `false`」と
    **設計では決めている**。**設計は正しく、設定が設計どおりでなかった。**

    影響の見立て（当方の推定。実測は Takumi様の確認を要する）：

    | 観点 | 影響 |
    |------|------|
    | 記事の二重取得 | **抑制されていた可能性が高い**。`check_and_run_batch()` は `last_fetched_at` の4時間ゲートを通る（§2-4-3・CLAUDE.md）ため、GitHub Actions が先に走っていればスキップされる |
    | Neon の CU-hours | **余計に消費していた**。スピンダウン復帰のたびに起動時バッチが DB に接続する。無料枠は 100 CU-hours/月（CLAUDE.md） |
    | APScheduler の常駐 | 10分ごとにチェックが走る（CLAUDE.md のローカル挙動）。スピンダウンする無料プランでは起きている間だけだが、**設計の意図と異なる状態**が継続していた |
    | 期間 | `render.yaml` に `ENABLE_SCHEDULER` を書いた時点（7-A-10 の移行作業と推定）から **2026-10-29 まで** |

  【なぜ 🟡 か】

    本書の記述に誤りがあるわけではない。§2-4-3 の設計も、
    基本設計書§5-3 の「本番は false」も正しい。
    欠けているのは「**その設定がどこに書かれ、どう検証されるか**」である。

    設計が正しくても、**設定の所在が設計に無ければ、設定の誤りは
    設計レビューでは見つからない**。実際、当方も7-A 以降のレビューで
    `render.yaml` を一度も対象にしていない（アクセス範囲外でもあった）。

  【対処案】

    案A（推奨）: **§3-6「`render.yaml`（変更）」を新設する。**

      最低限、本番で設定する環境変数の**キー名と値**を表にする。

      | キー | 値 | 根拠 |
      |------|-----|------|
      | `ENABLE_SCHEDULER` | **`false`** | §2-4-3・基本設計書§5-3。**未設定なら true になるため、キー名の誤記はそのまま「有効」になる** |
      | `PYTHON_VERSION` | **`3.11.18`** | SEC-1（§3-3 と同じ基準） |
      | `HOST` | `0.0.0.0` | CLAUDE.md |
      | `ALLOWED_ORIGINS` | （Static Site の URL） | §2-4-1 |
      | シークレット6件 | **`sync: false`**（値は書かない） | CLAUDE.md |

      **`ENABLE_SCHEDULER` の行には「未設定＝true」であることを必ず添える。**
      既定値が安全側でない（＝誤記が「有効」に倒れる）設定は、
      **その性質を設定表に書いておかないと誤記に気付けない**。

      あわせて CLAUDE.md の 🔴 警告（Blueprint sync はダッシュボードの値を
      `render.yaml` で上書きする／編集は最小回数に）を注記として引く。

    案B        : 基本設計書§5-3 の表に「本番の設定先＝`render.yaml` の
                 `envVars`」とだけ書き、詳細設計書には節を設けない。
                 → `batch.yml` を全文載せている本書の構成と揃わない。
                   また `PYTHON_VERSION` の置き場所が記録されない。

    → **案Aを推奨する。** あわせて検証手段をテスト設計書へ引き継ぐ
