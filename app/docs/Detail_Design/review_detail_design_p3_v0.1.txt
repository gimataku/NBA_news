  🔴 DD-R-01：`App.jsx` の変更が設計されていない。
              F-13 と F-15 が画面につながらず、素直に実装すると実行時に落ちる

  【該当】§1 フロントエンド詳細設計（§1-1〜§1-6 に `App.jsx` の節がない）

  【事実】

    (1) `App.jsx` は `NewsCard` を描画する唯一のファイルである。

        $ grep -n "NewsCard\|useNews" frontend/src/App.jsx
          2:  import { useNews } from './hooks/useNews';
          7:  import { NewsCard } from './components/NewsCard';
         51:  } = useNews(token, logout);
         88:  <NewsCard
         92:    isRevealed={revealedIds.has(article.id)}

    (2) 本書は `useNews.js` の戻り値に**4件を追加**する（§1-1-4）。

          expandedIds / relatedExpandedIds / toggleExpand / toggleRelatedExpand

    (3) 本書は `NewsCard` の props に**7件を追加**する（§1-4-1）。

          isExpanded / onToggleExpand / articles /
          relatedExpandedIds / onToggleRelated / revealedIds / isNested

    (4) (2) を (3) に渡せる場所は **`App.jsx` L88-92 しかない**。
        しかし本書には `App.jsx` の節がない。

  【問題1：機能が動かない】

    `App.jsx` を変更しなければ `isExpanded` は `undefined` になる。
    §1-4-2 の描画は `{isExpanded && (...)}` であるため、
    **すべての記事が永久に折りたたまれたまま**になる。
    F-13（本文の展開表示）と、その内側にある F-15（関連ニュース）が
    **1行も画面に現れない**。しかも例外は出ないため、
    「実装したのに何も起きない」という形で現れる。

  【問題2：素直に実装すると実行時に落ちる】

    実装者が `App.jsx` を自力で書く場合、`useNews` の
    `relatedExpandedIds`（**`Map<number, Set<number>>`**・§1-1-1）から
    `NewsCard` の `relatedExpandedIds`（**`Set<number> | undefined`**・§1-4-1）へ
    変換する必要がある。自然な書き方は次である。

        relatedExpandedIds={relatedExpandedIds.get(article.id)}

    ここで **`Map` にキーが無ければ `undefined` が返る**。
    そして「キーが無い」は例外ではなく**通常状態**である——
    §1-1-2 の `toggleRelatedExpand` は
    `next.size === 0 ? nextMap.delete(parentId) : ...` と書かれており、
    **展開されている子が0件のときはエントリを持たない**設計だからである。
    つまり**記事を初めて展開した瞬間は必ず `undefined`** である。

    一方 `RelatedNews`（§1-5）は受け取った値を**無条件に参照する**。

        isExpanded={expandedChildIds.has(a.id)}       ← §1-5 L484相当

    → `TypeError: Cannot read properties of undefined (reading 'has')`
      が、**関連ニュースを持つ記事を最初に展開した時点**で発生する。
      React のエラーバウンダリが無いため、**画面全体が白くなる**。

    §1-4-1 は型を `Set<number> | undefined` と**明示的に nullable と宣言**して
    いるにもかかわらず、§1-5 は既定値を持たない。そして両者をつなぐ
    §1-4-2 の `<RelatedNews ... />` は **`...` で省略されている**。
    **nullable が生まれる場所と、それを潰すべき場所の両方が本書にない。**

  【なぜ🔴か】

    ・本書§0-1 は自らの位置づけを「**実装者がそのまま書けるところまで
      具体化する**」と定めている。その基準で目的未達である。
    ・影響が F-13・F-15 という**本フェーズの主要2要件の全体**に及ぶ。
    ・「うっかり省略した」ではなく**3文書が一貫して `App.jsx` は変更対象外
      だと述べている**（下記）ため、実装時に自然に気付く仕組みがない。

        基本設計書§1-2  : コンポーネント一覧11件に `App.jsx` が無い
        本書§1          : `App.jsx` の節が無い
        テスト設計書§1-2-2/§1-3 : 「`App.jsx` は改修対象外（`useNews` の
                          戻り値を各コンポーネントへ渡すだけ）」と明記し、
                          **カバレッジ計測からも明示的に除外**している

      3文書が同じ前提を共有しているため、**どの工程でも検出されない**。
      基本設計書 v0.6 の DD-01（CORS の `PUT`）が🔴とされたのと
      同じ性質——「そのまま実装すると動かない」——であり、
      影響範囲は DD-01 より広い。

  【対処案】

    案A（推奨）: 本書に **§1-7 `App.jsx`（変更）** を新設する。
                 最小限、次の3点を確定させる。

                 ① `useNews` の戻り値の受け取り（4件）
                 ② `NewsCard` への props の受け渡し（7件）
                 ③ **`Map` → `Set` の変換と既定値**
                    `relatedExpandedIds={relatedExpandedIds.get(article.id) ?? EMPTY_SET}`
                    ※`EMPTY_SET` はモジュールスコープの
                      `const EMPTY_SET = new Set()`。
                      毎回 `new Set()` を書くと**参照が毎描画で変わり、
                      `NewsCard` のメモ化が効かなくなる**ため定数にする。

                 あわせて **§1-5 側にも既定値を置く**
                 （`expandedChildIds = EMPTY_SET` のデフォルト引数）。
                 呼び出し側と受け側の両方で潰しておけば、
                 将来 `App.jsx` 以外から使われても壊れない。

    案B        : `RelatedNews` に `relatedExpandedIds`（Map）と `parentId` を
                 そのまま渡し、変換を `RelatedNews` の内部で行う。
                 → 変換箇所が1つになり、`App.jsx` は単純な受け渡しに戻る。
                   ただし §1-4-1 の props 定義（`Set<number> | undefined`）を
                   変更することになる。

    案C        : `useNews` 側で `relatedExpandedIds` を
                 「キーが無ければ空 Set を返す」形（Proxy／getter関数）にする。
                 → フックの戻り値の型が複雑になる。推奨しない。

    ※ どの案を採っても、**`App.jsx` の節を設けること自体は必要**である。
      変換をどこで行うかに関わらず、戻り値と props をつなぐコードは
      `App.jsx` に書かれるためである。

  【波及】

    ・基本設計書§1-2 のコンポーネント一覧に `App.jsx` を追加する
      （本書§6 に「基本設計書の次版」への引き継ぎとして記録する。
      DD-01／DD-02 と同じ扱い。以下 **DD-03** と呼ぶ）。

3. 検証したが指摘に至らなかった事項（記録）
--------------------------------------------------------------------------------

  観点表§3（深度確認）を当てた結果、**指摘候補として立てたが取り下げた**
  ものを記録する。後の版で同じ疑義が出たときに再検証しないためである。

  ■ 3-1. §3-4 の `connect_args={"check_same_thread": False}` の削除

    【疑義】§3-4 は `connect_args` を**無条件に削除**しつつ、既定値を
            `"sqlite:///nba_news.db"` として「未設定時にローカルSQLiteで
            動く現行の挙動を維持する」としている。
            本アプリは APScheduler のワーカースレッドと FastAPI の
            両方から同一エンジンを触るため、`check_same_thread` が
            効くとローカル実行が
            `ProgrammingError: SQLite objects created in a thread can only
            be used in that same thread` で落ちるのではないか。

    【検証】実際に確認した（SQLAlchemy 2.0.52）。

      $ python3 -c "import sqlalchemy as sa;
                    e=sa.create_engine('sqlite:////tmp/t2.db');
                    print(e.dialect.create_connect_args(e.url))"
        (['/tmp/t2.db'], {'check_same_thread': False})   ← 自動で付く

      $ 別スレッドからプール経由で接続を再利用 → **OK**（例外なし）
      $ 素の sqlite3 で同じことをすると → ProgrammingError（比較対照）

    【結論】**SQLAlchemy 2.0 は file-based SQLite に対し
            `check_same_thread=False` を自動的に付与する**。
            したがって `connect_args` の削除は安全であり、
            §3-4 の記述は正しい。**指摘を取り下げる。**

            ただし `requirements.txt` の `sqlalchemy` は**版が無指定**である。
            この挙動は SQLAlchemy 2.0 系の仕様であり、
            1.x に戻した場合は前提が変わる。移行時に版を下げないこと。

  ■ 3-2. §2-1-1 の `slowapi` の API 面

    【疑義】`slowapi` は `requirements.txt` に未導入であり、
            本書が使う API（`Limiter` / `_rate_limit_exceeded_handler` /
            `RateLimitExceeded` / `get_remote_address`）が実在するか
            訓練データの知識で判断していないか。

    【検証】サンドボックスに `slowapi` を導入して確認した（2026-09-06）。

        from slowapi import Limiter, _rate_limit_exceeded_handler   → OK
        from slowapi.errors import RateLimitExceeded                → OK
        from slowapi.util import get_remote_address                 → OK
