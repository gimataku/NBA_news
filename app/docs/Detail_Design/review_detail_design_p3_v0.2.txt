  🟢 DD2-01：§2-1-1 の `main.py` コードブロックが、直下の注記に従っていない。

  ────────────────────────────────────────────────────────────────────────────

  【該当】§2-1-1『F-17：ログインのレートリミット』（v0.1 から変更なし）

  【事実】同一節に、互いに食い違う2つの記述がある。

    (A) コードブロック（`main.py` 側）:

        from slowapi import Limiter, _rate_limit_exceeded_handler
        from slowapi.errors import RateLimitExceeded
        from slowapi.util import get_remote_address

        limiter = Limiter(key_func=get_remote_address)   ← **ここで生成している**
        app.state.limiter = limiter
        app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

    (B) その直下の注記:

        「`limiter` は独立モジュール（`api/limiter.py`）に置き、
          **`main.py` と `routes.py` の両方がそこから import する。**」

    (A) は `main.py` で新しい `Limiter` インスタンスを作る。
    (B) は `api/limiter.py` の1つを共有せよと言う。**両立しない。**

    加えて `api/routes.py` 側のコードブロックにも不足がある。

        from config import LOGIN_RATE_LIMIT      ← これだけ

        @router.post("/auth/login")
        @limiter.limit(LOGIN_RATE_LIMIT)         ← `limiter` が未 import
        async def login(request: Request, ...):  ← `Request` が未 import

      実物（`api/routes.py` L1）:
        from fastapi import APIRouter, BackgroundTasks, Depends, HTTPException,
                            Query, status
        → **`Request` は含まれていない。**

      つまり `from fastapi import ... Request` と
      `from api.limiter import limiter` の2行が必要だが、
      **どちらもコードブロックに現れない**（前者は注記にすら無い）。

  【影響 ── 実測して確認した】

    `slowapi` をサンドボックスに導入して挙動を確認した（2026-09-06）。

    | 論点 | 結果 |
    |------|------|
    | `@limiter.limit()` の判定に使われる限界値 | **デコレータ側の `limiter`**（`self`）。`api.limiter` の実体が正しく数える |
    | `_rate_limit_exceeded_handler` | `request.app.state.limiter._inject_headers(...)` を呼ぶ ── **`app.state` 側を読む** |
    | `_inject_headers` の中身 | `if self.enabled and self._headers_enabled and ...` |
    | `_headers_enabled` の既定値 | **`False`** |

    → **既定設定では `_inject_headers` は何もせずレスポンスを返す**ため、
      インスタンスが2つあっても**現状は機能差が出ない**。
      `app.state.limiter` が存在はするので `AttributeError` にもならない。
      **したがって重要度は🟢である。**

    ただし次の2点で無害とは言い切れない。

      (1) **テストと本番で構成が食い違う。**
          テスト設計書§2-0 #1 はフィクスチャに
          `app.state.limiter = limiter`（**`api.limiter` から import**）を
          設定し、#3 は `from api.limiter import limiter; limiter.reset()` で
          カウンタを初期化する。
          本番の `main.py` が別インスタンスを持つなら、
          **テストが検証しているのは本番と異なる構成**である。
          これは **TD-R-01 で是正したばかりの問題と同じ型**である
          （テストが本番の実体を読んでいない）。

      (2) 将来 `Limiter(..., headers_enabled=True)` に変えたとき、
          `app.state` 側の**空のストレージから残り回数を計算する**ため、
          クライアントに誤った `X-RateLimit-Remaining` を返す。

  【対処】§2-1-1 の2つのコードブロックを、注記の内容に合わせる。

      # main.py 側
      from slowapi import _rate_limit_exceeded_handler
      from slowapi.errors import RateLimitExceeded
      from api.limiter import limiter          # ← 生成せず import する

      app.state.limiter = limiter

      # api/routes.py 側

4. 検証したが指摘に至らなかった事項（記録）
--------------------------------------------------------------------------------

  ■ 4-1. §1-1-4 の「既存の13項目」と §1-7-2 ② の「既存12件」

    【疑義】同じ `useNews` について、件数が2箇所で食い違っている。

    【検証】実物を確認した。

      $ grep -n "return {" -A 20 frontend/src/hooks/useNews.js
        L103-117: articles / apiStatus / selectedCategory / spursOnly /
                  spoilerGuard / revealedIds / loading / setSelectedCategory /
                  toggleSpursFilter / toggleSpoilerGuard / revealScore /
                  resetSpoiler / **fetchArticles**   → **13件**

      $ sed -n '38,51p' frontend/src/App.jsx
        articles 〜 resetSpoiler の **12件**（`fetchArticles` は受け取らない）

    【結論】**両方とも正しい。指摘なし。**
            §1-1-4 は**フックの戻り値**（13件）、
            §1-7-2 ② は**`App.jsx` の分割代入**（12件）を指しており、
            数える対象が違う。`App.jsx` が `fetchArticles` を使わないため
            分割代入が1件少ない。

  ■ 4-2. §1-5 が入れ子の `NewsCard` に `articles` / `revealedIds` /
          `relatedExpandedIds` / `onToggleRelated` を渡していない

    【疑義】入れ子カードでこれらが `undefined` になり、参照時に落ちないか。

    【検証】§1-4-2 の描画条件を読んだ。

        {!isNested && !needsSpoiler && (<RelatedNews ... />)}

      入れ子カードは `isNested={true}` を受け取るため、
      **`!isNested` で短絡し、`articles` 等は評価されない**。
      `NewsCard` 本体でこれらを参照する箇所は
      `RelatedNews` への受け渡しのみである（§1-4-1 のコメントで用途が明示）。

    【結論】**落ちない。指摘なし。**
            `isNested` を条件の**先頭**に置いていることが効いている。
            順序が入れ替わると `articles` が先に評価されるが、
            §1-4-2 のコードブロックは正しい順序で書かれている。

  ■ 4-3. §1-7-3 の「`import main` は `startup_event()` を走らせない」前提

    【疑義】テスト設計書 T-P3-05 の案B 却下理由・案C 保留の根拠になっている。
            `main.py` を import した時点でスケジューラが起動するなら、
            案Bはそもそも成立しない。

    【検証】`backend/scheduler.py` のモジュールレベルを確認した。

      L252  scheduler = BackgroundScheduler()
      L253  scheduler.add_job(check_and_run_batch, "interval", ...)
      L254  scheduler.add_job(check_and_run_game_schedule_batch, "interval", ...)

      → **オブジェクト生成とジョブ登録のみ。`start()` は呼ばれていない**
        （`start()` は `main.py` L56 の `startup_event()` 内）。
        `startup_event()` は `TestClient` の **context 進入時**に走る。

    【結論】**§1-7-3・§2-4-1 の記述は正確。指摘なし。**
            `import main` するだけならスケジューラは起動しない。
            起動するのは `with TestClient(app)` に入ったときである。
            → この事実は**テスト設計書 TD2-01 の対処案**に使える
              （テスト設計書レビュー§3 参照）。

  ■ 4-4. §2-4-1 の `allow_headers` に `Origin` 等が無い

    【疑義】ブラウザが送る `Origin` や `Accept` が拒否されないか。

    【結論】**問題ない。** CORS の `allow_headers` は
            **プリフライトの `Access-Control-Request-Headers` に載る
            カスタムヘッダ**に対する許可リストである。
            `Origin`・`Accept`・`Content-Length` 等の
            CORS-safelisted request header は対象外。
            `Content-Type` は値によって safelisted から外れるため
            明示が必要であり、本書は正しく含めている。指摘なし。

  ■ 4-5. §2-7 の「`sqlalchemy` を2.0系から下げない」

    【検証】当方が v0.1 報告書§3-1 で記録した検証結果
            （SQLAlchemy 2.0.52 が file-based SQLite に
              `check_same_thread=False` を自動付与する）を
            v0.2 が制約として取り込んだもの。

    【結論】**正しい取り込み。指摘なし。**
            レビュー報告書の「指摘に至らなかった検証」まで読んで
            設計に反映している点を評価する。
