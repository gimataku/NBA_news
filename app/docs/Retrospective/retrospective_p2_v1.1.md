## 2. 良かったところ

### 2-1. フェーズ1の振り返り13項目がほぼ全て機能した

フェーズ1の反省を「プロセス改善の組み込み一覧」として計画書に明記し、各手順に紐付けて管理した。結果として13項目すべてが✅完了となった。特に効果が大きかったのは以下の3点。

**カバレッジ計測の標準化（項目12）** — 目標80%を事前定義したことで、テスト作成時に「どこまでやるか」の判断が不要になった。結果93〜94%を達成。

**結合テストの新設（項目5）** — フェーズ1にはなかった工程。IT-01〜IT-04の4件で、モジュール間のインターフェース（認証フロー・dedup→DB→API・UPSERT→API）を実コードで検証できた。単体テストだけでは発見できない結合部の問題を事前に潰せた。

**カテゴリ境界ケースの明示（項目11）** — 要件定義§3-2で境界条件（インジャリーレポート⇔FAコラム等）を先に定義し、総合テストのシナリオ4で5件全件を検証した。トライアル運用でカテゴリ分類精度が3週連続5/5だったのはこの前倒し定義の効果と考えられる。

### 2-2. トレーサビリティマトリクスが抜け漏れを実際に検出した

`traceability_matrix_p2_v1.0.md` の作成過程で、**計画書に存在しなかった2つの実装項目**（Render公開インフラ構築・F-12 NBA公式順位リンク）が発覚した。要件と実装の対応表を機械的に作る作業が、計画レベルの盲点を炙り出した好例。これがなければ製造完了と判定した後に発覚していた可能性が高い。

### 2-3. レビューの多重実施が設計品質を担保した

基本設計4回・詳細設計4回・計画書8回以上のレビューを回した。設計書全体で38件（🔴4・🟡20・🟢14）の指摘が出て全件対処済み。特に🔴致命4件は、いずれも製造前に発見できたため手戻りコストが小さかった。

### 2-4. 中止基準を事前に数値で定義していた

「月次コスト200%超」「翻訳品質30%超が意味不明」など、撤退ラインを数値で先に決めていたため、トライアル運用の判定が主観に依存しなかった。A-2がNG判定でも「中止基準には該当しない」と機械的に判断でき、感情的な迷いが入らなかった。

### 2-5. オフシーズン制約を早期に切り分けた

`has_score=true` の実データが発生しないという環境制約を、手順9の時点で「確認不能」と正しく認識し、ブロッカーにせず10月開幕後に先送りする判断を明示的に承認・記録した。制約を曖昧にせず文書化したことで、後工程で蒸し返しが起きなかった。

### 2-6. 独立したセキュリティレビューを実施し🔴致命ゼロを確認した

JWT認証という**新規の攻撃面を追加したフェーズ**で、実装完了後に独立したセキュリティレビュー（`security_review_p2_v1.0.txt`）を実施した。結果は🔴致命0件・🟡要改善4件・🟢軽微4件で、以下を含む14件の肯定的確認が取れている。

- SQLインジェクション不成立（SQLAlchemy ORM経由）
- `dangerouslySetInnerHTML` 不使用（XSS面の遮断）
- JWTトークンのメモリ保持（localStorage/cookie不使用）
- `alg:none` 攻撃の遮断

これは**フェーズ1振り返り13項目に含まれていなかった新規の良い実践**である。認証を伴う機能を追加する場合、セキュリティレビューをフェーズ3の標準工程に昇格させる価値がある。

### 2-7. 数値で撤退ラインを引いたことが判断コストを下げた（2-4の補強）

3週間のトライアル運用で翻訳品質A-2が2週連続NGとなったが、「意味の取れない翻訳が30%超」という中止基準に照らして機械的に「該当なし」と判定できた。**定性的な不満と定量的な撤退基準を切り離していた**ことで、個人開発にありがちな「なんとなく気になるから作り直す」という判断の揺れを回避できた。

## 3. 改善点

### 3-1. 【重要】ドキュメント同士の整合性チェックが人力依存だった

**事象**: v1.7でサブ手順を7-J-0〜7-J-4にrenumberingした際、`traceability_matrix_p2_v1.0.md` 側の「7-J」表記が追従せず、次回レビュー（YEL-01）で指摘された。

**原因**: 複数ドキュメント間で同じ識別子を参照しているのに、更新箇所の洗い出しが目視だった。

**教訓**: §8バージョン管理ルールに項目4として追記して再発防止としたが、そもそも `grep -rn` による横展開確認を**バージョンアップ手順の必須ステップ**にすべきだった。

### 3-2. 【重要】プロジェクトドキュメント（README/CLAUDE.md）の追従更新が工程に存在しなかった

**事象**: 7-A〜7-I の実装完了後に、`README.md`・`CLAUDE.md` がフェーズ1当時の内容のまま放置されていたことが発覚（v1.5）。特に `CLAUDE.md` の「`host="127.0.0.1"` で起動（外部公開禁止）」という記述は、これから実装する `host="0.0.0.0"` 化と正面から矛盾しており、AIコーディング支援ツールを混乱させるリスクがあった。

**原因**: フェーズ1振り返りの13項目に「機能改修時にプロジェクトドキュメント一式を追従更新する」というチェックが含まれていなかった。設計書は更新対象として認識されていたが、README/CLAUDE.mdは「開発の副産物」として意識の外にあった。

**教訓**: AIコーディング支援ツールが自動参照する設定ファイル（CLAUDE.md等）は、**設計書と同格の更新対象**として扱う必要がある。矛盾した指示が残っていると実装フェーズで実害が出る。

### 3-3. 監視設計が「ローカル前提」のまま本番に持ち込まれた

**事象**: トライアル運用の週次チェックリスト v1.0 が、`python main.py` での起動・`logs/nba_news.log` の参照・`monitor.py` の実行を前提としていた。しかし本番はRender上で稼働しており、`monitor.py` はローカルSQLite DBを直接参照する設計のため**本番DBに接続できない**ことが実施直前に判明した。

**原因**: フェーズ1の運用チェックリストを流用した際、「ローカル運用 → クラウド運用」というアーキテクチャ変更が運用ドキュメントに反映されていなかった。計画書§2で「インフラ変更の断絶」をガイドラインとして明記していたにもかかわらず、その観点が**設計・実装フェーズには適用されたが運用フェーズには適用されなかった**。

**教訓**: アーキテクチャ変更時は、設計書・コードだけでなく**運用手順書・監視ツールも差分レビューの対象**に含める。「このドキュメントはどの環境を前提にしているか」を明示的に問う工程が必要。

### 3-4. 本番環境の可観測性（Observability）が不足している

**事象**: 総取得記事数を確認しようとした際、`/api/news` のレスポンスがページネーションで50件固定のため正確な総数がわからず、Render Web Shell からSQLiteに直接クエリを投げる必要があった。しかもDBパスの解決に失敗し、その場では取得できなかった。

**原因**: 「運用時にどんな数値を見たいか」を設計段階で定義していなかった。`/api/status` は last_fetched_at・api_limit_exceeded しか返さない。

**教訓**: 運用フェーズで必要な指標（総記事数・カテゴリ別件数・直近N日の取得数・エラー件数）を**要件定義の段階で洗い出し**、専用のステータスエンドポイントとして設計に組み込むべきだった。後から取りに行くのは高コストになる。

### 3-5. 翻訳品質の合格条件が主観的すぎた

**事象**: A-2「summary_ja が自然な日本語か」の合格条件が「読了に支障がないレベル」という定性表現だったため、選手名の表記ゆれ（ヒーロー→ヘロ、ヤニス→ギアニス）を理由に2週連続でNG判定となった。しかし中止基準の「意味の取れない翻訳が30%超」には全く届かず、**判定結果と実質的な深刻度が乖離**した。

**原因**: 合格条件の粒度が粗く、「意味が通じない」と「表記が慣例と違う」を区別できなかった。

**教訓**: 品質基準は「機能する／しない」と「好ましい／好ましくない」を分離して定義する。前者は合否判定、後者は改善バックログとして扱うべき。

### 3-6. 不要ファイル削除がバッチ実行できなかった

**事象**: 本番移行前のクリーンアップで31ファイルを削除しようとしたが、サンドボックスから対象フォルダへの書き込み権限がなく、PowerShellコマンドを手動実行してもらう形になった。

**より重大な副作用**: このクリーンアップで個別レビューファイル（`review_project_plan_p2_v*.txt` 等）を削除したため、手順11で作成した `review_management.md` は計画書の変更履歴からの**再構成**にならざるを得なかった。結果、指摘件数集計が「複数件」「20件以上」と粒度が落ち、正確な件数を復元できなくなっている。

**教訓**: クリーンアップを工程として計画に組み込むべきだったことに加え、より強く言うべきは **「レビュー記録・検証記録は削除対象から除外する（＝それらは成果物である）」**。一時ファイルと成果物の境界を、削除実行前に明示的に定義する必要がある。

### 3-7. 【重要】セキュリティレビュー指摘の対応追跡が存在しない

**事象**: `security_review_p2_v1.0.txt` で🟡要改善4件・🟢軽微4件が指摘されているが、その後の対応状況がどのドキュメントにも追跡されていない。`document_baseline_p2.md` の残課題一覧にも記載がない。

**特に運用リスクとして残っている2件**:

| ID | 内容 | リスクの性質 |
|---|---|---|
| YEL-01 | `ANTHROPIC_API_KEY` / `BALLDONTLIE_API_KEY` が空でも起動時エラーにならない | `SECRET_KEY` のみRuntimeErrorを投げる**非対称な設計**。環境変数の設定漏れが「起動はするが記事が翻訳されない」という気付きにくい故障として現れる。`config.py` に3行追加で完結 |
| YEL-02 | `/api/auth/login` にレートリミットがない | 本アプリは公開URL上にあり、JWT認証が唯一の防壁。認証は**セキュリティ目的ではなく著作権法第30条の公開範囲担保が主目的**（計画書§6制約）である以上、ブルートフォース耐性の欠如は「技術的な脆弱性」ではなく**法的前提を崩すリスク**として整理し直すべき |

**教訓**: レビューを実施しただけでは価値が確定しない。**指摘 → 対応要否判断 → 記録**までを1セットとして工程に組み込む。特にYEL-02のように、指摘の重要度が「技術的観点」と「プロジェクトの前提（法的要件）」で変わる場合、後者の観点で再評価する工程が必要。

### 3-8. 【重要】チェックリストが観測値を記録しない設計だった

**事象**: 週次チェックリストのD-1〜D-3は「$5.10以内であること → OK」のように**判定結果しか残らず、実額を記録する欄がない**（G章のサマリーに一部あるのみ）。結果として以下の問題が生じた。

- `document_baseline_p2.md` のコスト表の数値の出典が追跡できない
- 上記R-3の数値不整合（$7.25がRender固定費のみの疑い）をチェックリスト側で検出できなかった
- 3回分のデータがあるのに**トレンド分析ができない**。$1.27→$1.54→$1.72と単調増加しているが、記事数の増加なのかプロンプト長の変動なのか判断材料がない

**原因**: 3-4（可観測性不足）と同根だが、こちらは**ドキュメント側の問題**。「基準を満たすか」だけを問い、「実際の値はいくつか」を残す設計になっていなかった。

**教訓**: チェックリストは**「合否」と「観測値」を両方記録する**。合否だけを残すと、基準そのものの妥当性を後から検証できなくなる。指標は**取得手段（API）と記録欄（チェックリスト）をセットで設計する**。

### 3-9. 死活監視の自動化が構造的に機能していない

**事象**: 本運用移行に伴い設定した週次死活監視スケジュールタスクは、バックエンド `/api/status` に対して**サンドボックスのネットワーク制限により構造的に到達不可**であり、毎回「⚠️ 要確認」が記録され続ける状態にある。

**原因の誤認**: 当初、私はこれを「ツール承認の問題」と捉え、対策として「Run nowで権限を事前承認する」をネクストアクションに挙げていた。しかし**根本原因は権限ではなく到達性**であり、承認を済ませても⚠️は出続ける。対症療法だった。

**より深刻な副作用**: 「毎回⚠️が出る監視」は**アラート疲れを誘発し、本物の障害を見逃す**という運用上の典型的失敗パターンに該当する。監視として成立していないだけでなく、有害ですらある。

**教訓**: 監視を設計する際は「**その方式で実際に観測できるか**」を先に検証する。観測できない対象を監視項目に含めると、ノイズを生むだけで監視の信頼性全体を毀損する。監視できないものは「監視対象外」と明示的に宣言する方が誠実。
