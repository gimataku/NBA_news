【🟡 要改善（1件）】

[YEL-01] 成否判定（案A）を採用した後に「何が検知できるようになったか」が
         整理されておらず、失敗4種のうち1種しか拾えない

  対象箇所: §5-2「成否判定に `fetch_logs` を使う根拠」／ §6-2-2「ping の位置」

  §5-2 は失敗を4種に分解し、「例外になるか」を表にしている。これは正確である。

      #1 RSS全ソース失敗      → `scheduler.py` L60-70 で早期リターン  ❌例外にならない
      #2 試合日程取得の失敗    → L190-244 の try/except で握りつぶす   ❌例外にならない
      #3 Claude API RateLimit  → `api_limit_exceeded=true` で continue  ❌例外にならない
      #4 DB接続失敗            → `init_db()`/`crud` から送出            ✅例外になる

  そして案A（`fetch_logs` の最新レコードの `error_message` で判定）を採用した。

  問題:
    **案Aを適用した結果、4種のうちどれが検知できるようになったかが書かれていない。**
    実装を追うと次のようになる。

      #1 RSS全滅       → L63 で `error_message` を記録 → ✅**検知できる**
      #2 試合日程失敗  → `fetch_logs` に記録しない     → ❌検知できない
      #3 RateLimit     → `error_message` は NULL のまま → ❌**検知できない**
      #4 DB障害        → 例外 → 非ゼロ終了            → ✅検知できる

    **案Aで新たに拾えるようになったのは #1 のみ**である。
    §6-2-2 の採用根拠#2（「バッチが止まる全ての原因を検知できる」）に対する
    v0.3 の課題は、#1 について解消し、#2・#3 は残っている。

    (a) **#2 の除外理由の一部が不正確**

        §5-2 の注記:
          「`run_game_schedule_batch()` は `fetch_logs` に記録しない。
            記事取得が主目的であり、試合日程の失敗は記事の鮮度に影響しない
            ため、成否判定には含めない。
            **オフシーズンには試合データ自体が存在しないため、
            これを失敗とみなすと常時アラートになる**」

        後半が事実と合わない。試合が0件の場合、
        `run_game_schedule_batch()` は例外を出さず
        `logger.info("Game schedule fetched: 0 games")` で正常終了する
        （`scheduler.py` L191-243 の try 内で完走する）。
        したがって成否判定に含めても**常時アラートにはならない**。

        実際に検知できないのは **BALLDONTLIE API 障害・DB書き込み失敗**であり、
        これは「オフシーズンだから」ではなく
        「**関数が例外を握りつぶし、`fetch_logs` にも記録しないから**」である。

    (b) **#2 が全く検知されない状態であることが明示されていない**

        要件定義書 §4-1 の運用指標9件に、試合日程に関する指標はない。
        一方 `last_schedule_fetched_at` は `AppSetting` に既存であり
        （`scheduler.py` L239 で更新）、
        **指標化すれば `last_fetched_at` と同じ方法で停滞を検知できる**。

        試合日程が古いままだと、要望2で改修する試合日程タブ（C-05）と
        Section C の C-5（試合日程タブの `has_score` 反映確認）に影響する。

    (c) **#3 に触れていない**

        §5-2 の表 #3 は「例外にならない」とだけ書かれ、
        案A適用後も検知できないことに触れていない。
        `api_limit_exceeded` は `/api/status` の既存フィールドであり
        週次チェックリストで確認できるが、**主の監視では拾えない**。

    (d) **§6-2-2 の「ping の位置」行が §5-2 と矛盾している**

        §6-2-2「外部cron監視の設計」:
          | ping の位置 | `run_batch_once.py` の末尾
                         （`run_batch()` と **`run_game_schedule_batch()` が
                           両方成功した後**） |

        この行は v0.3 のままである。
        §5-2 は「試合日程は成否判定に含めない」と決めたため、
        **「両方成功した後」は成立しない**（試合日程が失敗しても ping する）。

  推奨対応:
    ・§5-2 の表に「**案A適用後に検知できるか**」の列を追加する。
        #1 ✅ ／ #2 ❌（意図的に除外・理由は下記）／ #3 ❌ ／ #4 ✅
      4種を並べた表があるので、1列足すだけで適用範囲が一目で分かる。

    ・#2 の除外理由を書き直す。
        「試合日程の失敗は `fetch_logs` に記録されないため、
          案Aでは検知できない。記事取得が主目的であり、
          試合日程の鮮度は記事の鮮度に影響しないため、
          **本設計では意図的に除外する**。
          検知が必要になった場合は、`last_schedule_fetched_at`
          （`AppSetting` に既存）を運用指標に追加することで
          `last_fetched_at` と同じ方法で停滞を検知できる」
      「オフシーズンには常時アラートになる」の記述は削除する。

    ・#3（RateLimit）について1行添える。
        「案Aでは検知できない。`api_limit_exceeded` は
          `/api/status` の既存フィールドであり、週次チェックリストで確認する」

    ・§6-2-2 の「ping の位置」行を修正する。
        「`run_batch_once.py` の末尾（**§5-2の成否判定に合格した場合のみ**）」
      「両方成功した後」を削除する。

  重要度の根拠:
    案Aの採用そのものは正しく、`scheduler.py` に手を入れずに #1 を拾えるように
    なったことは実質的な改善である。
    問題は、**対処の適用範囲が書かれていないため、
    「これで全部拾えるようになった」と読めてしまう**点にある。
    §6-2-2 の採用根拠#2 が「全ての原因を検知できる」と書かれたまま残っており、
    v0.4 でもこの表現は修正されていない。
    手順10（トライアル運用）で監視の妥当性を評価する際、

[GRN-03] §8 の注記「#4・#13 は…採否確定後に着手する」が、
         割り当てられた手順（手順4・5）と噛み合っていない

  §8 の注記:
    「**#4・#5・#13 との違い**: これらも要望1依存だが**手順4・5に置いている**。
      **#4・#13は実装の準備**であり**採否確定後に着手する**（条件欄で明示）」

  フェーズ3の工程は 手順4（詳細設計）→ 手順5（テスト設計）→ **手順6（採否）** の順である。
  したがって「手順4・5に置く」ことと「採否確定後に着手する」は**両立しない**。

  各項目の実態を見ると次のようになる。

      #4  `/api/fetch` 関連テストの削除（手順5）
          → テストファイルの実際の編集。要望1が不採用なら
            `/api/fetch` は残るため、**削除してはいけない**
      #13 `run_batch_once.py` の成否判定の実装（手順4）
          → 「実装」とあるが手順4は詳細設計であり、
            設計としてなら採否前でも問題ない

  条件欄に「要望1採用時」と明示されているため、
  実施者が条件を見て判断すれば実害は生じない。
  **注記の表現だけが実態と合っていない。**

  → 注記を書き直す。例：
      「#4・#13 は**設計・準備までを手順4・5で行い、
