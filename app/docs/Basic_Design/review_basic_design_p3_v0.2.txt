[YEL-01] `run_batch_once.py` に `init_db()` が含まれておらず、
         移行の作業順序（リスク調査書 §1-4-9）の手順4が必ず失敗する

  対象箇所: §5-2 バッチのエントリポイント

  §5-2 の設計:

      | 新規ファイル | `backend/run_batch_once.py` |
      | 呼び出す関数 | **`run_batch()` と `run_game_schedule_batch()`**
                      （`check_and_run_*` は呼ばない） |
      | ジョブ構成   | 1ジョブで両方を順に実行 |
      | 終了コード   | 例外発生時は非ゼロ |

  **`init_db()` の呼び出しがない。**

  問題:
    リスク調査書 §1-4-9 の移行の作業順序は次の通りである。

        手順1  Neon プロジェクトを作成し接続文字列を取得（**データはまだ入れない**）
        …
        手順4  GitHub Actions ワークフローを作成し、`workflow_dispatch` で
               **初回バッチを走らせる**（**この時点でNeonに記事が入る**）
        …
        手順7  Render：環境変数の差し替え（`DATABASE_URL` を Neon 接続文字列に）
        手順8  Render：手動デプロイ ← **ここで初めて Render が Neon に接続する**

    **手順4の時点で、Neon にテーブルを作成した主体が存在しない。**
    Render はまだ SQLite を見ており（手順7が未実施）、
    `init_db()`（`Base.metadata.create_all`）が Neon に対して実行されていない。

    `run_batch()` の処理は先頭で設定を読む。

        # scheduler.py L52
        if crud.get_setting("api_reset_month") != current_month:

        # db/crud.py L9-12
        def get_setting(key: str) -> str:
            with SessionLocal() as session:
                row = session.get(AppSetting, key)
                return row.value if row else ""

    テーブルが存在しないため `session.get(AppSetting, key)` が
    `ProgrammingError: relation "app_settings" does not exist` を送出し、
    **バッチは1行も処理せずに落ちる**。
    §5-2 の設計どおり「例外発生時は非ゼロで終了」するため、
    GitHub Actions のジョブは失敗する。

    さらに `init_db()` は `create_all` に加えて
    `_INITIAL_SETTINGS`（`last_fetched_at`・`api_limit_exceeded` 等6件）を
    投入している。これも実行されない。
    （`get_setting` は行がなければ `""` を返し、`set_setting` は upsert であるため、
      **テーブルさえあれば初期レコードがなくても動く**。
      したがって致命的なのは `create_all` の欠落である。）

  推奨対応:
    ・§5-2 に `init_db()` の呼び出しを追加する。

        | 呼び出す関数 | **`init_db()`** → `run_batch()` → `run_game_schedule_batch()` |

      `init_db()` は冪等であり（§5-3 で確認済み）、
      毎回呼んでも既存テーブルを再作成しない。
      **バッチが単独で自己完結する**方が、
      「バッチはバッチの実行環境で動かす」という §5-4 の方針とも一貫する。

    ・`init_user()` は**呼ばない**。バッチは認証を使わず、
      §5-5（案A）で `INIT_USERNAME` / `INIT_USER_PASSWORD` の検証を
      `auth/users.py` へ移すため、バッチ層でこれらを要求しないことが設計の目的である。
      **`init_db()` だけを呼ぶ**という区別を明記する。

    ・あるいは移行手順の側で対処する案もある
      （手順1と手順4の間に「Neon にスキーマを作成する」ステップを挿入）。
      ただしその場合、**定常運用でもバッチはテーブルの存在に依存する**ことになり、
      Neon をリセットした場合などに同じ問題が再発する。
      **`run_batch_once.py` に持たせる方が堅い。**

  重要度の根拠:
    リスク調査書 §1-4-9 は移行の実行手順であり、手順4は
    「データ破棄（手順5）の前に Neon へ記事を入れる」という
    **移行全体の前提を作るステップ**である。ここが失敗すると、
    手順5に進めない（進めば記事0件の状態になる）。


[YEL-02] Levenshtein の JS 実装の式が指定されておらず、
         閾値0.20 / 0.35 の意味が実装依存になる

  対象箇所: §3-2（計算列）／ §3-4 ／ §8 #1

  §3-2 は基準2の計算を **`Levenshtein.ratio()`** と書いている。
  これは Python の `python-Levenshtein` パッケージの関数名である。

  一方 §3-4 は
    「バックエンドの `python-Levenshtein` は使えないため、
      **軽量な自前実装**（動的計画法・数十行）とする」
  とのみ述べ、**どの式で ratio を求めるかを指定していない**。
  §8 #1 も「Levenshtein の JS 実装（動的計画法・外部ライブラリを使わない）」で、
  式には触れていない。

  問題:
    `Levenshtein.ratio()` は素朴な正規化とは異なる定義を持つ。

        python-Levenshtein の ratio():
            置換コストを **2** として距離 ldist を求め、
            ratio = (len(a) + len(b) - ldist) / (len(a) + len(b))

        素朴な実装でよく使われる形:
            ratio = 1 - distance / max(len(a), len(b))
            （置換コストは 1）

    **長さが等しい文字列では両者は一致するが、長さが異なると乖離する。**
    例：`"NBA"`（3文字）と `"NBAドラフト"`（7文字）
        削除4回 → 素朴：1 - 4/7 = 0.571
                  python-Levenshtein：(3+7-4)/(3+7) = 0.600

    ニュースのタイトルは長さが揃わないため、この差は常に生じる。

    §3-2 が定めた**ゲート0.20と閾値0.35は、`Levenshtein.ratio()` の
    値域を前提に設定されている**（`DEDUP_THRESHOLD = 0.80` との比較で
    「十分低い水準」と根拠づけている。`dedup.py` は `Levenshtein.ratio()` を使う）。
    JS 側が別の式を採ると、**同じ0.35でも意味が変わる**。

    加えて `dedup.py`（重複排除・閾値0.80）と F-15（関連ニュース・閾値0.35）が
    **同じ尺度上にあることが前提**になっている。
    式が違えば、この対比も成り立たない。

  推奨対応:
    ・§3-4 に式を明記する。

        > **`python-Levenshtein` の `ratio()` と同じ定義を用いる**：
        > 置換コストを2として編集距離 `ldist` を求め、
        > `ratio = (len(a) + len(b) - ldist) / (len(a) + len(b))`。
        > `dedup.py`（閾値0.80）と**同じ尺度**にするため。

    ・§8 #1 の引き継ぎ内容にも式を含める。
      手順4で実装者が式を選べる状態にしておくと、
      **閾値を決めた根拠（本書 §3-2）が無効になる**。

    ・手順5（テスト設計・§8 #9）で、
      **Python 側と JS 側で同じ入力に対して同じ値が出ること**を
      確認するテストを設けると確実である。
      `dedup.py` のテストケースを流用できる。

  補足:
    「後工程（手順4）に委ねる」こと自体は妥当だが、
    **本書が閾値を決めた以上、その閾値が意味を持つ前提も本書で固定する**必要がある。
    実装の詳細（動的計画法の書き方・メモリ最適化）は手順4でよい。


[YEL-03] 60日自動無効化の検知が週1回の目視に依存しており、
         最大7日間バッチ停止に気付けない

  対象箇所: §6-2-2 要望1を採用する場合の監視方式

  §6-2-2 は監視対象を3つ挙げ、上2つを「主」としている。

      | **主** | バッチが動いているか | **GitHub Actions のワークフロー失敗通知**
                                        （標準機能・メール） | ジョブ失敗時に通知 |
      | **主** | バッチが止まっていないか（60日自動無効化の検知）
                | 週次チェックリストで `/api/status` の `last_fetched_at` を確認
                | 最終取得から**12時間以上**経過していたら異常 |
      | 従   | Webサービスの死活 | 401判定 | 補助的 |

  問題:
    (1) **1つ目の「主」は60日自動無効化では発火しない**
        自動無効化されるとワークフローは**実行されなくなる**。
        実行されなければジョブは失敗せず、失敗通知も飛ばない。
        つまり60日自動無効化に対して、1つ目の手段は無効である。
        （GitHub は無効化の前に通知メールを送るが、
          リスク調査書 §1-5 リスク2 はこれを「補助手段」と位置づけている。）

    (2) **2つ目の「主」は週1回の目視である**
        検知手段は `last_fetched_at` の停滞だが、
        確認するのは**週次チェックリスト**（週1回）である。
        閾値12時間は「**何をもって異常とするか**」の定義であり、
        「**どれだけ早く気付けるか**」ではない。
        実際の検知遅れは**最大7日**になる。

    (3) 要件定義書 §3-1 項目5（バッチ安定性 成功率95%以上）への影響
        7日間停止すると、その週の取得は0件になる。
        週次チェックリストで初めて気付き、そこから復旧する。

    リスク調査書 §1-5 リスク2 は60日自動無効化を
    **影響度「高」／残存度「中」（発生は防げないが検知手段は定義済み）**と評価した。
    「検知手段は定義済み」は正しいが、**検知の速さは評価されていない**。
    本書 §6-2-2 はその評価をそのまま引き継いでいる。

  推奨対応:
    次のいずれか。実装コストの小さい順に挙げる。

      案A：**60日無活動を発生させない運用ルールを設ける**
           月1回でもコミットがあれば無効化されない。
           週次チェックリストに「**月初にリポジトリへコミットする**」を
           1項目加えるだけで、原因そのものを断てる。
           検知ではなく予防であり、最も確実である。

      案B：**外部の cron 監視を使う**
           healthchecks.io 等の無料枠は「決まった間隔で ping が来ないと通知」
           という用途に合う。`run_batch_once.py` の末尾で ping する。
           バッチが**走らなくなったこと**を検知できる唯一の方式である。
           ただし監視先が1つ増える（§4-2 の「管理対象が増える」に該当）。

      案C：**週次チェックリストの確認頻度を上げる**
           運用負荷が増えるため推奨しない。

    **案Aを推奨する。** 予防に振る方が、
