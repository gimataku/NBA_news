## 2. F-13：ニュース本文の展開表示

### 2-1. 状態管理の設計

要件定義書§2-3-2の派生仕様b・dより、**展開状態は独立・スコア表示状態は共有**である。既存の `useNews.js` に以下を追加する。

| 状態 | 型 | スコープ | 根拠 |
|---|---|---|---|
| `expandedIds` | `Set<number>` | **一覧側** | 展開状態（一覧） |
| `relatedExpandedIds` | `Map<number, Set<number>>` | **親記事IDごと** | 展開状態（関連ニュース内）。**独立**のため2階層 |
| `revealedIds`（既存） | `Set<number>` | **全体で共有** | スコア表示状態。**共有**のため1階層のまま |

> **`revealedIds` を変更しない**ことが要点。要件定義書がスコア表示状態を「共有」と決めたため、既存の状態管理をそのまま使える。展開状態のみ2階層になる。

### 2-2. 折りたたみ時のリセット

要件定義書§2-1-2 確認事項5より、**一覧側の折りたたみのみ** `revealedIds` から当該IDを削除する。

| 操作 | `expandedIds` | `revealedIds` |
|---|---|---|
| 一覧側で折りたたむ | 当該IDを削除 | **当該IDを削除** |
| 関連ニュース内で折りたたむ | `relatedExpandedIds` から削除 | **変更しない** |

### 2-3. 展開インジケータ

要件定義書§2-1-1 項目6は「**展開可能であることが操作前に分かること**」を要件とし、意匠は本書で決定する。

| 項目 | 設計 |
|---|---|
| 記号 | **`▶`（折りたたみ時）／`▼`（展開時）** |
| 位置 | タイトルの**左**（カテゴリバッジの下・タイトル行の先頭） |
| アニメーション | **なし**（実装を単純に保つ） |
| クリック対象 | **タイトル行全体**（記号だけでなくタイトル文字列も含む。タップ領域を広く取る） |

### 2-4. コンポーネント構造

```
NewsCard
├─ CategoryBadge
├─ TitleRow（クリックで展開/折りたたみ）      ← F-13
│   ├─ ExpandIndicator（▶ / ▼）
│   └─ title_ja
├─ [展開時のみ]
│   ├─ SpoilerOverlay または summary_ja        ← F-05（既存・二段展開）
│   └─ [スコア表示済みのみ] RelatedNews        ← F-15（新規）
└─ MetaRow（source・時刻・原文リンク）          ← F-20（リンク検証）
```

> **`SpoilerOverlay` は変更しない**。既存のまま `summary_ja` の位置に描画される。F-13は**その外側に展開制御を被せる**設計とし、フェーズ2で未検証のネタバレUIへの影響を最小化する（要件定義書§2-1-4の制約に対応）。

## 3. F-15：関連ニュース表示

### 3-1. 算出方式

リスク調査書§2-2より**案(a) Levenshtein流用**を採用する（追加依存・追加コストともゼロ）。

### 3-2. 関連度スコアの設計

要件定義書§2-3-3の3基準を、**加重和**で1つのスコアにする。

| # | 基準 | 計算 | 重み | 根拠 |
|---|---|---|---|---|
| 1 | 同一カテゴリ | 一致なら1.0・不一致なら0.0 | **0.2** | allタブでのみ識別力を持つ（要件定義書§2-3-3の注記） |
| 2 | タイトルの語句一致 | `Levenshtein.ratio()` | **0.6** | 主たる判定軸 |
| 3 | 取得時期の近接 | `max(0, 1 - 経過時間[h] / 168)` | **0.2** | 7日（168h）で0になる線形減衰 |

```
score = 0.2 × same_category + 0.6 × levenshtein_ratio + 0.2 × recency
```

**閾値：0.35**

| 項目 | 値 | 根拠 |
|---|---|---|
| 表示閾値 | **0.35** | 重複排除の閾値0.80（`DEDUP_THRESHOLD`）より十分低く、かつ無関係な記事を拾わない水準。**タイトル類似度が0.4程度でも同カテゴリ・同時期なら拾える**設定 |
| 表示件数 | 上位5件（要件定義書§2-3-1 項目3） | — |

> **閾値はトライアル運用（手順10）で調整する**。要件定義書§3-2の改善バックログ項目として扱い、合否判定には含めない。

### 3-3. 比較対象：`title_ja`（日本語）

| 案 | 採否 | 根拠 |
|---|---|---|
| `title_original`（英語） | ❌ | `dedup.py` は翻訳前の重複判定のため英語を使うが、**F-15は表示時の算出**であり翻訳済みデータが揃っている |
| **`title_ja`（日本語）** | ✅**採用** | **利用者が見ている文字列で類似を判定する**方が体感と一致する。選手名の表記ゆれ（F-16）があっても、同一記事群では同じ表記になるため影響は小さい |

> **`title_ja` が NULL の記事**（翻訳失敗時）は `title_original` にフォールバックする。

### 3-4. 算出タイミング：リクエスト時（フロントエンド）

| 案 | 採否 | 根拠 |
|---|---|---|
| **フロントエンドで算出** | ✅**採用** | 算出範囲が**表示リスト内（最大50件）**に確定しているため、**既に取得済みのデータだけで計算できる**。API呼び出し・スキーマ変更が不要 |
| バックエンドで算出 | ❌ | 追加のAPI呼び出しが必要。**表示リスト内**という制約下では利点がない |
| バッチ時に事前算出 | ❌ | スキーマ変更が必要。表示リストはフィルタで変わるため事前算出できない |

**計算量**: 1記事の展開ごとに最大49回の文字列比較。JavaScript実装で**体感の待ちは発生しない**見込み（要件定義書§6 項目2の閾値200msに対して十分）。

> **Levenshtein のJS実装が必要**。バックエンドの `python-Levenshtein` は使えないため、**軽量な自前実装**（動的計画法・数十行）とする。外部ライブラリを追加しない。

### 3-5. `RelatedNews.jsx`（新規コンポーネント）

| 項目 | 設計 |
|---|---|
| props | `articles`（表示リスト全件）・`currentArticle`・`spoilerGuard`・`revealedIds` など |
| 表示条件 | 要件定義書§2-3-1 項目9：**ネタバレ防止ON かつ `has_score=true` かつ未表示**なら**描画しない** |
| 該当なし | 閾値未満しかない場合は**欄自体を描画しない**（項目8） |
| 展開の深さ | **1段階まで**。`RelatedNews` 内の記事は `RelatedNews` を持たない（派生仕様a） |

## 4. セキュリティ由来の要件（F-17〜F-21）

### 4-1. F-17：ログインのレートリミット

| 項目 | 設計 | 根拠 |
|---|---|---|
| 適用対象 | `POST /api/auth/login` のみ | 他エンドポイントはJWT必須のため優先度が低い |
| 方式 | **アプリケーション層**（`slowapi`） | リスク調査書§4-1-1。Render無料プランでも動作する |
| 制限 | **5回/分（IPアドレス単位）** | 通常利用（1日数回のログイン）を妨げず、ブルートフォースには実効的 |
| 超過時 | HTTP **429**（Too Many Requests） | 標準的な応答 |
| ロックアウト | **なし** | 単一利用者のため、誤ってロックされると自分が使えなくなる。**レート制限のみ**とする |

> **ロックアウトを設けない根拠**: 本アプリの利用者は1名であり、アカウントロックは**攻撃者ではなく本人を締め出す**リスクの方が大きい。5回/分の制限だけでも、総当たりに要する時間は現実的でない水準になる。

### 4-2. F-18：日付パラメータのバリデーション

| 項目 | 設計 |
|---|---|
| 対象 | `GET /api/schedule` の `start_date` / `end_date` |
| 方式 | **Pydantic の型検証**（`datetime.date`）に委ねる |
| 不正時 | FastAPIが自動的に HTTP **422** を返す |

> 独自のバリデーション関数を書かず、**フレームワークの標準機能に寄せる**。

### 4-3. F-19：`datetime.utcnow()` の置換

| 対象 | 置換後 |
|---|---|
| `auth/jwt.py` の `datetime.utcnow()` | `datetime.now(timezone.utc)` |

> **注意**: `utcnow()` は naive、`now(timezone.utc)` は aware を返す。JWTの `exp` クレーム生成では**数値に変換されるため影響はない**が、比較処理がある場合は要確認（手順4で精査）。

### 4-4. F-20：外部リンクのスキーム検証

| 項目 | 設計 |
|---|---|
| 対象 | `NewsCard.jsx` の `article.source_url` |
| 方式 | **`http:` / `https:` のみ許可**。それ以外は**リンクを描画しない**（プレーンテキストとして表示） |
| 実装位置 | `NewsCard.jsx` 内のヘルパー関数 |

> **F-13で同一ファイルを改修するため、同時に対応する**（要件定義書§5-2）。

### 4-5. F-21：CORS設定の限定

| 項目 | 変更前 | 変更後 |
|---|---|---|
| `allow_methods` | `["*"]` | **`["GET", "POST"]`** |
| `allow_headers` | `["*"]` | **`["Authorization", "Content-Type"]`** |
| `allow_origins` | 環境変数（変更なし） | 変更なし |

> **要望1の採否に依存しない**。移行先が変わっても `allow_origins` は環境変数のままであり、メソッド・ヘッダの限定は共通である。

### 4-6. F-16：選手名・用語の表記統一

| 項目 | 設計 |
|---|---|
| 実装位置 | `processor/claude_client.py` のプロンプト |
| 形式 | **固有名詞の対訳表**をプロンプトに埋め込む |
| 収録範囲 | 要件定義書§3-4-2の9件＋主要選手20〜30名 |
| 指示 | 「**表にある語は必ず表の表記に従う。表にない選手名は一般的なカタカナ表記を用いる**」 |

### 5-5. `config.py` の必須チェックの用途別分離

リスク調査書§4-2-1の案A〜Dより、**案Aを採用**する。

| 案 | 採否 | 根拠 |
|---|---|---|
| **案A：用途別に分離** | ✅**採用** | **構造的に正しい**。認証系の必須チェックが認証を使わない処理まで巻き込む現状を是正する。**要望1が不採用でも価値がある**（リスク調査書§4-2-2） |
| 案D：ダミー値運用 | ❌不採用 | 最小コストだが、**GitHub Secrets上で本物とダミーが見分けられない**。将来「SECRET_KEYが設定されている」ことを根拠に誤った前提を置くリスクが残る |

**設計**

| 区分 | 検証タイミング | 対象 |
|---|---|---|
| **共通**（`config.py` のロード時） | 従来どおり | `ANTHROPIC_API_KEY`・`BALLDONTLIE_API_KEY`（**先-1で追加**） |
| **認証系**（`auth/` のロード時に移動） | **`auth/jwt.py`・`auth/users.py` へ移す** | `SECRET_KEY`・`INIT_USERNAME`・`INIT_USER_PASSWORD` |

```
変更前： config.py が全6シークレットを必須チェック
         → scheduler.py が config を import した時点で全部要求される

変更後： config.py         → APIキー2件のみ必須チェック
         auth/jwt.py       → SECRET_KEY を必須チェック
         auth/users.py     → INIT_USERNAME / INIT_USER_PASSWORD を必須チェック
         → scheduler.py は auth を import しないため、認証系は要求されない
```

> **先-1（2026年9月まで）の実施時に本設計を反映する**（リスク調査書§5-0 #1）。
>
> **テストへの影響**: `conftest.py` L19-23 は5件すべてにダミー値を設定しており、**変更後も動作する**（余分に設定していても害はない）。

| cron式 | **`0 21,1,5,9,13,17 * * *`（UTC）** | JST **6/10/14/18/22/2時** |
| 間隔 | 4時間（現行と同じ） | — |

> **JST 6時を含める根拠**: NBAの試合は日本時間の午前中に終わる。**朝6時のバッチにより、起床時（7〜8時頃）には前夜の試合記事が入っている**状態にする。`0 */4 * * *`（UTC）だとJST 9時が最初になり、朝の閲覧に間に合わない。
