【🟡 要改善（1件）】
================================================================================

[YEL-01] §5-2 #3 の「翻訳が止まっても記事の取得自体は継続する」が事実と異なる
         ——上限超過中は記事が保存されず、RSSから流れ落ちれば永久に失われる

  対象箇所: §5-2「#3（Claude API のRateLimit）の扱い」（L453）

  v0.5 の記述:
    「**案Aでは検知できない**（⑨の `save_fetch_log`（L171）では
      `error_message` が NULL のまま記録される）。
      `api_limit_exceeded` は **`/api/status` の既存フィールド**であり、
      **週次チェックリストで確認する**（§6-3）。
      **翻訳が止まっても記事の取得自体は継続するため、
      主の監視で即時に拾う必要性は低い。**」

  実装（`backend/scheduler.py` L111-123）:

      # ⑤ Claude API処理
      # API上限超過中は翻訳・保存をスキップ
      if crud.get_setting("api_limit_exceeded") == "true":
          continue                          # ← 記事を保存せず次へ

      result = process_article(title_original, description)
      if result is None:
          if crud.get_setting("api_limit_exceeded") == "true":
              # RateLimitError（429）→ スキップ（DB保存しない）
              continue                      # ← 同上

  問題:
    (1) **記事の取得は継続しない**
        コード内のコメント自体が「**翻訳・保存をスキップ**」と明記している。
        上限超過中、記事は `articles` テーブルに**一切保存されない**。
        `summary_ja` が NULL で保存されるのでもなく、**行が作られない**。

    (2) **RSSから流れ落ちた記事は永久に失われる**
        `exists_article(link)` に記録が残らないため、
        次に翻訳が再開したときに再取得**される可能性はある**が、
        それはその記事がまだRSSフィードに残っている場合に限られる。
        Hoops Rumors 等のRSSは直近20〜50件程度を保持するため、
        本アプリの取得間隔（4時間）と記事数（週50件・1日約7件）からすると
        **数日で流れ落ちる**。
        上限超過が数日続けば、その期間の記事は取り戻せない。

    (3) **したがって「必要性は低い」という評価は成立しない**
        §5-2 の評価は「翻訳だけが止まり、記事は貯まり続ける」という
        前提に立っている。実際には**記事の蓄積そのものが止まる**。
        これは #1（RSS全滅）と同じ結果——「バッチは走ったが記事が増えない」
        ——であり、#1 を案Aで拾えるようにした判断と整合しない。

    (4) **唯一の検知手段が月次リセットで消える**
        `api_limit_exceeded` は `run_batch()` ①（L50-55）で
        **月が替わった最初のバッチ実行時に `false` へリセットされる**。

            if crud.get_setting("api_reset_month") != current_month:
                crud.set_setting("api_limit_exceeded", "false")

        月内であればフラグは残るため週次確認で捕捉できるが、
        **月末に上限超過が起き、週次確認が月初にずれ込むと見逃す**。
        `fetch_logs` にも記録されない（`error_message` は NULL）ため、
        **事後に確認する手段がない**。

  推奨対応:
    判断（週次確認に委ねる）を変えるかどうかは、
    上限超過の発生見込みをどう見るかによる。
    フェーズ2の実績は Claude API が月 $1.27〜$1.72（試算 $3.40 の半分以下）であり、
    **上限超過の可能性は低い**。よって「主の監視で即時に拾わない」判断自体は
    維持できる可能性が高い。ただし**理由を書き直す必要がある**。

      案A：**理由を差し替えて判断は維持する**（推奨）
           「翻訳が止まっても記事の取得自体は継続する」を削除し、
           「**上限超過中は記事も保存されないため、影響は #1（RSS全滅）と同等である。
             ただしフェーズ2の実績（月 $1.27〜$1.72・試算の半分以下）から
             発生見込みが低く、主の監視に載せる費用対効果が小さい**」
           とする。あわせて「**発生した場合は当該期間の記事が失われる**」ことを
           明記する。

      案B：**`fetch_logs` に記録して案Aで拾えるようにする**
           `run_batch()` ⑨の `save_fetch_log()` に
           「上限超過によりスキップした件数」または `error_message` を入れる。
           `scheduler.py` の変更が必要になるため、
           案C（早期リターンを例外に変える）を不採用にした理由
           （既存動作を変えない）と同じ観点で慎重に判断する。

      案C：**運用指標に「上限超過の履歴」を追加する**
           要件定義書 §4-1 に指標を追加し、§6-1 の `metrics` に含める。
           月次リセットの影響を受けない形（例：直近7日で
           `fetched_count` が期待値を大きく下回った日数）にすれば、
           §6-3 ③の週次確認が確実になる。

    あわせて §6-3 Section F ③（`api_limit_exceeded` の確認）に
    「**月替わりでフラグがリセットされるため、月初の確認では前月分を捕捉できない**」
    という注意を添える。

  重要度の根拠:
    v0.5 は §5-2 の表に「案A適用後に検知できるか」列を追加し、
    #2・#3 の扱いを明示するという**正しい方向**の改訂を行った。
    その #3 の扱いを支える評価が事実と異なるため、
    **判断の妥当性が確認できない状態**になっている。
    判断そのものは維持できる見込みが高く、理由の差し替えで解消する。
