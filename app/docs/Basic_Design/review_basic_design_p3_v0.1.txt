[YEL-01] `main.py` の startup で呼ばれる `check_and_run_batch()` が設計から漏れており、
         `/api/fetch` を削除する趣旨と矛盾する

  対象箇所: §1-2 #9 ／ §5-3 ／ §5-4

  実装を確認したところ、`backend/main.py` の startup イベントは次の通りである。

      @app.on_event("startup")
      def startup_event() -> None:
          init_db()
          init_user(crud)
          scheduler.start()
          logger.info("Scheduler started")
          **check_and_run_batch()**        ← スケジューラとは別の直接呼び出し

  `scheduler.start()` の**後に `check_and_run_batch()` が直接呼ばれている**。
  これは APScheduler のジョブとは独立した、**起動時の1回実行**である。

  本書の記述:
    §1-2 #9  `main.py`「CORS設定の限定・**スケジューラ起動の条件分岐**」
    §5-3     `ENABLE_SCHEDULER` で `scheduler.start()` を分岐

  **`check_and_run_batch()` の扱いに触れていない。**

  問題:
    (1) 設計どおりに `scheduler.start()` だけを分岐すると、
        `ENABLE_SCHEDULER=false` でも**起動時のバッチ実行は残る**。
        要望1採用時の構成は「Render 無料 Web Service（**FastAPIのみ**）」であり、
        API層でバッチが動くことは構成の前提に反する。

    (2) **§5-4 で `/api/fetch` を削除した趣旨と矛盾する。**
        §5-4 は `/api/fetch` を削除する根拠として
        「無料インスタンス上でのバッチ実行・GH Actions との二重実行・
          代替手段の存在」の3点を挙げている。
        しかし `check_and_run_batch()` が残れば、
        **同じ3つの問題が起動のたびに発生する**。
        手動トリガを消して自動トリガを残す形になる。

    (3) 無料プランでは影響が大きい。
        Render 無料プランは15分の無アクセスでスピンダウンするため、
        **利用者のアクセスのたびにコールドスタートが起きる**。
        そのたびに `check_and_run_batch()` が走る。
        ゲート（前回取得から4時間）があるため通常はスキップされるが、
        GitHub Actions が失敗して4時間以上空いた場合、
        **利用者が最初のアクセスをした瞬間に、
        起動待ち約1分に加えてバッチ（Claude API呼び出しを含む）が走る**。

    (4) `ENABLE_SCHEDULER=false` の意味が曖昧になる。
        「スケジューラを止める」のか「バッチ実行全体を止める」のかで、
        実装者の解釈が分かれる。

  推奨対応:
    ・§5-3 の設計対象を「`scheduler.start()`」から
      「**`scheduler.start()` と startup の `check_and_run_batch()` の両方**」に広げる。
      `ENABLE_SCHEDULER=false` のとき両方を実行しない、と明記する。
    ・§1-2 #9 の変更内容も「スケジューラ起動**および起動時バッチ実行**の条件分岐」に改める。
    ・あわせて `startup_event()` 内の他の処理（`init_db()`・`init_user()`）が
      要望1採用時にどう振る舞うかを確認する。
      `init_db()` は Neon に対して `create_all` を実行するため
      **Render 側と GitHub Actions 側の両方から呼ばれうる**（冪等だが二重実行になる）。
      `init_user()` も同様（`count_users() == 0` のときのみ作成するため冪等）。
      いずれも問題は起きない見込みだが、**設計として確認済みであることを記録**すると
      手順4で迷わない。

  重要度の根拠:
    §5-4 は3つの論点を挙げて `/api/fetch` の削除を決めた。
    その論点がそのまま当てはまる呼び出しが `main.py` に残っている。
    設計の一貫性の問題であり、実装段階で気付いても
    「なぜ片方だけ消したのか」を再検討することになる。


[YEL-02] §2-4 と §3-5 で `RelatedNews` の表示条件が矛盾しており、
         §2-4 のとおり実装すると大半の記事で関連ニュースが表示されない

  対象箇所: §2-4 コンポーネント構造 ／ §3-5 表示条件

  §2-4 のコンポーネント構造:

      ├─ [展開時のみ]
      │   ├─ SpoilerOverlay または summary_ja
      │   └─ **[スコア表示済みのみ] RelatedNews**

  §3-5 の表示条件:

      「要件定義書§2-3-1 項目9：**ネタバレ防止ON かつ `has_score=true` かつ未表示**
        なら**描画しない**」

  両者は同じ条件ではない。

      §3-5（否定形・正しい）：
        描画しない ⇔ spoilerGuard かつ has_score かつ !revealed
        → 描画する  ⇔ !spoilerGuard または **!has_score** または revealed

      §2-4（肯定形）：
        描画する ⇔ revealed

  問題:
    `has_score=false` の記事には「スコアを表示」という操作が存在しない。
    したがって `revealedIds` に当該IDが入ることはない。
    §2-4 のとおり「スコア表示済みのみ」を条件にすると、
    **`has_score=false` の記事では関連ニュースが永久に表示されない**。

    要件定義書 §4-1 の運用指標を見ると、`has_score=true` は
    試合結果を含む記事に限られる（オフシーズンには0件）。
    つまり**通常は大半の記事が `has_score=false`** であり、
    §2-4 のとおり実装すると **F-15 がほぼ機能しない**。

    また `spoilerGuard=false`（ネタバレ防止OFF）の場合も、
    §3-5 では描画するが §2-4 では描画しない。

  推奨対応:
    ・§2-4 のツリーの条件を §3-5 に合わせる。
      表現としては否定形のまま書く方が誤解が少ない。

          ├─ [展開時のみ]
          │   ├─ SpoilerOverlay または summary_ja
          │   └─ RelatedNews
          │       （**ネタバレ防止ON かつ has_score=true かつ未表示のときは描画しない**）

    ・§3-5 の表示条件の行に「**§2-4 の構造図と同じ条件**」と相互参照を入れると、
      片方だけ直る事態を防げる。

  重要度の根拠:
    コンポーネント構造図は実装者が最初に見る図であり、
    条件が誤っていると機能が動かない形で実装される。
    §3-5 が正しいため設計判断としての誤りはなく、**図の記述の問題**だが、
    影響範囲（F-15 全体）が大きい。


[YEL-03] 関連度の閾値0.35が「タイトル類似度ゼロ」の下限を下回っており、
         要件定義書 §2-3-1 項目8（該当なしなら非表示）が機能しない

  対象箇所: §3-2 関連度スコアの設計

  設計:
      score = 0.2 × same_category + 0.6 × levenshtein_ratio + 0.2 × recency
      recency = max(0, 1 - 経過時間[h] / 168)
      表示閾値 = **0.35**

  問題:
    **タイトル類似度が 0 でも、同一カテゴリかつ最近の記事は閾値を超える。**

      same_category = 1.0、levenshtein = 0.0、経過24時間の場合
        recency = 1 - 24/168 = 0.857
        score   = 0.2 × 1.0 + 0.6 × 0.0 + 0.2 × 0.857 = **0.371 > 0.35**

      閾値を下回るのは経過**約40時間**を超えてからである
        （0.2 + 0.2 × (1 - 40/168) = 0.2 + 0.152 = 0.352）。

    本アプリは週50件（1日約7件・1カテゴリあたり約1.8件）を取得するため、
    **同一カテゴリで40時間以内の記事は常に数件存在する**。
    それらはタイトルがまったく無関係でも閾値を超える。

    結果として:
      ・カテゴリタブでは表示リスト全件が同一カテゴリのため、
        **直近の記事はすべて「関連」と判定される**
      ・要件定義書 §2-3-1 項目8「関連度が閾値未満の記事しかない場合、
        **関連ニュース欄自体を表示しない**」が、
        同カテゴリの新着がある限り発動しない

    設計は「閾値はトライアル運用（手順10）で調整する」としているが、
    **初期値が構造的に機能しない**状態で運用に入ることになる。

  推奨対応:
    次のいずれか（併用も可）。

      案A：**閾値を下限より上に設定する**
           カテゴリ＋時期だけで到達する最大値は
           0.2 + 0.2 = **0.4**（同カテゴリ・同時刻）。
           閾値を **0.45〜0.5** にすれば、
           「タイトルにある程度の類似がないと通らない」設計になる。
           0.45 の場合、同カテゴリ・24時間差なら
           levenshtein ≥ 0.13 が必要。

      案B：**タイトル類似度にゲートを設ける**
           `levenshtein_ratio < 0.2 なら score = 0` とする。
           加重和の枠組みを保ったまま、
           「タイトルが似ていないものは関連としない」を明示できる。
           §2-3-3 が基準2を「主たる判定軸」としていることとも整合する。

      案C：**重みを見直す**
           カテゴリ0.1・Levenshtein0.7・時期0.2 なら下限は0.3。
           閾値0.35 のままでも下限を下回る。

    案Bを推奨する。「主たる判定軸」という要件定義書の位置づけを
    構造として保証でき、閾値の調整（手順10）とも独立に効く。

  補足:
    重み・閾値そのものの妥当性は運用で調整する性質のものであり、
    本指摘は「値が間違っている」ではなく
    **「値の取り方によらず、加重和の下限が閾値を上回っている」という構造**に対するものである。


[YEL-04] 親記事を折りたたんだときの状態が設計されていない

  対象箇所: §2-2 折りたたみ時のリセット

  要件定義書 §2-3-2「§2-1-2 確認事項5（折りたたみ時のリセット）の適用先」は
  **3パターン**を定義している。

      | 一覧側で折りたたむ           | リセットする                                   |
      | 関連ニュース内で折りたたむ   | リセットしない                                 |
      | **親記事（関連ニュースを表示している記事）を折りたたむ**
        | **親記事自身のスコア表示状態のみリセット。
           関連ニュース内で表示した記事の状態は保持** |

  本書 §2-2 の表は**上2つのみ**で、3つ目がない。

  問題:
    親記事Aを折りたたむと、A の `RelatedNews` はアンマウントされる。
    このとき決めるべきことが2つある。

      (1) `relatedExpandedIds` の A のエントリを削除するか保持するか
          削除すれば、A を再展開したとき関連ニュースはすべて折りたたみ状態に戻る。
          保持すれば、再展開時に前回の展開状態が復元される。
          **要件定義書は `revealedIds` について「保持」と定めているが、
          `relatedExpandedIds` については規定がない。**
          本書が新設した状態であるため、**本書で決める必要がある**。

      (2) 関連ニュース内で展開した記事Xの `revealedIds` を保持する
          要件定義書は「保持」と明記している。
          §2-1 の設計（`revealedIds` は共有・1階層）では、
          A を折りたたんでも X のエントリは触らないため自然に保持される。
          **設計としては満たされているが、§2-2 の表に書かれていない**ため、
          実装者が「親を閉じたら子もリセット」と解釈する余地が残る。

  推奨対応:
    ・§2-2 の表に3行目を追加する。

        | 親記事を折りたたむ | `expandedIds` から当該IDを削除。
                              `relatedExpandedIds` の当該エントリは**〔削除／保持〕**
                            | **親記事自身のIDのみ削除**。
                              関連ニュース内で表示した記事のIDは**保持** |

    ・`relatedExpandedIds` の扱いを決める。
      **削除を推奨する**。関連ニュースは「今読んでいる記事の周辺情報」であり、
      親を閉じた時点で文脈が切れる。保持すると
      `Map` が単調増加してメモリに残り続ける点も考慮に入る
      （§2-1 が `Map<number, Set<number>>` を採用しているため、
        削除しないとエントリが溜まる）。


[YEL-05] レートリミットの「IPアドレス単位」が Render のプロキシ環境で機能せず、
         ロックアウトを設けない根拠が成立しない

  対象箇所: §4-1 F-17

  設計:
      | 制限 | **5回/分（IPアドレス単位）** |
      | ロックアウト | **なし** |

      根拠：「本アプリの利用者は1名であり、アカウントロックは
              **攻撃者ではなく本人を締め出す**リスクの方が大きい」

  問題:
    Render はリバースプロキシ経由でリクエストを転送する。
    FastAPI / uvicorn が実クライアントIPを得るには
    `X-Forwarded-For` を信頼する設定が必要だが、
    `backend/main.py` の `uvicorn.run()` には
    `proxy_headers` / `forwarded_allow_ips` の指定がない。

        uvicorn.run(
            "main:app",
            host=os.getenv("HOST", "127.0.0.1"),
            port=int(os.getenv("PORT", 8000)),
            reload=False,
            ...
        )

    uvicorn の既定は `forwarded_allow_ips="127.0.0.1"` であり、
    Render のプロキシはこれに該当しない。
    したがって `slowapi` の既定キー関数（`get_remote_address` →
    `request.client.host`）が返すのは**プロキシのIP**になる。

    結果として、**レート制限は全アクセス共通の1つのバケット**になる。

    これは §4-1 のロックアウト非採用の根拠を弱める。
      「ロックアウトは本人を締め出す」→ 採用しない
      しかし**IP単位が機能しないなら、レート制限自体が本人を締め出す**。
      攻撃者が5回/分を消費し続ければ、利用者もログインできない。
      「レート制限のみなら本人は締め出されない」という前提が成り立たない。

  推奨対応:
    ・**`X-Forwarded-For` を信頼する設定**を設計に含める。
        uvicorn 起動時に `forwarded_allow_ips="*"`（Render のプロキシを信頼）
        または `ProxyHeadersMiddleware` を明示的に追加する。
      信頼範囲を `"*"` にする場合、**Render 以外から直接到達できない**ことが
      前提になる。Render の構成では外部からアプリのポートに直接届かないため
      成立するが、**その前提を設計に書く**必要がある。
    ・上記を行っても、単一利用者のアプリでは
      **攻撃者と本人のIPが異なる**ため、per-IP 制限は本来の意図どおり働く。

  補足:
