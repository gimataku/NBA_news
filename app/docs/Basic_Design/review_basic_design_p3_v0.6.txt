3. 本版の指摘（🟢2件）
--------------------------------------------------------------------------------

  いずれも**本書の修正を求めるものではない**。上位文書（リスク調査書v0.6）が
  既に完了しているため、詳細設計書側で吸収するのが正しい。§4-5に引き継ぐ。

  ────────────────────────────────────────────────────────────────────────────
  🟢 GRN-01：`HEALTHCHECK_PING_URL` が、シークレットの列挙元である
             リスク調査書§4-2-1 配置表に載っていない
  ────────────────────────────────────────────────────────────────────────────

  【該当】本書 §6-2-2「外部cron監視の設計」L729
          | ping URL | **GitHub Secrets に登録**（`HEALTHCHECK_PING_URL`） |

  【事実】`grep -rn "HEALTHCHECK_PING_URL" docs/ --include=*.md` の結果、
          出現するのは basic_design_p3 の v0.3・v0.4・v0.5・v0.6 のみ。
          リスク調査書・要件定義書・プロジェクト計画書には**一度も現れない**。

          一方、リスク調査書§4-2-1「シークレットの配置表」は
          `ANTHROPIC_API_KEY` / `BALLDONTLIE_API_KEY` / `DATABASE_URL` /
          `SECRET_KEY` / `USERNAME` / `USER_PASSWORD` の**6件のみ**を
          列挙しており、これがプロジェクト内で唯一の
          「どのシークレットをどこに置くか」の一覧である。

  【問題】移行作業（リスク調査書§1-4-9の11ステップ）で GitHub Secrets を
          登録する際、この配置表を見ながら作業すると
          **`HEALTHCHECK_PING_URL` の登録が漏れる**。

          漏れた場合の挙動は本書§6-2-2で定義済みである
          （「未設定なら ping をスキップする。`config.py` の必須チェックには
          加えない」）。したがって**バッチは正常に動き、エラーも出ない**。
          しかし ping が飛ばないため、healthchecks.io 側は猶予超過で
          「異常」と通知する。**監視が導入初日から誤報を出す**状態になる。
          あるいは逆に、チェック自体を作っていなければ
          「監視を入れたつもりで入っていない」状態に静かに落ち着く。

          未設定時にスキップする設計自体は正しい（ローカル実行で監視を
          誤って満たさないため）。問題は、その安全側の設計が
          **登録漏れを気付きにくくしている**点にある。

  【重要度が🟢である理由】
          設計の誤りではなく、文書間の反映漏れである。かつ、対処は
          詳細設計書に一覧を持たせるだけで済む。

  【対処案】

    案A（推奨）: 詳細設計書に「GitHub Secrets 登録一覧（確定版）」を置き、
                 そこを移行作業時の唯一の参照先とする。
                 リスク調査書§4-2-1は完了済み文書として据え置く。
                 詳細設計書側に「本表はリスク調査書§4-2-1に
                 `HEALTHCHECK_PING_URL` を加えたものである」と出所を書く。

    案B        : リスク調査書を v0.7 に改版して配置表へ1行追加する。
                 → 完了済み文書を1行のために開けることになる。
                    かつ §5-5（案A採用）による陳腐化（GRN-02）も同時に
                    直す必要が生じ、改版範囲が広がる。推奨しない。

    案C        : 移行手順（§1-4-9）のステップ側に注記を足す。
                 → 一覧表と手順の2箇所に情報が分かれ、次に増えたときに
                    同じ漏れが起きる。推奨しない。

  【案Aを採る場合の一覧（当方で作成。詳細設計書での確定を求める）】

    ＜先-1（`config.py` 用途別分離）実施後・要望1採用時＞

    | シークレット             | Render(API層) | GitHub Secrets(バッチ層) |
    |-------------------------|---------------|-------------------------|
    | `ANTHROPIC_API_KEY`     | ✅必要         | ✅必要                   |
    | `BALLDONTLIE_API_KEY`   | ✅必要         | ✅必要                   |
    | `DATABASE_URL`          | ✅必要         | ✅必要                   |
    | `SECRET_KEY`            | ✅必要         | ❌不要（案Aにより解消）   |
    | `USERNAME`              | ✅必要         | ❌不要（案Aにより解消）   |
    | `USER_PASSWORD`         | ✅必要         | ❌不要（案Aにより解消）   |
    | `HEALTHCHECK_PING_URL`  | ❌不要         | ✅必要（未設定時スキップ）|

      → バッチ層に置くのは**4件**。認証系3件は先-1の完了により
        「ダミー値すら不要」になる。これはリスク調査書§4-2-1が
        前提としていた状態（⚠️現状の実装では必要）と異なる。

    ＜要望1不採用時＞
      GitHub Actions を使わないため、GitHub Secrets 欄はすべて不要。
      `HEALTHCHECK_PING_URL` も不要（§6-2-1に外部cron監視は無い）。

  ────────────────────────────────────────────────────────────────────────────
  🟢 GRN-02：§5-5（案A採用）により、リスク調査書§4-2-1 配置表の
             「バッチ層で本来必要か」欄が先-1実施後に陳腐化する
  ────────────────────────────────────────────────────────────────────────────

  【該当】本書 §5-5「`config.py` の必須チェックの用途別分離」（案A採用）

  【事実】リスク調査書§4-2-1 の配置表は、`SECRET_KEY` / `USERNAME` /
          `USER_PASSWORD` の GitHub Secrets 欄を
          「⚠️**現状の実装では必要**」と書き、本文で
          「バッチ層に置く値は『本物』である必要がない」
          「GitHub Secrets に置くのは任意の値でよい」と説明している。

          この記述はすべて「`config.py` がロード時に全6件を必須チェックする」
          という**現状の実装**を前提にしている。
          本書§5-5が案Aを採用し、先-1（2026年9月まで）で実施すると、
          この前提は消える。認証系3件は `auth/` 側でのみ検証されるため、
          `scheduler.py` は `auth` を import せず（リスク調査書§4-2-1が
          import連鎖で確認済み）、**ダミー値の設定すら不要になる**。

  【問題】リスク調査書§4-2-1を読んだ人は「バッチ層にもダミー値を3件置く」
          と理解する。実際には先-1の完了後は0件でよい。
          移行作業（要望1採用時）は先-1より後になる可能性が高く、
          **不要なダミー値3件を GitHub Secrets に登録する**手戻りが起きる。

          実害は小さい（余分な設定が3件残るだけ）。ただし
          リスク調査書§4-2-1の案Dのリスク欄が指摘したとおり、
          「GitHub Secrets 上に意味のない項目が並ぶ」状態は
          **将来『SECRET_KEYが設定されている』ことを根拠に何かを判断する
          コードが入ったときに静かに壊れる**土台になる。案Aを採ったのは
          まさにそれを避けるためであり、設定だけ案D相当が残るのは本末転倒。

  【重要度が🟢である理由】
          本書の設計は正しい。上位文書の記述が本書の決定によって
          古くなるという、**予告すべきだったのに予告しなかった**類の問題。

  【対処】GRN-01 の案Aと同じ一覧表で同時に解消する。
          詳細設計書の「GitHub Secrets 登録一覧（確定版）」に
          「認証系3件は先-1（`config.py` 用途別分離）の完了により不要。
          リスク調査書§4-2-1 の『⚠️現状の実装では必要』は先-1完了前の記述」
          と明記する。
