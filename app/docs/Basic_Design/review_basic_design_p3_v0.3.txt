【🟡 要改善（2件）】
================================================================================

[YEL-01] `run_batch()` / `run_game_schedule_batch()` は失敗しても例外を投げないため、
         「非ゼロ終了」と「ping しない」が機能せず、
         §6-2-2 の採用根拠「バッチが止まる全ての原因を検知できる」が成立しない

  対象箇所: §5-2（終了コード）／ §6-2-2（採用根拠 #2・失敗時）／ 外部cron監視の設計

  設計の前提:
      §5-2  「終了コード：**例外発生時は非ゼロで終了**し、
              GitHub Actionsのジョブを失敗させる」
      §6-2-2「**失敗時：ping しない** → 猶予超過で通知。
              あわせてGitHub Actionsの失敗通知も飛ぶ」
      §6-2-2 採用根拠 #2
             「案Bは**バッチが止まる全ての原因**（無効化・cron遅延・実行失敗・
               Neon障害）を検知できる」

  実装の挙動（`backend/scheduler.py` を確認）:

    (1) `run_batch()` は RSS 全ソース失敗時に**例外を投げず return する**

        # scheduler.py L57-70
        entries, source_name, is_fallback = fetch_rss()
        if not entries:
            error_message = "All RSS sources failed"
            logger.error(error_message)
            crud.save_fetch_log({... "error_message": error_message})
            return        # ← 例外ではなく正常終了

    (2) `run_game_schedule_batch()` は**全体が try/except で包まれ、
        どんな失敗でも例外を出さない**

        # scheduler.py L190-246
        def run_game_schedule_batch() -> None:
            try:
                ...（BALLDONTLIE取得・DB書き込み・削除）...
            except Exception as exc:
                logger.error("run_game_schedule_batch failed: %s", exc)
                # ← 再送出しない

    (3) Claude API の RateLimitError も例外にならない
        `api_limit_exceeded=true` を立てて `continue` する仕様
        （リスク調査書・CLAUDE.md の設計どおり）

  問題:
    上記のいずれの失敗も**例外にならない**ため、

      `run_batch_once.py` は正常終了する（終了コード0）
        → GitHub Actions のジョブは**成功**扱い → 失敗通知は飛ばない
      末尾の ping は**実行される**
        → 外部cron監視は**正常**と判定する

    つまり **「バッチは走ったが記事が1件も取れていない」状態を、
    2つの「主」の監視がどちらも検知できない。**

    実際に例外が出るのは、`init_db()` や `crud` の呼び出しがDB接続に失敗した場合
    （Neon障害）くらいである。採用根拠 #2 が挙げた4原因のうち、
      無効化・cron遅延 → ✅ ping が来ないため検知できる
      Neon障害         → ✅ 例外になり非ゼロ終了・ping せず
      **実行失敗**     → ❌ **RSS全滅・試合日程取得失敗は検知できない**

    残る検知手段は §6-2-2 の「従」——週次チェックリストで `last_fetched_at` を
    確認——のみである。RSS全滅時は `run_batch()` が ⑩（`set_setting`）に到達せず
    `last_fetched_at` が更新されないため、停滞として検知できる。
    ただし**週1回**であり、YEL-03（v0.2）で解消したはずの
    「最大7日の検知遅れ」が、この経路には残っている。

  推奨対応:
    ping の発火条件を「プロセスが完走したこと」から
    「**バッチが目的を達したこと**」に変える。実装コストの小さい順に3案。

      案A：**`fetch_logs` の最新レコードを見て判定する**
           `run_batch()` は成功・失敗いずれの場合も `save_fetch_log()` を呼ぶ。
           `run_batch_once.py` の末尾で最新の `fetch_log` を取得し、
           `error_message` が非NULL なら **ping せず非ゼロ終了**する。
           既存のデータ構造をそのまま使え、`scheduler.py` に手を入れない。

      案B：**`run_batch()` の戻り値を使う**
           現在 `None` を返しているため、`fetched_count` や成否を返すよう変更する。
           `scheduler.py` の変更が必要になるが、意図が明確になる。
           APScheduler 側（要望1が不採用の場合）は戻り値を無視すればよい。

      案C：**`run_batch()` の early return を例外に変える**
           既存の動作（APScheduler 経由では例外がログに出るだけ）が変わるため、
           影響が最も大きい。**推奨しない。**

    **案Aを推奨する。** `scheduler.py` を変更せずに済み、
    §5-2 の「バッチが単独で自己完結する」という方針とも一貫する。

    あわせて次を修正する。
      ・§6-2-2 採用根拠 #2 の「バッチが止まる**全ての原因**」を
        「バッチが**実行されなくなる**原因」に限定するか、
        案Aを採る前提で「**取得に失敗した場合も含む**」と書き直す。
      ・§5-2 の「終了コード」行に、
        「**例外だけでなく `fetch_logs` の `error_message` も判定に含める**」を追記。
      ・§8 に「`run_batch_once.py` の成否判定の実装」を引き継ぎとして追加。

  重要度の根拠:
    §6-2-2 は v0.3 の中心的な変更であり、YEL-03（v0.2）への対応として
    「検知の速さを最大7日から約5時間に短縮する」ことを目的にしている。
    その目的が**一部の失敗原因に対しては達成されていない**。
    設計の方向は正しいため、発火条件の修正で解消できる。

[GRN-03] `HEALTHCHECK_PING_URL` が未設定の場合の挙動と、
         ローカル実行時に ping しない仕組みが定義されていない

  §6-2-2 の「外部cron監視の設計」は
    | ping URL | **GitHub Secrets に登録**（`HEALTHCHECK_PING_URL`） |
  としているが、次の2点が未定義である。

    (1) **環境変数が未設定のときの挙動**
        `run_batch_once.py` はローカルでも実行しうる
        （手順4・手順5での動作確認、移行前の検証）。
        未設定時に ping をスキップするのか、エラーにするのかが決まっていない。
        `config.py` の必須チェック（§5-5 案A）に加えるかどうかも不明である。
        **バッチの目的に必須ではないため、未設定なら黙ってスキップするのが妥当**だが、
        明記がないと実装者が判断することになる。

    (2) **ローカル実行時に ping が飛ぶと監視が誤判定する**
        開発者が動作確認のためローカルで `HEALTHCHECK_PING_URL` を設定して
        実行すると、監視サービスは「バッチが動いた」と記録する。
        **本番のバッチが止まっていても、ローカル実行で ping が入れば
        通知が出ない**という状態になりうる。

  → §6-2-2 に2行追記する。
      「`HEALTHCHECK_PING_URL` が**未設定なら ping をスキップ**する
        （必須チェックには加えない）」
      「**GitHub Actions 上でのみ設定する**。ローカルでは設定しない
        （設定すると本番の停止を隠してしまう）」

  補足:
    (2) は「監視を欺く」典型的な落とし穴である。
    §6-2-2 が ping の位置（末尾）について
    「先頭や中間に置くと…成功と区別できなくなる」と丁寧に論じているのと
    同じ水準で、**どこから ping するか**も決めておく価値がある。
